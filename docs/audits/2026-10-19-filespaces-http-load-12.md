# Проверка HTTP-нагрузки Files 1.2 — 19 октября 2026 года

## Что действительно испытано

Добавлен изолированный повторяемый стенд в GitHub Actions:
[Nginx + PHP-FPM 8.3 + MySQL 8.4](../../.github/workflows/filespaces-http-load-12.yml).

- Приложение запускается через **настоящий index.php**, а не заглушку контроллера.
- Восемь независимых HTTP-клиентов входят с действительными сессиями и защитными токенами.
- В течение 12 секунд выполняется смесь чтения общего каталога, скачивания и загрузки небольших текстовых файлов. Для загрузок используются случайные уникальные имена и контроль версии родителя.
- HTTP 409 считается ожидаемым только при конкурентной загрузке в изменившийся каталог. Ошибки авторизации, некорректное содержимое файла и ответы 5xx проваливают испытание.
- Измеряются p50/p95/p99 с позиции HTTP-клиента, счётчики MySQL, активные процессы и очередь PHP-FPM, суммарная RSS-память процессов, изменение свободного дискового пространства.
- После завершения отдельно проверяется, что база содержит загруженные файлы и не содержит дублирующих имён в каталоге.
- Исходные пользовательские данные не используются. Тест работает только на одноразовой базе fsp_http_load, отдельном приватном каталоге и локальном адресе 127.0.0.1:18096.

Лимит входа и CSRF не отключаются. Только для одноразового CI-стенда порог авторизации установлен на 25 попыток, чтобы восемь независимых сеансов могли пройти с одного локального адреса.

Эти показатели нельзя сравнивать как одинаковую нагрузку.

## Как воспроизвести

Открыть [проверку Files 1.2 — HTTP-нагрузка](../../.github/workflows/filespaces-http-load-12.yml)
в GitHub Actions и запустить вручную. Скрипт ограничивает нагрузку
8 клиентами и 12 секундами. Машина CI автоматически создаёт
и уничтожает Nginx/PHP-FPM и одноразовое хранилище.

Результат сохраняется в обезличенном файле
**filespaces-http-load-metrics** сроком на семь дней.
Секреты из .env, пользовательские cookie и содержимое файлов туда не включаются.

**Не направлять скрипт на производственный адрес.** Для отдельного
стенда сначала подготовить тестовую БД, временную лицензию,
разрешения на приватный каталог и ограничение интенсивности запросов.
Изменение пользователя процессов веб-сервера в CI — особенность временной
рабочей копии GitHub Runner, а не инструкция по настройке производства.

## Вердикт и открытые риски

На данном ограниченном HTTP-стенде не обнаружено серверных ошибок и
нарушений целостности. PHP-FPM не заполнял очередь при восьми сеансах.

При этом **примерно 225 SQL-запросов на HTTP-ответ** являются сигналом
для отдельного профилирования маршрутов и сокращения повторных
обращений к данным: под нагрузкой сотен пользователей это может стать
ограничением раньше, чем PHP-FPM. Сначала нужно разделить запросы входа,
просмотра, скачивания и записи и снять точный профиль SQL.

Остаются обязательными перед производственной готовностью Files 1.2:
- длительная смешанная нагрузка на **отдельном стенде** с параметрами реального сервера, а не 12-секундная проверка на GitHub Actions;
- испытания 1000 одновременных пользователей, если именно этот предел выбран для выпуска, с контролем p95/p99 и ошибок;
- параллельный отзыв ACL при чтении, загрузке и скачивании;
- проверка конфигурации Nginx/Apache на реальном сервере и запрета публичных путей;
- проверка полного восстановления резервной копии БД вместе с физическими файлами.

Итог: **тест HTTP-нагрузки разработан и выполнен**, но промышленная
приёмка под тысячу клиентов пока **не подтверждена**.
