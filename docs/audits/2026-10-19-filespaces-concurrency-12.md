# Конкурентная приёмка Files 1.2 — 19 октября 2026 года

## Состояние

Профильные проверки с реальными независимыми PHP-процессами успешно
выполнены на двух конфигурациях MySQL 8.4: без префикса таблиц и с
`DBPREFIX=fsp_`. Использовался PHP 8.3 на исполнителях GitHub Actions.
Код хранилища и личные файлы не изменялись; добавлен воспроизводимый
контур испытаний в `tests/integration/filespaces_concurrency_12_scenarios.php`
и `tests/integration/filespaces_concurrent_worker_12.php`.

## Методика

Каждая волна создаёт **восемь независимых PHP-процессов**, каждый со
своим соединением с базой. Перед стартом действия процессы ожидают общего
барьера, после чего выполняют одну конкурирующую операцию.

Проверяются:
- параллельная загрузка в один каталог с одной ожидаемой версией:
  ровно одна успешная операция, семь конфликтов;
- восемь одновременных повторов одной завершённой команды:
  одна квитанция без дублирования физического файла;
- переименование и перемещение одного объекта:
  ровно один победитель, семь конфликтов версий;
- одновременное изменение одного ACL:
  ровно одно сохранённое правило, семь конфликтов;
- удаление и восстановление одного файла:
  ровно одно изменение, семь отклонённых уже выполненных операций;
- проверка исходных байтов файла после удаления и восстановления.

Дочерние процессы завершаются с ограничением по времени;
сбой процесса или нераспознанная ошибка приводит к падению приёмки.
Для повторяемости используются изолированная тестовая БД и временный
приватный каталог. Тест включён в узкий CI Files, а не во все системные
испытания.

## Измерения

**p95 относится ко времени выполнения одной операции внутри рабочего
PHP-процесса после общего барьера**; запуск интерпретатора, подготовка
соединения и ожидание остальных процессов в него не входят.
В каждой строке всего восемь наблюдений, поэтому это диагностическая
характеристика, а не статистически устойчивый показатель производства.

| Конкурирующая операция | p95 без префикса, мс | p95 с префиксом, мс |
|---|---:|---:|
| Загрузка | 49,1 | 38,9 |
| Повтор загрузки | 37,6 | 30,8 |
| Переименование | 57,5 | 52,4 |
| Перемещение | 73,7 | 75,1 |
| Изменение ACL | 42,2 | 30,2 |
| Удаление | 51,5 | 47,5 |
| Восстановление | 46,5 | 38,8 |

Для восьми процессов **в фазе перемещения** MySQL зафиксировал
282 запроса в обоих вариантах БД. Для загрузки — 119,
повторных загрузок — 107, переименования — 192,
ACL — 134, удаления — 184, восстановления — 169.

Это значения глобального счётчика `Queries` за короткую фазу;
они включают создание соединений и служебные обращения приёмки и
не являются точным профилем SQL каждой операции.

Отчёт о пиковом потреблении памяти PHP показал до **4 МиБ на процесс**
при загрузке и до **2 МиБ на процесс** в остальных сценариях.
Не учитываются ресурсы MySQL, PHP-FPM, веб-сервера и реальные файлы
производственного объёма.

## Вывод и границы

Ошибок целостности данных в проверенных сценариях не обнаружено:
дубликатов файлов, двойных изменений, обхода конфликтов версий или
порчи восстановленного содержимого нет.

**Это не испытание 1000 одновременно работающих пользователей.**
Не измерялись длительная работа со смешанными запросами,
веб-маршруты с PHP-FPM и браузером, реальные размеры пользовательских
файлов, конкурирующие отзыв прав и чтение, а также дисковая
нагрузка на конкретном сервере.

Для производственной готовности остаются:
1. Длительное смешанное испытание реального веб-стенда с ограниченными
   параметрами ресурсов, метриками ошибок, p95/p99, MySQL и диска.
2. Контроль отзыва ACL одновременно с загрузкой, перемещением и
   выдачей файлов в браузере.
3. Проверка резервного копирования и восстановления общей БД
   **вместе** с приватными физическими файлами.
4. Проверка конфигурации Nginx/Apache и невозможности прямого
   обращения к приватному каталогу.

До выполнения этих условий не присваивать Files 1.2 статус
производственной готовности под тысячу одновременных пользователей.
