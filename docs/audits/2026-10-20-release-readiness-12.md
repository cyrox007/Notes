# Notes 1.2.0 — итоговый аудит готовности к выпуску

**Дата:** 20 октября 2026 года.  
**Исследованная ветка:** `1.2`.  
**Точный исходный коммит:** `7f560018b7a78a3508d0731e9c5b6b95e4ef4f31` (слияние PR #407).  
**Решение аудита:** **НЕ ГОТОВ К ПУБЛИКАЦИИ / БЛОКИРОВАН**.

Это **срез** исходников и доступных GitHub-проверок на указанном коммите, а не утверждение, что все серверные сценарии были повторно выполнены на этом коммите. После новых изменений необходимо обновить аудит и получить доказательства для нового точного SHA.

## Метод проверки

Проверены дерево файлов и `module.json`, `core/Version.php`, `composer.json`, канонический `database/migrations/manifest.json`, важные SQL-миграции, маршруты Tasks, криптографический обработчик Messenger, код уведомлений, процессы GitHub Actions, документация релизов, планы 1.2 и статус задач/PR.

Для ограниченной нагрузки изучены результаты HTTP-стендов на Nginx/PHP-FPM 8.3/MySQL 8.4. **Ни install/update/rollback с опубликованной 1.1.0, ни 1000-пользовательская нагрузка, ни ручная приёмка Windows/OSPanel на точном SHA в рамках этого аудита не запускались.** Отсутствие доказательства не записывается как успешный тест.

Критерий выпуска определён в `docs/plans/1.2-unified-cycle.md`. Все обязательные части должны быть реализованы и приняты либо явно исключены отдельным решением владельца проекта. Нельзя менять версию на `1.2.0 stable` просто потому, что зелёные проверки нескольких модулей.

В последней серии (см. `docs/audits/2026-10-20-notes-staged-capacity-12.md`) для 12 клиентов зафиксированы p95 **150,59 мс** у «Дефектов» и **181,52 мс** у Files, без неожиданных HTTP-ошибок. В Files число ожиданий блокировок InnoDB на трёх ступенях: 5 → 9 → 18. Ресурсы и скорость GitHub-runner недостаточно стабильны, чтобы экстраполировать эти значения на 1000 пользователей.

## Отдельные риски и недостающие доказательства

### Миграции и данные

- `database/migrations/manifest.json` содержит миграции `20261019_defects_foundation.sql`, `20261019_defects_history.sql`, `20261019_defects_reference_versions.sql` в правильном логическом порядке. Однако `defects_schema.sql` уже содержит колонку `version`, а последняя миграция добавляет её через `ALTER TABLE` без условного `IF NOT EXISTS`. **Это не доказанная ошибка:** свежая установка и обновление должны по-разному формировать журнал миграций. Обязательно проверить этот порядок в реальном инсталляторе, повторе миграций и обновлении существующей базы.
- Для `DBPREFIX` нужны SQL-сценарии на реальных MySQL/MariaDB, в том числе защита от изменения чужих таблиц в общей базе и совместимость триггеров, индексов и внешних ключей.
- Тесты сервиса на SQLite и краткая установка с MySQL 8.4 не заменяют проверку миграций опубликованной 1.1.0 и сохранения пользовательских данных.
- До релиза подтвердить резервную копию, восстановление в чистое окружение, прерывание в критических фазах, rollback и повторное применение.

### Безопасность и платформа

- Штатные RBAC, CSRF, жизненный цикл модулей и ограничение памяти обновлятора присутствуют. Это **не полная независимая приёмка безопасности** и не доказательство отсутствия всех уязвимостей.
- Подписанные релизные артефакты, хранение production-ключей, отзыв токенов, перенос между машинами и операционная церемония требуют отдельного протокола на точном RC. Секреты, закрытые ключи и токены не должны попадать в отчёт.
- Для Windows выбранный режим `UpdateProcessRunner` ограничивает память, но пишет **временный вывод на диск**. При огромном диагностическом потоке контролировать свободное место и права каталога — отдельный [эксплуатационный риск #427](https://github.com/cyrox007/Notes/issues/427); положительный тест 12 МиБ не доказывает неограниченную дисковую устойчивость.
- Отдельно проверить реальный сценарий ручной работы на OSPanel 5.2.2 и мобильных устройствах. GitHub CI не замещает этого подтверждения.

### Релизная идентичность и документация

- GitHub latest release на момент аудита — [`v1.1.0`](https://github.com/cyrox007/Notes/releases/tag/v1.1.0). Ветку `1.2` нельзя объявлять уже опубликованной stable.
- Документы `docs/RELEASE_ACCEPTANCE.md`, `docs/RELEASE_EVIDENCE.md`, `docs/RELEASE_GOVERNANCE.md` относятся к прежним линейкам; их нельзя повторно применять к выпуску 1.2 без адаптации.
- README, CHANGELOG, код версии, дата, требования PHP, манифесты, инструкции обновления, поддерживаемые окружения и релизные подписи должны совпасть **на том же exact-head**, который пройдёт финальный барьер.
- Сохранённые в Git ветки без открытых PR не требуют механического слияния: каждая функция принимается в `1.2` через явную PR и проверку. На дату аудита открытых PR было 0; позже могут появиться новые.
