# Notes 1.2 — SQL-профиль и сокращение лишних запросов «Дефектов»

Дата: 20 октября 2026 года.

## Зачем проводилась проверка

Ограниченная HTTP-нагрузка модуля показала высокий глобальный счётчик запросов MySQL. Сам по себе счётчик \`Queries\` недостаточен, чтобы определить виновника: он включает системные операции, проверку схемы и измерители. Поэтому дополнен существующий стенд \`.github/workflows/defects-http-load-12.yml\`.

Измеритель \`tests/integration/defects_http_sql_profile_12.py\` временно включает журнал выполняемых команд MySQL **только на одноразовой базе \`defects_http_load\`**. Для каждого HTTP-маршрута записывает количество реально выполненных SQL-команд, разбивку по подсистемам и нормализованные шаблоны без параметров. Журнал выключается до двенадцатисекундного нагрузочного прогона; сырой журнал и секреты в артефакты не попадают.

Профиль применяется к обычному и фильтрованному реестру, обычной и фильтрованной сводке, карточке, истории, регистрации и закрытию.

## Выявленные издержки

В базовом измерении без оптимизации было зафиксировано:

| Маршрут | SQL за 8 HTTP до | SQL на HTTP до |
| --- | ---: | ---: |
| Реестр | 201 | ~25 |
| Реестр с фильтрами | 201 | ~25 |
| Сводка | 225 | ~28 |
| Сводка с фильтрами | 225 | ~28 |
| Карточка | 209 | ~26 |
| История | 217 | ~27 |

На каждом запросе в \`Core\ModuleLifecycleStore::reconcile\` происходили **восемь UPDATE \`module_lifecycle\`** независимо от того, изменились ли состояние, контрольная сумма, версия или сообщение об ошибке. Семь запросов относились к другим модулям, ещё один — к «Дефектам». Прежде классификатор ошибочно относил эту последнюю запись к предметным запросам из-за текстового параметра \`module_id='defects'\`; классификация исправлена.

Сводка \`DefectReportService::summary\` выполняла четыре отдельные выборки: общее количество, просроченные записи, группы приоритетов и группы участков. Первые три читали одинаковый набор записей.

## Что исправлено

1. **Ядро.** В \`ModuleLifecycleStore::reconcile\` запись выполняется только если различаются установленная версия, отпечаток манифеста, расчётное состояние или ошибка. Проверка прав и лицензионных ограничений остаётся на каждом запуске; изменения сохраняются без задержки.
2. **Модуль.** Количество, просрочка и разбивка по приоритетам вычисляются одним группирующим запросом, а разбивка по участкам остаётся отдельной ограниченной выборкой. Итог: две SQL-выборки вместо четырёх, без изменения ответа API.
3. **Контракты.** Интеграционный тест \`module_lifecycle_noop_12.php\` проверяет отсутствие SQL UPDATE при неизменной композиции и наличие записи при изменении контрольной суммы, версии и состояния. Тест \`defects_reporting_12.php\` проверяет две выборки и нулевые итоги при пустых данных. Нагрузочный профилировщик теперь завершает CI ошибкой при обнаружении ненужного \`UPDATE module_lifecycle\`.

## Повторный замер после оптимизации

При тех же восьми последовательных HTTP-запросах каждого маршрута, на одноразовом MySQL 8.4:

| Маршрут | SQL до | SQL после | Изменение |
| --- | ---: | ---: | ---: |
| Реестр | 201 | 137 | −64 (−31,8 %) |
| Реестр с фильтрами | 201 | 137 | −64 (−31,8 %) |
| Сводка | 225 | 145 | −80 (−35,6 %) |
| Сводка с фильтрами | 225 | 145 | −80 (−35,6 %) |
| Карточка | 209 | 145 | −64 (−30,6 %) |
| История | 217 | 153 | −64 (−29,5 %) |
| Регистрация, 1 запрос | 40 | 32 | −8 |
| Закрытие, 1 запрос | 36 | 28 | −8 |

Подсчёт включает системные SQL-команды и настройки соединения. Это сокращение **количества запросов**, не гарантированное ускорение всей системы.

Последующая параллельная HTTP-проверка сохранила нулевое число неожиданностей и прошла проверку конкурирующих команд. Но общая пропускная способность в двух запусках непостоянного GitHub-runner отличалась (около 138,6 и 97 запросов/с), а p95 изменился с 59,6 до 93,2 мс. **По этим запускам нельзя утверждать, что пользовательские ответы стали быстрее.** Для доказательства ускорения нужен отдельный контролируемый повтор с фиксированными ресурсами и несколькими сериями A/B.

## Остаточные расходы и дальнейшая приёмка

В профиле остаются три чтения \`module_lifecycle\`, три чтения настроек и проверки структуры БД на один запрос. Это общеплатформенные вызовы, их нельзя устранять простым отключением проверок лицензии, прав или структуры. Для следующих оптимизаций требуется отдельный анализ их жизненного цикла и сценариев изменения прав в процессе работы.

Ограниченные 8 клиентов на 12 секунд **не заменяют** общую приёмку 1.2 на 1000 параллельно активных пользователей. Её необходимо проводить на отдельной инфраструктуре с известным бюджетом памяти, CPU, профилем рабочих операций, p95/p99, длительным прогоном, контролем очередей и целостности, а не экстраполировать результаты CI.
