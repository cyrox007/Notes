# Files 1.2: раздельный SQL-профиль HTTP-маршрутов — 19 октября 2026 года

## Предмет проверки

После [HTTP-нагрузки PR #393](2026-10-19-filespaces-http-load-12.md)
общий счётчик MySQL давал около 222–225 команд на один учтённый ответ.
Это было **ориентировочное**, а не помаршрутное измерение.
Первоначальный клиент не учитывал в числе ответов дополнительный HTTP GET
формы перед каждой загрузкой. Этот запрос теперь учитывается отдельно.

Для анализа создан [SQL-профиль](../../tests/integration/filespaces_http_sql_profile_12.py),
который выполняется внутри
[изолированного HTTP-стенда](../../.github/workflows/filespaces-http-load-12.yml):

- настоящие Nginx, PHP-FPM 8.3, MySQL 8.4 и индексный маршрут приложения;
- действительная авторизация, сессия и CSRF, без обхода проверок;
- три последовательных HTTP-запроса каждого типа: каталог, скачивание, загрузка;
- одна временная база fsp_http_load, один клиент, без фоновой нагрузки;
- 30 удалённых объектов в одном каталоге для воспроизводимой проверки корзины;
- счётчик SQL-команд Query и Execute из временного mysql.general_log
  (без повторного учёта подготовительных Prepare);
- в опубликованном отчёте только группы команд и имена таблиц, без значений
  параметров, паролей и содержимого файлов.

Временный общий журнал MySQL включается строго вокруг каждого отдельного
HTTP-запроса, затем выключается; контейнер MySQL удаляется по окончании работы.
**Такой метод не включать на рабочем сервере.** Нагрузочный клиент работает
отдельно при выключенном подробном SQL-журнале.

## Изменения кода

- FileSpaceAccessService: несколько прав на один объект проверяются вместе;
  пользователь, родительская цепочка и набор подходящих ACL загружаются по
  одному разу в рамках операции. Нет долговременного кеша прав.
- FileSpaceFolderService: права на просмотр, список, загрузку, создание и
  настройку ACL рассчитываются одним набором; пакетные права детей сохранены.
- FileSpaceTransferService: права на просмотр и скачивание проверяются
  вместе, причём удалённые предки всё равно закрывают доступ.
- FileSpaceObjectService: права view и restore, а также версия одного
  родительского каталога используются повторно при построении одной корзины.
  При следующем HTTP-запросе они снова проверяются.
- В контрактных тестах проверяются выдача и отзыв ACL, явный запрет,
  появление актуальных прав при новом вызове и содержимое корзины.
- В SQL-профиле установлены регрессионные пределы: **150** команд для каталога,
  **55** для скачивания и **80** для загрузки. Они применяются к конкретному
  изолированному сценарию, а не объявляются нормативом для произвольного сайта.

## Повторная смешанная нагрузка

В прогоне после оптимизации за 12 секунд зарегистрировано 525 HTTP-ответов:
494 ответа HTTP 200, 31 ожидаемый HTTP 409, **0 неожиданных ошибок**.
p95 — 175,95 мс, p99 — 201,52 мс. Предварительное чтение формы
перед загрузкой теперь включено в число ответов и распределение задержек,
поэтому численные итоги не полностью сопоставимы с PR #393.

## Ограничения

Статистика отражает конкретный объём тестовых данных, действующий маршрут
и короткий одноразовый CI-стенд, а не промышленную нагрузку. Подробный
SQL-журнал влияет на время ответа, поэтому p50 из SQL-профиля не следует
сравнивать с обычными HTTP-бенчмарками.

Значительная постоянная часть SQL-запросов относится к запуску приложения:
в частности, повторно проверяется и обновляется module_lifecycle.
Это отдельное направление оптимизации ядра, не повод ослаблять ACL Files.

Не проверены тысяча одновременных пользователей, длительная нагрузка на
сервере с фактической конфигурацией, отзыв ACL одновременно с передачей
большого файла и полное восстановление резервной копии с содержимым файлов.
Эти задачи остаются отдельными условиями промышленной приёмки.
