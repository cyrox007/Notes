# Проверка границ модулей Notes 1.2 после PR #395

Дата: 19 октября 2026 года.

## Исходные архитектурные требования

Перед изменениями изучены:
- [MODULE_DEVELOPMENT.md](../MODULE_DEVELOPMENT.md);
- [MODULE_PLATFORM.md](../MODULE_PLATFORM.md);
- [MODULE_RUNTIME_ISOLATION_1.0.md](../MODULE_RUNTIME_ISOLATION_1.0.md);
- [DB_ARCHITECTURE.md](../DB_ARCHITECTURE.md).

Ядро предоставляет интерфейсы, подключение к БД, транзакции и загрузку
модулей. Каждый модуль владеет собственной схемой, а остальные получают
его услуги через объявленную и доступную во время работы возможность.

## Ошибка прежнего приёмочного вывода

PR #395 устранил найденные прямые вызовы PDO, но проверка «0 нарушений»
не учитывала использование `DatabaseManager` для чтения чужой таблицы.
Она не проверяла косвенные зависимости через модели соседнего модуля.
Проверка прямого PDO остаётся полезной, но не может заменить аудит
модульной архитектуры.

## Подтверждённые нарушения и исправления

1. Admin читал `user_to_dialogs` и `dialogs` Messenger при
   деактивации и запросе на удаление аккаунта. Теперь проверка выполняется
   через существующий `Core\AccountDeactivationGuard` в
   `MessengerCapability`.
2. Admin читал `task_boards` и `task_board_members` Tasks.
   Проверка владения передана `TasksCapability` через тот же интерфейс.
3. Admin напрямую вызывал `UserAvatarService` из Profile.
   Очистка переведена на `Core\AccountAvatarCleanup` и
   `ProfileCapability`.
4. Контроллер Admin непосредственно управлял `user_fields` из Profile
   и обращался к общей модели поля. Теперь выполнение запросов,
   блокировка строк и транзакция находятся в модуле Profile; Admin
   вызывает `Core\ProfileCustomFields`.
5. Добавлена проверка SQL-литералов по владельцам таблиц в `module.json`.
   В текущих модулях после исправления она находит **0 явных
   обращений к чужим таблицам или файловых подключений**, но не
   претендует на анализ произвольного динамического SQL.

## Защита данных при отключённых модулях

Если Messenger или Tasks недоступен и невозможно проверить, что
пользователь передал владение общими объектами, Admin **отказывает**
в деактивации или постановке на удаление. Отключение или потеря лицензии
не удаляют данные модуля, поэтому пропуск проверки был бы небезопасен.
Это сознательная ограничительная мера, требующая дальнейшего развития
фоновой платформенной проверки без запуска отключённого модуля.

## Нерешённая инфраструктурная задача

В `app/services/RetentionService.php` остаётся существующая проверка
чужих таблиц для самостоятельной фоновой очистки. Эта процедура может
запускаться без пользовательской композиции модулей. Простое удаление
SQL-запросов сделало бы возможным удаление аккаунта с непереданными
общими объектами. Для полного исправления необходим отдельный
интерфейс безопасной проверки владения, доступный фоновой очистке и
учитывающий установленные, но неактивные модули.

До такой переработки нельзя заявлять о полном устранении
всех архитектурных исключений проекта.

## Приёмочные проверки

- контракт загрузки, manifest и реестра возможностей;
- проверка владения таблицами в SQL-литералах всех модулей;
- проверка обеих ветвей блокировки через подставные реализации;
- реальные SQLite-запросы `TasksCapability` и
  `MessengerCapability`, в том числе отсутствие ложных блокировок;
- прежняя проверка обращений к PDO;
- PHP 8.3, целостность команд и контроль версий.

Ограничение статической проверки: динамические запросы,
неявные обращения через общие модели и новые формы подключения
проверяются отдельно на ревью.
