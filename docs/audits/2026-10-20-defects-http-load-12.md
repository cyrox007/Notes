# Notes 1.2 — нагрузочная приёмка модуля «Дефекты» по HTTP

## Назначение

Проверить настоящие маршруты модуля при ограниченном параллелизме, а не только вызовы сервисов или имитацию ответов. Стенд собирается в GitHub Actions из канонических схем и запускает **Nginx, PHP-FPM 8.3, MySQL 8.4** на локальном адресе. Для изменения данных используется временная подписанная CI-лицензия с явно включённым \`workspace.defects\`. Производственные лицензии и данные не используются.

## Подготовка данных

Скрипт \`tests/integration/defects_http_seed_12.php\` создаёт одноразового пользователя, четыре участка, 12 категорий, 48 объектов, четыре службы и 720 открытых дефектов с начальными событиями истории. Разрешена только база \`defects_http_load\`; создание данных вне неё запрещено. Тестовый SQL не используется внутри рабочего модуля.

## Сценарии

Скрипт \`tests/integration/defects_http_load_12.py\` выполняет настоящий вход независимых HTTP-сеансов. Каждый клиент циклически читает реестр, отчёт, карточку и историю, регистрирует дефект и закрывает его. Изменяющие запросы передают штатный CSRF-токен и идентификатор команды. После параллельной нагрузки отдельно проверяются:

- Два одновременных запроса регистрации с одним идентификатором команды и одинаковыми данными: одна запись, один ответ с признаком повтора.
- Повтор уже завершённой регистрации: тот же идентификатор дефекта.
- Одновременное закрытие одной карточки двумя сеансами с одинаковой ожидаемой версией: ровно один успех и один конфликт \`409\`.
- Повтор команды, победившей при закрытии: отсутствие второй записи в истории; описание выполненных работ не теряется.
- SQL-проверка: у каждой созданной при нагрузке карточки одна запись истории регистрации, одна закрытия, версии увеличены ровно на единицу, есть ответственные службы.

## Показатели

Отдельный JSON-отчёт содержит число успешных запросов, число активных клиентов, длительность, пропускную способность, распределение операций, p50/p95/p99 задержек, приблизительное число запросов MySQL за интервал, максимальное число занятых PHP-FPM-процессов, очередь PHP-FPM и суммарную память процессов PHP-FPM. Данные не содержат паролей, cookie и значений токенов.

**Условие прохождения текущего CI:** все рабочие операции успешны, обнаружена хотя бы одна операция каждого типа, нет неожиданных HTTP-ошибок, подтверждена целостность параллельного закрытия и доступны замеры ресурсов. Значения задержек фиксируются, но пока не сопоставляются с производственным соглашением об уровне сервиса (оно не определено).

## Как запускается

В рабочем процессе \`.github/workflows/defects-http-load-12.yml\` штатный ограниченный профиль:

\`\`\`bash
python3 tests/integration/defects_http_load_12.py \
  --origin http://127.0.0.1:18097 \
  --fixture /tmp/defects-http-fixture.json \
  --out /tmp/defects-http-load-report.json \
  --concurrency 8 --seconds 12
\`\`\`

Скрипт намеренно допускает только локальный HTTP-адрес, 2–16 клиентов и 3–45 секунд. На собственной тестовой инфраструктуре при увеличении параллелизма сначала требуется согласовать ресурсы и предельные задержки, затем воспроизвести реальные профили нагрузки.

## Ограничения результатов

Это **ограниченный регрессионный HTTP-стенд**, а не доказательство готовности системы к 1000 одновременно активным пользователям. Проверка на 1000 пользователей требует отдельного согласованного многопользовательского стенда, длительной нагрузки, реального распределения операций и оценки всей системы, включая соседние модули. В отчёте нельзя экстраполировать измеренную пропускную способность на 1000 пользователей.

Ручная визуальная приёмка на физических устройствах также остаётся отдельным этапом.
