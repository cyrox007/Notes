# Резервная HTTP-доставка уведомлений в 1.1

Дата: 2026-10-12

## Назначение

Основным способом внешней доставки уведомлений остаётся ограниченный запуск `php bin/notifications_worker.php` по cron или через планировщик задач. Для shared-hosting, где постоянный worker недоступен или cron временно не выполняется, добавлен резервный HTTP-проход очереди.

Резервный механизм не заменяет cron. Его задача — не позволить очереди внешних уведомлений зависнуть навсегда при отсутствии фонового процесса.

## Ограничения HTTP-прохода

- за один HTTP-проход обрабатывается не более 3 заданий;
- один экземпляр приложения запускает такой проход не чаще одного раза в 60 секунд;
- параллельные запросы защищены неблокирующей advisory-блокировкой MySQL;
- занятая блокировка сразу прекращает резервный проход и не заставляет пользовательский запрос ждать;
- повторная проверка времени выполняется уже после получения блокировки;
- время разрешённого прохода фиксируется до начала внешней доставки, поэтому серия медленных или ошибочных SMTP-попыток не создаёт лавину новых запусков.

## Влияние на HTTP

Резервная доставка регистрируется как shutdown-задача после обычной загрузки приложения.

Перед обработкой очереди:

- закрывается активная PHP-сессия, чтобы не удерживать блокировку сессии пользователя;
- при наличии FastCGI вызывается `fastcgi_finish_request()`, поэтому ответ клиенту завершается до внешней доставки;
- long-poll Messenger, `HEAD`, `OPTIONS` и выдача `module-assets` не используются как триггер резервной доставки.

На хостингах без `fastcgi_finish_request()` задача всё равно остаётся строго ограниченной размером пакета и частотой запуска.

## Отказоустойчивость

HTTP и CLI используют общий `NotificationDeliveryRuntime` и одну реализацию `NotificationDeliveryWorker`. Очередь сохраняет существующие гарантии:

- атомарный захват заданий через `FOR UPDATE`;
- идентификатор владельца обработки;
- восстановление зависших заданий в состоянии `processing`;
- учёт номера попытки;
- контролируемый повтор после временной ошибки;
- отсутствие повторной успешной доставки уже завершённого задания.

Состояние ограничения частоты хранится в таблице `notification_runtime_state`, которая создаётся только миграцией `20261012_notifications_http_fallback.sql`. Runtime не изменяет схему БД во время пользовательских запросов.

## Безопасность

- SMTP-секреты по-прежнему разрешаются через `secret_ref`, а не хранятся в открытой конфигурации;
- ошибка резервного запуска не ломает пользовательский ответ;
- в системный журнал записывается тип исключения, но не его текст, чтобы случайно не вывести секретные данные;
- HTTP fallback использует те же адаптеры каналов, что и CLI worker, отдельного обходного пути доставки нет.

## Проверки

Профильный набор тестов проверяет:

- ограничение пакета тремя заданиями;
- интервал 60 секунд;
- неблокирующую MySQL-блокировку;
- обработку пяти заданий за два разрешённых прохода без дублей попыток;
- регистрацию миграции в каноническом `manifest.json` и `DatabaseOwnership`;
- отсутствие runtime-DDL;
- общий runtime для cron и HTTP;
- безопасное подключение shutdown-механизма к HTTP entry point.

Эта работа закрывает shared-hosting fallback внешней доставки в рамках #233, но сама по себе не означает закрытие всех критериев общего центра уведомлений 1.1.
