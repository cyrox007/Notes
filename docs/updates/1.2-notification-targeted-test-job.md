# Notes 1.2 — адресная проверка доставки уведомлений

## Исправленное поведение

При отправке пробного уведомления из административной панели система публикует диагностическое событие через общий `NotificationService`. После постановки задания обработчик захватывает **только его идентификатор**, вместо первого готового задания общей очереди.

Захват выполняет `DatabaseNotificationDeliveryQueue::claimJob()` через `Core\\DatabaseManager` с блокировкой `FOR UPDATE`, проверкой состояния, времени следующей попытки и права пользователя на получение. Выполнение сохраняет штатные записи об успешных попытках, повторной отправке и окончательной ошибке. Для обычного обработчика `claimBatch()` поведение не изменено.

Если задание уже забрал другой обработчик или оно ожидает повторной попытки, адресная проверка не пытается отправить вместо него постороннее сообщение. В админке показывается текущее состояние именно тестового задания — оно может оставаться `pending`, `processing` или `retry`.

## Разделение каналов

Категории `diagnostics.email`, `diagnostics.browser`, `diagnostics.telegram`, `diagnostics.max`, `diagnostics.webhook` и `diagnostics.sms` остаются независимыми. Для браузерного Push одному событию могут соответствовать несколько заданий, по одному на устройство. Синхронный тест обрабатывает только одно выбранное задание; остальные обработает обычный фоновый процесс.

## Проверки

`php tests/integration/notification_targeted_delivery_contract.php` подтверждает, что адресный тест не затрагивает соседние задания, а обычный проход продолжает работать. Изменение не подтверждает доставку внешним сервисом до фактической проверки на установленной системе.
