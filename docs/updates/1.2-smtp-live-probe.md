# Notes 1.2 — пробная отправка SMTP

## Назначение

Для задачи #429 добавлена отдельная команда, которая действительно обращается к настроенному SMTP-серверу. Она не заменяет проверку планировщика, очереди, подписок и доставки события через `NotificationService`.

Запускать **только в консоли сервера Notes** доверенным администратором. Не размещать команду в публичном HTTP-маршруте.

## Порядок работы

1. Сначала выполните `php bin/notifications_diagnose.php --json` и убедитесь, что глобальная SMTP-конфигурация активна.
2. Уточните внутренние числовые идентификаторы конфигурации и получателя в защищённой панели или административной консоли. Для этого теста допускается только активная глобальная конфигурация SMTP; пользователь должен быть активным, с корректным адресом E-mail.
3. Проверьте входные данные без отправки:

```bash
php bin/notifications_smtp_probe.php --config-id=1 --user-id=1 --json
```

4. **Только после осознанного подтверждения** выполните отправку:

```bash
php bin/notifications_smtp_probe.php --config-id=1 --user-id=1 --send --json
```

Числа `1` приведены для примера. Используйте действительные идентификаторы своей установки, не подбирая их в публичных запросах.

## Значение результата

- `ready`: конфигурация и получатель найдены; сетевое соединение не проверялось.
- `accepted_by_smtp`: SMTP-сервер принял сообщение; фактическая доставка в почтовый ящик **не гарантирована**.
- `smtp_failed`: безопасный код причины сбоя (`smtp_connect_failed`, `smtp_tls_failed`, `smtp_auth_rejected` и т. п.).
- `smtp_probe_preflight_failed`: проблема подготовки, отсутствующая миграция или неподходящие идентификаторы.

Пароли, ссылки на секреты, SMTP-хост, адреса и тела сообщений в вывод не включаются. Для работы используется штатный SMTP-адаптер и разрешение секрета из окружения. Тестовое письмо не создаёт событие в центре и задание очереди, чтобы не вмешиваться в пользовательские подписки. Команда не измеряет статус планировщика и не должна выполняться периодически.

## Условия закрытия #429

После успешной пробы отдельно проверяются публикация настоящего события, создание и обработка задания, повторы ошибок, получение письма адресатом и работоспособность cron/HTTP-подхвата на Windows/OSPanel и Linux. Без этих проверок неисправность #429 остаётся открытой.
