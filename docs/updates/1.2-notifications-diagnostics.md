# Диагностика внешних уведомлений Notes 1.2

## Проверка без изменения данных

На установленном сайте, из каталога приложения, выполните:

```bash
php bin/notifications_diagnose.php
php bin/notifications_diagnose.php --json
```

Команда использует штатное подключение `Core\\DatabaseManager`, читает только агрегированные показатели событий, уведомлений, активных SMTP-конфигураций, подписок, состояний заданий доставки и коды последних попыток за 24 часа. Не выводятся пароль SMTP, ссылки на секреты, адреса получателей, содержимое писем и настройки транспорта.

## Как интерпретировать результат

- Нет активной конфигурации SMTP: необходимо настроить канал, пароль в переменной окружения и включить его.
- Нет активных почтовых подписок: внешние письма для соответствующих событий не будут запланированы.
- Есть уведомления, но нет заданий SMTP: следует проверять категорию, подписку и активную конфигурацию на момент публикации. Существующие события не получают новые задания автоматически после включения канала.
- Есть `pending` или `retry`: проверить запуск `php bin/notifications_worker.php --json` по планировщику. **Команда worker изменяет очередь и реально отправляет письма**, поэтому её запуск должен быть осознанным.
- Есть `failed`: изучить коды попыток доставки и настройки канала. В выводе диагностики присутствуют только коды, без чувствительных текстов ошибок.
- `smtp_sent` означает принятие сообщения SMTP-сервером, но не гарантирует получение письма адресатом.

Поле `last_http_fallback_utc` отражает последнюю запись резервного прохода через HTTP, **не подтверждая** наличие исправно работающего cron. Поля `scheduler_running` и `smtp_delivery_received` намеренно равны `not_verified`.

## Ограничения

Диагностика не создаёт тестовых событий и не отправляет писем. Для закрытия задачи #429 нужны проверка живой установки, диагностика фактического планировщика, тестовое письмо и подтверждение получения пользователем на Windows/OSPanel и Linux. Нельзя объявлять доставку восстановленной только по результатам этой команды.

## Сводка по всем каналам в 1.2

В JSON-ответ добавлен раздел `channels` со всеми шестью каналами: `email`, `browser`, `telegram`, `max`, `webhook`, `sms`. Для каждого показаны количество активных и выключенных конфигураций, активных подписок, задания по состояниям и суммарные исходы попыток за последние 24 часа.

Эти значения **не раскрывают** чаты, номера телефонов, адреса получателей, секреты и содержимое уведомлений. Наличие конфигурации и записи `sent` не означает, что сообщение было реально показано пользователю: поле `actual_delivery_verified` остаётся `false` до независимой проверки доставки на устройстве.

Личная настройка Telegram, MAX, SMS и Push никогда не должна подменяться общим адресатом. Отсутствие у пользователя личного адресата означает отсутствие задания для этого канала, а не отправку в системный чат. Для реальной проверки отдельно используются защищённые административные сценарии и тестовые устройства.
