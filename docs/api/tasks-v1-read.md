# Tasks API v1 — первый рабочий маршрут чтения

`GET /api/v1/tasks?limit=30&cursor=...` возвращает личные задачи текущего пользователя в формате JSON. На этом этапе используется **существующая авторизованная браузерная сессия** и право `tasks.use`. Это **не внешний сервисный API по токену** — выдача и отзыв сервисных токенов будут отдельным этапом #423.

Ответ содержит `api_version`, `items`, `has_more`, `next_cursor`, `limit`. Порядок фиксирован: дата создания по убыванию, затем внутренний идентификатор по убыванию. Внутренний ID из ответа удалён. Архивные задачи остаются видимыми, удалённые — нет. Лимит от 1 до 100, по умолчанию 30. Повреждённый или принадлежащий другому пользователю курсор отвергается с HTTP 422.

Курсор непрозрачен для клиента, но **не подписан**: это указатель позиции, не разрешение доступа. Все запросы в БД независимо фильтруются по текущему пользователю. При вставке новых задач между страницами ранние страницы остаются устойчивыми; редактирование времени создания не поддерживается. Защитой маршрута служат прежние middleware авторизации и RBAC.

На следующие итерации остаются сервисные токены с ограниченными областями действия, проверка отзыва токена, журнал внешних запросов, регулирование частоты, изменяющие команды API и HTTP-проверки; не считать #423 закрытой.

## Ключи для внешнего клиента (этап 1.2)

Веб-интерфейс с действующей сессией и правом `tasks.use` может управлять личными ключами без отдельной системы прав:

- `GET /tasks/api-tokens` — список своих ключей без секретов.
- `POST /tasks/api-tokens` — выдать ключ, поля `name` и `days` (1–90), обязательно штатное подтверждение CSRF.
- `POST /tasks/api-tokens/{id}/revoke` — немедленно отозвать собственный ключ, с CSRF.

При создании возвращается строка `ntk1_...` **ровно один раз**. В БД остаётся только SHA-256. Храните её в защищённом хранилище клиента; не передавайте в адресной строке, журнале и сторонней аналитике.

`GET /api/v1/tasks` принимает `Authorization: Bearer ntk1_...` либо действующую сессию. При наличии заголовка Authorization неправильный ключ никогда не подменяется сессией. Ключ разрешает **только** `tasks.read`: проверяются и срок действия, и отзыв, и действующие права `tasks.use` владельца. Ключ не даёт доступа к чужим задачам. Внешние клиенты должны пользоваться исключительно HTTPS: схема не обеспечивает конфиденциальность ключа по HTTP.

Выдача ключей сейчас доступна через JSON-маршруты, без отдельного экранного управления. Нет прав записи по сервисным ключам, самостоятельной регистрации приложений или обещания полноценного внешнего API. Следующие задачи: управление ключами в интерфейсе, журнал обращения, ограничения частоты и изменяющие версионные команды.

## Изменяющие запросы (1.2)

Ключ может иметь `scope=tasks.read` или `scope=tasks.write`; ключ записи также разрешает чтение. Создание ключа выполняется через защищённый маршрут `POST /tasks/api-tokens` с полем `scope`. Область ключа после выпуска не расширяется.

Внешние команды принимают **только** `Authorization: Bearer ntk1_...` с областью `tasks.write` и `Content-Type: application/json`, без сессионной авторизации: это исключает обход CSRF. Клиент должен использовать HTTPS.

- `POST /api/v1/tasks`: JSON `{"command_id":"my-command-0001","title":"Задача","priority":"medium"}`. Необязательны `description` и `due_date` в виде `YYYY-MM-DD HH:MM:SS`.
- `PATCH /api/v1/tasks/{uid}`: JSON `{"command_id":"my-command-0002","expected_version":1,"title":"Исправлено"}`. В первой итерации можно менять `title`, `description`, `priority`, `due_date`.

Обработчики используют общий `MutationCommandStore` и `TaskVersionMutationService`. Повтор того же `command_id` и тела команды возвращает сохранённый ответ; изменённое тело отвергается, устаревшая `expected_version` даёт `409` без записи. Ошибки авторизации: `401`, прав: `403`, входных данных: `422`, отсутствие объекта: `404`. Создание возвращает `201`, повтор создания — `200`.

**Незавершённый объём #423:** управление ключами в интерфейсе, ограничение частоты, журнал обращений, действия со статусом и общими досками, браузерная приёмка и нагрузка. Внешние команды нельзя считать полностью принятыми до этих проверок.

## Экран управления ключами

Из раздела **Мои задачи → Ключи API** открывается `/tasks/api-tokens/manage`. В интерфейсе можно создать ключ с названием, правами `tasks.read`/`tasks.write` и сроком действия 7, 30 или 90 дней. Сразу после выпуска секрет отображается один раз; кнопка копирования использует буфер обмена, а «Скрыть секрет» очищает поле. При уходе со страницы секрет удаляется из отображаемого поля.

Действующие подключения показаны отдельно от отозванных и просроченных. Для каждого ключа доступны разрешения, срок действия и отзыв. Список загружается и обновляется через AJAX, ответ добавляется через `textContent`, а не через HTML. Данные управления не кешируются. При завершении сессии интерфейс показывает ошибку запроса без повторной отправки секрета.

**Обратите внимание:** веб-страница позволяет управлять ключами, но это не заменяет HTTPS, ограничения частоты, журнал обращений и дополнительную браузерную проверку. Секрет из буфера обмена следует удалить после переноса в защищённое хранилище клиента. Продолжаем #423.

## Ограничение частоты и история запросов

Для каждого сервисного ключа действует отдельная атомарная минутная квота: **120 запросов чтения** или **30 изменяющих запросов** за минутное окно. Счётчик хранится в общей БД установки и корректно учитывает конкурентные процессы PHP. При превышении возвращаются `429`, `Retry-After` и JSON `error=rate_limited`. Чтение из браузерной сессии не учитывается в квоте ключей; создание и изменение по внешнему API требуют ключа `tasks.write`.

Владелец может получить последние 50 записей своего журнала: `GET /tasks/api-tokens/history` (обычная авторизованная сессия и `tasks.use`). В журнал входят идентификатор ключа, понятное имя подключения, действие (`read`, `create`, `update`), код ответа и время. Секреты, заголовки Authorization, содержимое запросов и адреса пользователей не сохраняются. Журнал удаляется при удалении самого ключа или пользователя.

Ограничения этапа: текущая квота общая по ключу в рамках одной минуты (первый вид запроса не выделяет отдельный независимый бюджет); неограниченный перебор **неизвестных** ключей нужно ограничивать ещё на уровне веб-сервера. Для предотвращения бесконечного роста таблицы минутных счётчиков необходима периодическая очистка устаревших окон. Пользовательский экран истории обращений и нагрузочная проверка конкуренции — отдельные последующие задачи.

## История в интерфейсе и очистка

На странице **Мои задачи → Ключи API** под списком подключений расположен блок «История обращений». Показываются последние 50 событий по собственным ключам, с названием подключения, действием, временем и кодом ответа. Список загружается и обновляется через AJAX, вывод выполняется безопасным текстом. История не показывает секреты, IP-адреса и содержимое запросов.

Модуль Tasks использует уже действующее фоновое задание `retention_cleanup`. Счётчики минутных квот старше **48 часов** удаляются независимо от общего срока хранения задач, ограниченными пачками. История вызовов очищается по общему сроку хранения, переданному системной службой; при каждом проходе применяется тот же предел количества записей. В режиме предпросмотра отражается число подлежащих удалению записей. Новая самостоятельная служба и отдельный планировщик не требуются.

Для запуска автоматической очистки должен выполняться существующий планировщик платформенного задания хранения. Данный этап не заменяет защиту от подбора недействительных токенов на уровне веб-сервера и нагрузочное испытание конкурентных запросов.

## Общие доски и командные задачи (первый этап)

Маршруты принимают **только** действительный сервисный ключ. Доступ пользователя и его роль на доске проверяются при каждом запросе, независимо от разрешений ключа.

- `GET /api/v1/task-boards` — доступные доски с названием, ролью (`owner`, `manager`, `member`, `viewer`), числом участников и задач; нужен ключ `tasks.read` или `tasks.write`.
- `GET /api/v1/task-boards/{boardUid}/tasks?limit=30&after_id=0` — выдача задач только доступной доски. Максимум 100 записей, продолжение через `next_after_id`, внутренние идентификаторы элементов не отображаются; доступ `viewer` разрешает чтение.
- `PATCH /api/v1/task-board-items/{taskUid}` — атомарная команда изменения через `TaskBoardVersionMutationService`, требуется `tasks.write`, `command_id` и `expected_version`. Пример тела: `{"command_id":"board-change-0001","expected_version":1,"status":"in_progress"}`. Допустимы поля штатного сервиса (`title`, `description`, `status`, `priority`, `due_date`, `archived`, `assignee_ids`, `delete`) с проверками ролей и политики назначения.

Повтор идентичной команды возвращает сохранённый ответ, устаревшая версия — HTTP 409, запрещённое действие — 403, недоступный объект — 404. Сессионный доступ к изменяющим внешним маршрутам не используется. Запросы подчиняются общей минутной квоте ключа и учитываются в журнале.

**Ограничения:** создание командной задачи с идемпотентностью, внешнее управление составом доски и HTTP-интеграционное испытание полного контроллера остаются следующими задачами #423. Проверка подключения маршрутов не заменяет испытания всех ролей в настоящей БД.

## Создание задач на общей доске

`POST /api/v1/task-boards/{boardUid}/tasks` требует `Authorization: Bearer ntk1_...` с областью `tasks.write`, действующего права `tasks.use` и роли владельца, руководителя или участника доступной доски. Наблюдателям и посторонним запись запрещена. Пример тела: `{"command_id":"board-create-command-0001","title":"Подготовить отчёт","priority":"high"}`. Можно также передать `description` и `due_date` в формате `YYYY-MM-DD HH:MM:SS`. При создании статус — `pending`, версия — `1`.

Создание задачи, обновление времени доски и квитанция `MutationCommandStore` фиксируются **одной транзакцией** через `Core\DatabaseManager`. Повтор одинаковой команды получает сохранённый `task_uid` и HTTP 200 без дублирования; новая команда получает 201. Повтор с иным телом или тем же идентификатором для другой операции запрещён. При отзыве роли повтор прежней команды также запрещён — доступ перепроверяется каждый раз. Лимиты частоты и журналирование аналогичны другим маршрутам внешнего API.

Назначение исполнителей при создании пока не поддерживается. После создания можно применить `PATCH /api/v1/task-board-items/{taskUid}` с полем `assignee_ids` при наличии соответствующих прав роли. Самостоятельное изменение состава доски через API остаётся отдельным этапом #423.
