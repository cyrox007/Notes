# Tasks API v1 — первый рабочий маршрут чтения

`GET /api/v1/tasks?limit=30&cursor=...` возвращает личные задачи текущего пользователя в формате JSON. На этом этапе используется **существующая авторизованная браузерная сессия** и право `tasks.use`. Это **не внешний сервисный API по токену** — выдача и отзыв сервисных токенов будут отдельным этапом #423.

Ответ содержит `api_version`, `items`, `has_more`, `next_cursor`, `limit`. Порядок фиксирован: дата создания по убыванию, затем внутренний идентификатор по убыванию. Внутренний ID из ответа удалён. Архивные задачи остаются видимыми, удалённые — нет. Лимит от 1 до 100, по умолчанию 30. Повреждённый или принадлежащий другому пользователю курсор отвергается с HTTP 422.

Курсор непрозрачен для клиента, но **не подписан**: это указатель позиции, не разрешение доступа. Все запросы в БД независимо фильтруются по текущему пользователю. При вставке новых задач между страницами ранние страницы остаются устойчивыми; редактирование времени создания не поддерживается. Защитой маршрута служат прежние middleware авторизации и RBAC.

На следующие итерации остаются сервисные токены с ограниченными областями действия, проверка отзыва токена, журнал внешних запросов, регулирование частоты, изменяющие команды API и HTTP-проверки; не считать #423 закрытой.

## Ключи для внешнего клиента (этап 1.2)

Веб-интерфейс с действующей сессией и правом `tasks.use` может управлять личными ключами без отдельной системы прав:

- `GET /tasks/api-tokens` — список своих ключей без секретов.
- `POST /tasks/api-tokens` — выдать ключ, поля `name` и `days` (1–90), обязательно штатное подтверждение CSRF.
- `POST /tasks/api-tokens/{id}/revoke` — немедленно отозвать собственный ключ, с CSRF.

При создании возвращается строка `ntk1_...` **ровно один раз**. В БД остаётся только SHA-256. Храните её в защищённом хранилище клиента; не передавайте в адресной строке, журнале и сторонней аналитике.

`GET /api/v1/tasks` принимает `Authorization: Bearer ntk1_...` либо действующую сессию. При наличии заголовка Authorization неправильный ключ никогда не подменяется сессией. Ключ разрешает **только** `tasks.read`: проверяются и срок действия, и отзыв, и действующие права `tasks.use` владельца. Ключ не даёт доступа к чужим задачам. Внешние клиенты должны пользоваться исключительно HTTPS: схема не обеспечивает конфиденциальность ключа по HTTP.

Выдача ключей сейчас доступна через JSON-маршруты, без отдельного экранного управления. Нет прав записи по сервисным ключам, самостоятельной регистрации приложений или обещания полноценного внешнего API. Следующие задачи: управление ключами в интерфейсе, журнал обращения, ограничения частоты и изменяющие версионные команды.
