# Workspace Organizer — дорожная карта развития

Актуально: 16 октября 2026.

Этот документ содержит **только текущий план релизов и обязательные сквозные правила**. Подробные спецификации вынесены в `docs/plans/`, а идеи без назначенной версии — в [PRODUCT_BACKLOG.md](PRODUCT_BACKLOG.md). Исторические планы и аудиты перечислены в [ARCHIVE.md](ARCHIVE.md).

## Текущее состояние

Линия **1.0.x** находится в режиме сопровождения: опубликована `v1.0.16`, для неё выпущена накопительная серия repair-патчей вплоть до r15. Линия `1.1` подготовлена к выпуску `1.1.0` как GitHub Latest.

- все шесть встроенных production-модулей `admin`, `files`, `messenger`, `notes`, `profile`, `tasks` используют изолированный runtime;
- включение/отключение модулей, лицензирование по `workspace.*`, RBAC и межмодульные capability работают через общий платформенный контракт;
- новые 1.0.x выпускаются только для исправлений, эксплуатационных улучшений и небольших совместимых доработок существующей функциональности;
- следующий продуктовый релиз — **1.1.0**;
- после 1.1.0 открывается единый расширенный цикл **1.2**.

Фактический статус линии 1.0: [RELEASE_STATUS_1.0.md](RELEASE_STATUS_1.0.md).

## Порядок продуктового развития

Следующий основной модуль: день/неделя/месяц, agenda, события, повторы, напоминания, временные блоки и безопасные связи с Task/Note/File.

Одновременно в 1.1.0 вводится обязательный общий платформенный слой уведомлений. Calendar публикует семантические события, а общий сервис отвечает за хранение, центр уведомлений, подписки, дедупликацию, очередь и внешние каналы доставки. Каналы не должны встраиваться непосредственно в Calendar или другие модули.

### 1.2 — единый расширенный цикл

1.2 — крупный единый цикл, в который объединён ранее разнесённый объём 1.2 и 1.3. Работа разбивается только на внутренние этапы одной ветки/дорожной карты 1.2 и не переносится в отдельные продуктовые версии только ради уменьшения размера релиза.

Обязательные направления:

- переход минимального runtime на PHP 8.3.x с полной проверкой совместимости;
- укрепление install/update/rollback/recovery и регрессия обновлятора;
- модуль «Дефекты»;
- модуль «Наряды и допуски», ранее планировавшийся на 1.3;
- крупное развитие Tasks: личная и командная очередь, команды, исполнители, ответственность, ежедневные сводки, просрочка и быстрые действия;
- защита от конкурентной перезаписи через версии сущностей и явный конфликт;
- идемпотентность изменяющих команд;
- развитие NotificationService для живых сводок, интерактивных действий и Browser/PWA Push;
- устанавливаемая PWA-оболочка без обязательного полного offline-редактирования;
- версионированный API Tasks, курсорная пагинация и внешние адаптеры без дублирования бизнес-логики;
- фундамент настоящего E2EE Messenger: отдельные ключи устройств, версионированный криптографический конверт, клиентское шифрование вложений, отзыв устройств, ротация ключевого состояния и миграционный режим рядом с текущим серверным шифрованием;
- расширение существующих политик и metadata-only аудита;
- активные сеансы, удалённое завершение сеанса, основа доверенных устройств, дополнительное подтверждение чувствительных действий и ограниченный режим;
- обязательная нагрузочная приёмка на 1000 одновременно активных авторизованных пользователей;
- серверная пагинация, ограниченные ответы, устранение N+1 и контролируемые фоновые очереди;
- перевод большинства действий внутри уже открытой страницы на AJAX там, где это безопасно и не ухудшает восстановление после ошибки.

Визуальный стиль системы в 1.2 **не меняется**. Новые функции продолжают текущую систему интерфейса; улучшение удобства достигается сокращением лишних перезагрузок, понятными состояниями загрузки/ошибки и мобильной пригодностью, а не очередным редизайном.

### 1.5 — CodeExplorer / Workspace IDE — долгосрочный ориентир

Рабочее пространство для локальных файлов и Git с безопасным редактированием. Выполнение произвольного кода не входит в доверенное ядро автоматически.

На этом этапе платформенное управление может быть расширено до устанавливаемых пакетов и внешних соединений: подпись и целостность пакета, доверие к издателю, карантин, декларация внешних адресов в manifest, политика разрешённых соединений и отдельные ограничения сети/привилегий для CodeExplorer.

### 1.6 — Офисный контур — долгосрочный ориентир

Долгосрочная программа документов, таблиц и презентаций. До реализации обязателен отдельный исследовательский прототип и выбор технологического фундамента.

Вместе с офисным контуром рассматривается управляемое использование AI: реестр разрешённых провайдеров и моделей, возможность локального или выбранного организацией провайдера, глобальное отключение AI, политики по модулю/группе/роли/пользователю, проверка классификации данных до внешней передачи и экспорт выбранных событий аудита во внешние системы анализа.

## Сквозное развитие Tasks

Основной объём Tasks после 1.1 выполняется в едином цикле 1.2:

- «Мои задачи», «Сегодня», «Завтра», «Просрочено»;
- ручной порядок дневной очереди;
- общий слой команд/участников, исполнители и ответственность;
- персональная и командная очередь;
- подтверждение принятия задачи и история ответственности;
- ежедневные живые сводки и повторные напоминания о просрочке;
- действия прямо из уведомлений с защитой от повторного и устаревшего применения;
- Browser/PWA Push и устанавливаемая PWA-оболочка;
- версионированный API Tasks, webhook-события, сервисные токены и бот-адаптеры;
- версии сущностей, идемпотентность команд и курсорная пагинация;
- базовая операционная сводка без автоматической оценки эффективности сотрудников.

Постоянная секретная ссылка не заменяет штатную аутентификацию. Если сценарии быстрого доступа нужны, используются только ограниченные, сроковые и отзывные подписанные механизмы. Конкретные мессенджеры не встраиваются напрямую в `Tasks`: модуль публикует семантические события и действия через общие платформенные контракты.

Полный план: [plans/tasks-evolution.md](plans/tasks-evolution.md).

## Messenger и сквозное шифрование

Текущее шифрование Messenger через XChaCha20-Poly1305 с серверным `MSG_SECRET_KEY` считается защищённым серверным хранением, но не E2EE: сервер способен расшифровать содержимое.

В 1.2 обязательна отдельная E2EE-архитектура, в которой сервер хранит и пересылает шифротекст, но не обладает приватными ключами конечных устройств и не может расшифровать содержимое защищённого диалога.

Ключевые правила:

- отдельная криптографическая идентичность каждого устройства;
- безопасная регистрация и отзыв устройства;
- проверенный протокол класса Signal Protocol / Double Ratchet либо зрелая схема с сопоставимыми свойствами; собственный непроверенный криптопротокол не создаётся;
- рабочий E2EE-путь как минимум для личных диалогов в 1.2;
- клиентское шифрование вложений до загрузки;
- формальный контракт групп и смены состава;
- Push без открытого текста на серверной стороне;
- локальный поиск вместо серверной расшифровки E2EE-содержимого;
- явное различие `server_encrypted` и `e2ee` без ложной маркировки старой переписки;
- резервное копирование/перенос ключей без скрытого административного мастер-ключа чтения переписки.

Полный контракт: [plans/1.2-messenger-e2ee.md](plans/1.2-messenger-e2ee.md).

## Сквозной контур управления и защиты данных

В 1.2 объединяются два прежних этапа:

- развитие существующих ролевых политик и metadata-only аудита до сквозного платформенного контракта;
- управление активными сеансами;
- удалённое завершение сеанса;
- основа доверенных устройств;
- дополнительное подтверждение чувствительных операций;
- ограниченный режим для выбранной роли, пользователя или модуля.

Более поздние направления — классификация/контроль движения данных, доверие к устанавливаемым пакетам и управление AI — остаются отдельными долгосрочными этапами.

Workspace Organizer не превращается в собственный браузер, MDM или универсальный агент контроля операционной системы.

Полный контракт: [plans/platform-governance.md](plans/platform-governance.md).

## Сквозной контракт производительности

Нагрузочная приёмка назначена на **1.2.0** и не блокирует 1.1.0. До измерений ёмкость 1000 пользователей не объявляется подтверждённой.

Для стабильной 1.2.0 целевая ёмкость — не менее **1000 одновременно активных авторизованных пользователей** на документированной эталонной конфигурации.

Это означает реальную смесь чтения, записи, поиска, навигации, Messenger, файловых операций и типовых сценариев новых модулей, а не 1000 бездействующих вкладок.

Обязательны:

- серверная пагинация и ограниченные ответы;
- отсутствие N+1 и тяжёлых полных выборок в горячих путях;
- измеримые p50/p95/p99, частота ошибок, CPU/RAM, SQL и соединения БД;
- ограниченные пулы и backpressure;
- отдельный нагрузочный прогон и длительная проверка;
- доказательство, что realtime не исчерпывает обычные HTTP-ресурсы;
- при необходимости — несколько HTTP/WS-узлов с общим состоянием.

Полный контракт: [PERFORMANCE_1000_USERS.md](PERFORMANCE_1000_USERS.md).

## Политика PHP

Patch-релизы одной линии не повышают минимальную версию PHP.

Текущий план:

| Линия | Минимальный PHP |
|---|---:|
| 1.0.x | 8.1 |
| 1.1.x | 8.2 |
| 1.2.x | 8.3 |
| 1.3.x | 8.4 |
| 1.4.x | 8.5 |
| 1.5.x | 8.6 после выхода стабильной PHP 8.6 |

Для 1.2 проводится полный аудит возможностей и несовместимостей PHP 8.3.x. Новые возможности применяются выборочно: рефакторинг ради одного нового синтаксиса не является целью; изменение принимается, если уменьшает код, ужесточает контракт или снижает риск ошибок.

Перед повышением обязательны CI на новом минимуме, аудит устаревших API, проверка зависимостей, install/update/rollback, cron/worker/CLI и обновление системных требований.

Текущие требования 1.0: [SYSTEM_REQUIREMENTS.md](SYSTEM_REQUIREMENTS.md).

## Развитие платформы модулей

После базового lifecycle и entitlement 1.0.13 платформа должна постепенно получить:

- подписанные устанавливаемые пакеты;
- доверие к издателю и проверку целостности до исполнения;
- resolver зависимостей и версий;
- транзакционные module-owned migrations с rollback;
- install/enable/disable/quarantine/uninstall hooks;
- compatibility preflight;
- health-state модуля;
- first-party, private и позднее контролируемый third-party catalog;
- расширение entitlement для внешних пакетов и издателей.

В 1.2 новые first-party модули обязаны уже соблюдать изолированный runtime, schema ownership, manifest/capability и полный lifecycle установки/обновления/отключения. Более широкий каталог и доверие к сторонним издателям остаются последующими этапами.

## Идеи без назначенной версии

«Авто», универсальный межмодульный поиск, универсальные automation/workflows, полное двустороннее offline-редактирование и общий публичный API всей платформы находятся в [PRODUCT_BACKLOG.md](PRODUCT_BACKLOG.md).

Не относятся к backlog:

- общий NotificationService — обязательная часть 1.1.0;
- PWA-оболочка, Browser/PWA Push, API Tasks и действия из уведомлений — часть 1.2;
- фундамент настоящего E2EE Messenger, ключи устройств и защищённые вложения — часть 1.2;
- доверенные устройства и управление активными сеансами — часть 1.2.

## Архитектурные правила нового модуля

Новый модуль с первого коммита должен:

- находиться в `modules/<id>/`;
- использовать `runtime.mode = isolated`;
- объявлять dependencies, capabilities, storage и schema ownership;
- не переносить прикладные маршруты/сервисы в Core;
- не читать внутренние данные другого модуля напрямую;
- корректно отсутствовать из runtime composition;
- иметь install/update/disable/recovery проверки по уровню риска;
- соблюдать лицензионный и производительный контракты платформы;
- объявлять управляемые чувствительные операции через платформенный контракт, а не собственные несовместимые механизмы.

## Когда пункт считается завершённым

Нужны одновременно:

- реализация;
- миграция и recovery story;
- runtime/integration/browser проверки;
- упаковка;
- документация;
- критерий приёмки и сохранённое доказательство.

UI, manifest или незавершённая ветка сами по себе не означают готовую функцию.
