# Workspace Organizer — дорожная карта развития

Актуально: 26 сентября 2026.

Этот документ описывает текущее состояние и следующий продуктовый план. Исторические аудиты и старые PR сохраняются как свидетельства развития, но их закрытые пункты не являются текущими блокерами без нового воспроизводимого дефекта.

## Линия 1.0.x — текущее состояние

### Завершённая архитектурная стабилизация

- все шесть встроенных production-модулей `admin`, `files`, `messenger`, `notes`, `profile`, `tasks` используют `runtime.mode = isolated`;
- переходный рекурсивный загрузчик product-кода из `app/*` удалён из runtime-контракта;
- межмодульные интеграции используют capabilities/contracts вместо прямого доступа к внутренним файлам соседнего модуля;
- browser lifecycle для Notes, Tasks, Files, Profile и Admin, HTTPS/WSS E2E, WebSocket deployment и storage fault injection входят в релизную матрицу;
- последний опубликованный baseline — `v1.0.4`;
- старые дефекты File Manager lifecycle, перенос Profile/Admin/Messenger и пустые production trust roots закрыты и не должны возвращаться в работу без новой регрессии.

Историческая последовательность PR #136–#146 остаётся полезной для понимания миграции, но больше не является списком незавершённых задач.

### 1.0.5 — текущий релиз-кандидат линии 1.0.x

`1.0.5 (10005)` уже находится в `master`, но до создания тега `v1.0.5` остаётся релиз-кандидатом, а не опубликованным релизом.

Ключевая граница 1.0.5:

- `1.0.4 → 1.0.5` — последний переходный шаг через Admin → Updates;
- начиная с `1.0.5 → 1.0.6` установка сама обнаруживает совместимый подписанный stable-релиз и предлагает одношаговое обновление;
- при ошибке миграции или post-update healthcheck рабочий код и БД автоматически возвращаются к последней проверенной версии;
- следующий HTTP-запрос умеет продолжить незавершённое восстановление до запуска БД и прикладных модулей;
- публикация `v1.0.5` допускается только после exact-head CI, операторской приёмки OSPanel 5.2.2, проверки production trust roots и неизменяемого подписанного артефакта.

### 1.0.2 — финальная стабилизация перед 1.1

`1.0.2` — patch-релиз, сфокусированный на надёжности Messenger, signed updater и эксплуатационной готовности.

В состав входят:

- WebSocket как основной realtime-транспорт Messenger;
- аутентифицированный HTTP Long Poll как автоматический резервный транспорт с возвратом на WebSocket после восстановления;
- исправление границы Long Poll timeout без пропуска события;
- сохранение неподтверждённого черновика Messenger при HTTP 403/503, сетевом отказе и ошибке обработчика;
- явная CSRF-защита HTTP mutation fallback;
- exact upgrade drill `v1.0.1 -> 1.0.2` с принудительным отказом после переключения и проверкой автоматического отката кода и БД;
- Windows/PHP 8.1/8.3 compatibility checks и ручная приёмка OSPanel 5.2.2;
- единый обязательный набор release checks для `1.0` и `master`;
- production ZIP, manifest/signature и trust canaries как финальная операторская граница.

Финальная процедура и открытые human/operator gates ведутся в `docs/RELEASE_STATUS_1.0.md` и `docs/RELEASE_ACCEPTANCE.md`.

### 2FA/TOTP

2FA/TOTP входит в состав `1.0.2` как завершающая функция линии 1.0.x.

Контракт:

- стандартный TOTP по RFC 6238 с индивидуальным секретом каждого пользователя;
- персональное включение и отключение в профиле, когда общесистемная обязательность выключена;
- настройка в Admin: «По выбору пользователя» или «Обязательно для всех пользователей»;
- при обязательном режиме аккаунт без TOTP после проверки пароля проходит принудительную настройку до получения обычного доступа;
- при обязательном режиме пользователь не может самостоятельно отключить 2FA;
- отключение глобальной обязательности не удаляет персонально настроенные секреты;
- одноразовые резервные коды с хранением только их SHA-256-хешей;
- отдельное ограничение частоты попыток и журналирование событий безопасности;
- TOTP-секреты участвуют в безопасной возобновляемой ротации `UNIQUE_KEY` и rollback;
- clean install и upgrade с опубликованной 1.0.1 входят в релизную проверку;
- полный lifecycle входа и политики должен быть принят на точном объединённом RC.

Подробный контракт: `docs/TWO_FACTOR_AUTH.md`.

### Историческая граница 1.0

Старые записи о красном File Manager lifecycle, Draft Profile #146, legacy Admin/Messenger и существовании переходного recursive loader относятся к промежуточному состоянию сентября 2026 и больше не описывают текущий код.

## Политика повышения версии PHP

Начиная с линии 1.x минимальная поддерживаемая версия PHP повышается вместе с каждым новым минорным продуктовым релизом. Исправительные релизы внутри одной линии не меняют системный минимум.

| Линия Workspace Organizer | Минимальный PHP | Обязательный технический этап перед выпуском |
|---|---:|---|
| 1.0.x | 8.1 | Сохранение совместимости текущей стабильной линии |
| 1.1.x | 8.2 | Рефакторинг под PHP 8.2: защита чувствительных параметров, применение readonly-классов для неизменяемых объектов, устранение динамических свойств и несовместимостей |
| 1.2.x | 8.3 | Рефакторинг под PHP 8.3: проверяемые переопределения через `#[\Override]`, типизированные константы и другие оправданные улучшения контрактов |
| 1.3.x | 8.4 | Рефакторинг под PHP 8.4: `#[\Deprecated]`, асимметричная видимость, перехватчики свойств только там, где они упрощают модель, устранение устаревших nullable-контрактов |
| 1.4.x | 8.5 | Рефакторинг под PHP 8.5: `#[\NoDiscard]` для обязательных результатов, единый URI API для URL/origin/security-политик, удаление устаревших конструкций среды выполнения |
| 1.5.x | 8.6 | Следующий цикл рефакторинга после выхода стабильной PHP 8.6 |
| последующие 1.N.x | следующая стабильная ветка PHP | Та же схема: новый минорный релиз принимает следующую стабильную ветку PHP и использует её полезные возможности для упрощения и усиления кодовой базы |

Это правило означает не механическую замену синтаксиса, а обязательный технический аудит перед каждым новым минорным релизом. Используются только возможности новой версии PHP, которые уменьшают собственную инфраструктурную обвязку, усиливают типовые и защитные контракты, устраняют устаревшие API или делают код проще для сопровождения.

Для каждого повышения минимальной версии PHP до выпуска релиза обязательны:

- обновление ограничения PHP в `composer.json`, установщике, healthcheck, документации системных требований и метаданных релиза;
- обновление CI: новая минимальная версия становится обязательной проверкой среды выполнения, отдельно сохраняется прогон на актуальной стабильной версии PHP;
- полный поиск и устранение `E_DEPRECATED`, несовместимых сигнатур и удалённых API на принимаемой версии;
- отдельный рефакторинг кода с применением полезных возможностей новой версии PHP; косметическое массовое переписывание без измеримой пользы не является целью;
- проверка чистой установки, обновления с предыдущей стабильной линии, отката/восстановления и основных браузерных/интеграционных сценариев на новом минимальном PHP;
- предварительная проверка обновлятора должна до изменения файлов и БД остановить обновление с понятной ошибкой, если текущий PHP ниже минимального требования целевого релиза;
- примечания к выпуску должны явно сообщать о новом минимальном PHP как о системном требовании обновления.

Новая минимальная ветка PHP должна быть стабильной к моменту релиз-кандидата. Если следующая запланированная версия PHP ещё не выпущена как стабильная, соответствующий минорный релиз Workspace Organizer не должен объявлять предварительную версию PHP производственным требованием: выпуск либо ожидает стабильную PHP, либо политика для этого релиза отдельно пересматривается до начала RC.

## 1.1 — Календарь и ежедневник

Календарь и ежедневник становятся первым новым крупным продуктовым модулем после стабилизации линии 1.0.x. Это личное пространство планирования времени, а не переименование Tasks.

Целевой объём:

- представления день/неделя/месяц;
- agenda и планирование дня;
- события и повторяющиеся события;
- напоминания и уведомления;
- временные блоки;
- связь события с Task/Note/File через публичные module contracts;
- личные и при необходимости общие календари;
- корректная работа часовых поясов;
- import/export как последующая capability;
- собственные permissions/storage/schema/migrations и isolated package с первого дня.

Tasks и Календарь взаимодействуют, но остаются независимыми: Tasks управляет задачами и досками, Календарь — временем и календарным контекстом.

## Частный рабочий контур

После календаря в план добавляются два прикладных модуля для автоматизации личной рабочей деятельности: **«Дефекты»** и **«Наряды и допуски»**.

Оба модуля проектируются как полностью самостоятельные изолированные продукты внутри Workspace Organizer. Между ними не создаётся общей рабочей цепочки, общего жизненного цикла или обязательных ссылок. Каждый модуль должен устанавливаться, включаться, обновляться, отключаться и использоваться независимо от второго.

«Дефекты» отвечают только за собственный процесс: **регистрация → контроль → закрытие → отчётность**. Модуль не создаёт задания или наряды и не связывает карточку дефекта с Notes, Tasks, Files, Календарём либо другими прикладными модулями.

«Наряды и допуски» также работают автономно: собственные справочники, шаблоны, документы, номера, жизненный цикл, история и отчётные/печатные формы. Наличие модуля «Дефекты» не является условием создания или закрытия наряда.

Общими остаются только платформенные возможности Core, необходимые любому модулю: аутентификация, пользователи и роли, жизненный цикл модулей, базовые защитные механизмы и системное журналирование. Прикладные данные модулей друг другу не принадлежат и напрямую не используются.

Для модуля «Дефекты» пользовательская спецификация уже получена и зафиксирована ниже в разделе 1.2. Для «Нарядов и допусков» точный состав полей, ролей и переходов продолжает уточняться отдельно. Не следует превращать эти задачи ни в универсальный конструктор бизнес-процессов, ни в единую связанную отраслевую систему.

## 1.2 — Дефекты

Модуль предназначен для регистрации, учёта и сопровождения выявленных дефектов, фиксации выполненных работ и формирования выборок по параметрам пользователя. Пользовательская спецификация этого модуля зафиксирована и заменяет прежний предварительный перечень полей.

Модуль с первого этапа остаётся полностью автономным и изолированным: собственные схема БД, миграции, права, маршруты, браузерные проверки, справочники и отчётность. Перекрёстные связи с Files, Notes, Tasks, Календарём, заданиями, нарядами и другими прикладными модулями в его объём не входят.

### Справочники

Поля с известными значениями не должны заполняться произвольным текстом. Базовая иерархия:

`Участок/РЭС → Категория объекта → Объект`.

Отдельным справочником ведутся службы, ответственные за устранение дефекта.

Для справочников обязательны:

- выпадающие списки в рабочих формах;
- зависимость доступных объектов от выбранных Участка/РЭС и категории объекта там, где это следует из структуры данных;
- служебная страница управления справочниками, доступная только администратору;
- создание, изменение и удаление значений с защитой уже используемых записей от разрушения ссылочной целостности;
- импорт из текстового файла: одна строка файла соответствует одной записи справочника;
- предварительная проверка импортируемых строк, отчёт о добавленных/пропущенных/ошибочных значениях и отсутствие частично применённого импорта при критической ошибке;
- история административных изменений справочников.

Исходная пользовательская структура содержит, в частности:

- Нововоронежский РЭС: категории ПС 110 кВ, ПС 35 кВ, РП 10 кВ и соответствующие объекты;
- Каменский РЭС: категории ПС 110 кВ, ПС 35 кВ, РП 6 кВ и соответствующие объекты;
- службы: «Служба ЛЭП», «Служба подстанций», «Служба РЗА», «Служба СДТУ».

Конкретные записи являются начальными данными, а не захардкоженными значениями интерфейса.

### Регистрация дефекта

Форма регистрации строится в следующем порядке:

1. **Участок/РЭС** — обязательный выпадающий список из справочника.
2. **Категория объекта** — обязательный выпадающий список из справочника.
3. **Объект** — обязательный выпадающий список из справочника.
4. **Описание дефекта** — обязательное многострочное текстовое поле.
5. **Категория дефекта / приоритет восстановления** — обязательный список:
   - «Неотложный» — срок устранения 1 день;
   - «Первоочередной» — 7 дней;
   - «Важный» — 14 дней;
   - «Обычный» — 30 дней.
6. **Дата обнаружения дефекта** — обязательный выбор даты.
7. **Служба, ответственная за устранение** — обязательный множественный выбор из справочника; один дефект может одновременно относиться к нескольким службам.
8. **ФИО регистрирующего** — обязательное однострочное текстовое поле согласно исходной спецификации.

Форма содержит действия «Зарегистрировать дефект» и «Очистить форму». После успешной регистрации создаётся уникальная запись с уникальным системным ID.

Плановая дата устранения рассчитывается системой от даты регистрации/обнаружения и выбранной категории дефекта. Расчётный срок хранится явно и не должен каждый раз выводиться только из текущего названия категории, чтобы последующее изменение справочника не меняло исторические обязательства.

### Реестр дефектов

Основная страница показывает все незакрытые дефекты в табличном или адаптивном карточном представлении. Минимальный состав данных:

- ID дефекта;
- Участок/РЭС и объект;
- категория дефекта;
- дата регистрации/обнаружения;
- плановая дата устранения;
- описание;
- одна или несколько ответственных служб;
- назначенный ответственный сотрудник, если он указан;
- состояние записи.

Фильтры первого этапа:

- Участок/РЭС;
- объект;
- дата регистрации;
- плановая дата устранения;
- ответственная служба;
- состояние, включая отдельный режим «Дефект закрыт».

Фильтры должны быть компактными и пригодными для небольшого экрана; не требуется буквально повторять табличную раскладку исходного документа.

### Назначение исполнителя и ограниченное редактирование

Для обычного пользователя изменение открытого дефекта ограничено рабочими полями:

- список служб, ответственных за устранение;
- ФИО сотрудника, которому поручено устранение.

Если ответственный сотрудник ещё не назначен руководителем службы, поле/состояние ответственной службы должно иметь отдельный визуальный признак. В исходной спецификации для этого указан зелёный цвет; итоговая тема должна сохранить смысл признака и достаточную доступность в светлой и тёмной темах.

Администратор может редактировать любое поле карточки и удалять дефект. Удаление должно быть отдельным привилегированным действием с подтверждением и журналированием; для записей, уже связанных с выполненными работами или другими модулями, предпочтительно безопасное архивирование/логическое удаление вместо разрушения истории.

### Сроки и визуальные состояния

Реестр обязан явно показывать срочность:

- новый дефект в первые 24 часа после регистрации — отдельное предупреждающее выделение; в исходной спецификации жёлтое;
- до срока устранения осталось менее 10 суток — усиленное предупреждение;
- осталось менее 3 суток — более сильное предупреждение;
- срок устранения истёк — критическое состояние; в исходной спецификации красное.

Цвет не должен быть единственным носителем смысла: состояние дублируется текстом, значком или доступной меткой.

Исходная спецификация требует при просрочке блокировать изменение и закрытие дефекта и заменять действия значком замка/крестом. Это правило фиксируется как **открытый продуктовый вопрос до реализации**, потому что буквальная блокировка закрытия может сделать просроченный дефект невозможно завершить штатным способом. До решения правило не менять молча: необходимо отдельно выбрать один из вариантов — полный запрет, разрешение закрытия с обязательной причиной просрочки или специальное право руководителя/администратора.

### Закрытие дефекта

Действие «Закрыть» открывает отдельный экран. Исходные поля карточки показываются только для чтения. Дополнительно вводятся:

- **Выполненные работы** — обязательный текст;
- **Дата и время выполнения/закрытия** — обязательное значение;
- **Сотрудник, закрывший дефект** — обязательное значение;
- **Комментарий** — необязательный текст.

После подтверждения:

- дефект получает состояние «закрыт»;
- обычное редактирование полностью блокируется;
- закрытый дефект исчезает из списка по умолчанию;
- запись остаётся доступной через фильтр «Дефект закрыт»;
- сведения о выполненных работах и закрытии сохраняются как часть истории и не затирают исходные сведения дефекта.

### Права

Минимальная модель прав:

- обычные пользователи могут просматривать дефекты;
- обычным пользователям разрешено менять только ответственные службы, назначенного сотрудника и данные закрытия в рамках допустимого состояния;
- администратор может изменять все поля;
- только администратор может удалять/архивировать запись и управлять справочниками;
- все значимые изменения, закрытие, административное редактирование и удаление журналируются с пользователем и временем.

До реализации необходимо определить, требуется ли отдельная роль руководителя службы между обычным пользователем и администратором; исходная спецификация упоминает назначение сотрудника руководителем службы, но отдельную модель роли не задаёт.

### Отчётность

Отчётность является собственной функцией модуля «Дефекты», а не межмодульной интеграцией.

Минимальный первый объём должен позволять строить отчёты и сводки только по данным самого модуля:

- за выбранный период;
- по Участку/РЭС, категории и объекту;
- по категории/приоритету дефекта;
- по ответственной службе;
- по состоянию: открытые, закрытые и просроченные;
- с количеством записей и возможностью перейти от сводки к отфильтрованному реестру.

Точная форма печатных отчётов, набор итоговых показателей и необходимость экспорта в файл уточняются до реализации. Первый выпуск не должен зависеть от внешней системы аналитики или данных соседних модулей.

### Этапы реализации

**Этап 1 — модель данных и справочники**

- схема дефектов, ответственных служб и назначенных сотрудников;
- иерархия Участок/РЭС → Категория объекта → Объект;
- административное управление справочниками;
- безопасный построчный импорт текстовых файлов;
- права и журналирование.

**Этап 2 — регистрация**

- форма в согласованном порядке;
- зависимые списки;
- множественный выбор служб;
- расчёт плановой даты;
- уникальный ID;
- серверная валидация всех обязательных полей.

**Этап 3 — реестр**

- список открытых дефектов;
- фильтры;
- адаптация под ноутбук и мобильный экран;
- визуальные состояния 24 часа / <10 суток / <3 суток / просрочен;
- назначение исполнителя и ограниченное редактирование.

**Этап 4 — закрытие и история**

- отдельный экран закрытия;
- выполненные работы, дата/время, сотрудник, комментарий;
- неизменяемость закрытой записи для обычного пользователя;
- просмотр закрытых через фильтр;
- история изменений и административных действий.

**Этап 5 — отчётность**

- выбор периода и основных измерений отчёта;
- сводки по Участку/РЭС, объектам, категориям, службам и состояниям;
- отдельный учёт открытых, закрытых и просроченных дефектов;
- переход из сводки в соответствующий отфильтрованный реестр;
- согласованная печатная форма и/или экспорт, если они будут подтверждены отдельным требованием.

### Обязательные проверки перед выпуском

Модуль не считается готовым без автоматических и браузерных сценариев:

- чистая установка и миграции;
- импорт справочника с валидным файлом, дублями, пустыми строками и ошибочными данными;
- каскад выбора Участок/РЭС → Категория → Объект;
- регистрация каждого из четырёх приоритетов и проверка рассчитанного срока;
- несколько ответственных служб;
- фильтрация реестра по каждому обязательному фильтру и их комбинациям;
- переход временных состояний на границах 24 часов, 10 суток, 3 суток и просрочки;
- проверка прав обычного пользователя и администратора;
- назначение исполнителя;
- закрытие с обязательными полями и без необязательного комментария;
- невозможность обычного редактирования закрытого дефекта;
- просмотр закрытых записей отдельным фильтром;
- сохранность истории после изменения справочников;
- отключение модуля без ошибок Core;
- отчётность по периоду, объектам, категориям, службам и состояниям;
- отсутствие прикладных зависимостей, ссылок и прямого доступа к данным Files, Tasks, Notes, Календаря, «Нарядов и допусков» и других модулей.

### Критерий готовности

Первый завершённый выпуск модуля должен позволять в полностью локальной установке без внешнего интернета: администратору заполнить/импортировать справочники, пользователю зарегистрировать дефект, увидеть рассчитанный срок и срочность, отфильтровать реестр, назначить службы и сотрудника, зафиксировать выполненные работы и закрыть дефект, затем найти закрытую запись и сформировать отчёт по данным модуля. Все операции должны сохранять права, историю, автономность от соседних модулей и корректную работу на небольшом экране.

## 1.3 — Наряды и допуски

Модуль предназначен для автономной подготовки и ведения нарядов и допусков по согласованной пользователем логике. Он работает сам по себе и не зависит от модуля «Дефекты», Notes, Tasks, Files, Календаря или других прикладных модулей.

Предварительный объём:

- отдельная карточка наряда или допуска;
- несколько выпадающих списков из управляемых справочников;
- текстовые поля для рабочих сведений;
- плановые и фактические даты начала/окончания, а также другие значения, предусмотренные итоговой формой;
- объект эксплуатации, место проведения работ, организационная структура, подразделение-исполнитель, ответственный персонал, категория объекта и тип разрешительного документа там, где это требуется рабочим процессом;
- программа или краткое содержание работ;
- сохранение черновика и последующее изменение записи;
- список записей с поиском, фильтрами и сортировкой;
- история значимых изменений;
- собственные schema, migrations, permissions и browser lifecycle;
- отсутствие зависимости Core и соседних модулей от наличия этого пакета.

Точные роли участников, поля формы, статусы, проверки, переходы и правила завершения будут добавлены после отдельного описания рабочей логики. Печать, экспорт в установленную форму, электронные подписи и внешний обмен не считаются обещанной частью первого этапа без отдельного требования.

### Упрощённая целевая модель наряда

По дополнительному описанию рабочего процесса цель модуля — не повторить всю сложность существующей системы регистрации работ, а дать подробный, но быстрый сценарий подготовки документа с минимальным ручным вводом.

Базовые справочники первого этапа:

- **структура** — иерархия административных единиц;
- **персонал** — принадлежность человека к административной единице, права, группа по ЭБ и разрешения на выполнение работ;
- **объекты** — справочник объектов, к которым привязываются работы и разрешительные документы.

Основной сценарий создания наряда должен строиться по принципу «выбрать известное, вписать только изменяемое»:

- большая часть полей выбирается из справочников;
- вручную вводятся только сведения, которые нельзя разумно систематизировать;
- после заполнения система присваивает документу собственный номер;
- по данным карточки формируется PDF установленной формы;
- созданный документ остаётся связан с исходной структурой данных и не превращается только в отдельный PDF-файл.

### Шаблоны нарядов

Шаблоны считать одной из ключевых функций удобства, а не поздним необязательным дополнением.

Пользователь должен иметь возможность сохранить типовой набор значений для повторяющейся работы и при создании нового наряда:

1. выбрать шаблон;
2. получить заранее заполненные повторяющиеся поля;
3. изменить только переменную часть;
4. проверить итоговые значения;
5. создать новый документ с отдельным системным номером.

Использование шаблона не должно изменять сам шаблон без отдельного действия редактирования. Конкретный состав сохраняемых полей определяется при проектировании формы наряда.

### Минимальный жизненный цикл выполнения

Для наряда необходимо отдельно хранить значимые фактические отметки рабочего процесса, а не сводить всё к одному статусу:

- время начала подготовки рабочего места;
- время допуска бригады к работе;
- время фактического начала работ;
- время окончания работ;
- время полного закрытия наряда.

Если наряд действует несколько дней, должны поддерживаться оформляемые перерывы в работе с сохранением их истории. Точная форма возобновления, количество допустимых перерывов и правила изменения уже зафиксированных отметок определяются отдельной спецификацией.

Главный критерий удобства: типовой наряд должен создаваться преимущественно выбором значений из справочников и шаблона, без повторного ручного ввода одной и той же информации.

### Принципы интерфейса и рабочего процесса

Интерфейс должен следовать фактической последовательности оформления работы, а не структуре таблиц или внутренним ограничениям реализации. Не допускается сценарий, в котором пользователь вводит часть данных на одной вкладке, затем для продолжения обязан перейти в несколько других разделов, установить служебные признаки и вернуться назад.

Целевой принцип:

- один последовательный сценарий от выбора шаблона до готового документа;
- поля показываются в порядке, в котором они реально нужны при оформлении;
- зависимые поля и действия появляются по мере необходимости;
- уже выбранные данные не требуется повторно вводить или подтверждать в другом месте;
- типовой документ должен оформляться с минимальным числом переходов между экранами;
- продвинутые и редко используемые параметры не должны мешать основному сценарию;
- точный порядок страниц, полей, вкладок и действий фиксируется по отдельному пользовательскому описанию реального процесса до реализации.

При проектировании приоритет имеет модель работы конечного пользователя, который фактически оформляет наряды, а не попытка воспроизвести существующую систему или её внутреннюю терминологию без проверки необходимости.

### Автономность модуля

Все основные функции «Нарядов и допусков» должны полностью работать внутри локальной установки без доступа к внешнему интернету и без других прикладных модулей:

- собственные справочники, шаблоны и поиск;
- создание, изменение и закрытие документов;
- фиксация этапов и перерывов;
- присвоение системных номеров;
- формирование итогового PDF;
- просмотр собственной истории изменений.

Модуль не должен требовать существования дефекта, задания из другого модуля, задачи, заметки, файла или календарного события. Если в будущем появится отдельное требование на внешний обмен, оно проектируется как дополнительная необязательная интеграция и не меняет автономный базовый жизненный цикл.

Потеря внешнего интернет-доступа не должна блокировать оформление или закрытие наряда в локальной сети.

Итоговый PDF формируется средствами самой системы или её локального поставляемого компонента и не должен зависеть от наличия Microsoft Office, R7-Офис или другого пользовательского офисного пакета на рабочем месте. Если позднее появится экспорт в редактируемые офисные форматы, он получает отдельные тесты совместимости.

### Производительность и работа в часы пик

В пользовательском референсе существующая система существенно деградирует при массовом утреннем оформлении работ и временами перестаёт реагировать на действия. Для Workspace Organizer это считается отдельным классом недопустимого дефекта.

До выпуска модуля обязательны:

- нагрузочный сценарий одновременного создания, открытия, поиска и изменения нарядов;
- отдельная проверка наиболее тяжёлых справочников, фильтров и генерации документов;
- отсутствие глобальных блокировок, из-за которых один тяжёлый запрос останавливает работу остальных пользователей;
- измеримые критерии времени ответа для основных пользовательских действий; конкретные пределы и расчётная одновременная нагрузка фиксируются перед реализацией после уточнения реального количества пользователей;
- диагностика медленных запросов и операций без необходимости воспроизводить проблему только в рабочее утреннее окно;
- сохранение введённых данных и понятное восстановление после временной ошибки, а не зависший интерфейс или потеря формы.

Производительность считается частью функциональной приёмки модуля, а не отдельной необязательной оптимизацией после выпуска.

### UX-выводы из рабочего референса

Референс с журналами разрешительных документов и заданий использовать прежде всего как источник структуры данных и сценариев поиска, а не как шаблон интерфейса. Для Workspace Organizer предпочтительны:

- единый журнал с быстрым поиском и несколькими основными фильтрами;
- дополнительные фильтры в компактной раскрываемой панели, чтобы они не занимали значительную часть экрана;
- сохранённые наборы фильтров для повторяющихся рабочих сценариев;
- видимые статус, объект, исполнитель и плановые/фактические сроки непосредственно в строке списка;
- адаптация таблиц и карточек под небольшой ноутбук и мобильный экран без потери основного содержимого;
- отсутствие длительных пустых состояний при загрузке: показывать структуру списка, состояние загрузки и понятную ошибку вместо исчезновения контента.

Визуальное копирование показанной системы не является целью.

## Перспективный модуль — «Авто» / бортовой журнал

Отдельное перспективное направление — личный бортовой журнал для автомобилистов, которые сейчас вручную ведут записи о пробеге, заправках, расходе топлива, обслуживании и ремонтах.

Версия реализации пока не определена. Модуль не входит в релизный объём 1.0.2 и не должен влиять на текущий frozen RC.

Предварительный объём:

- поддержка нескольких автомобилей в одной установке;
- карточка автомобиля с основными данными и текущим пробегом;
- журнал показаний одометра;
- журнал заправок: дата, пробег, объём топлива, цена, сумма, АЗС и признак полного бака;
- автоматический расчёт расхода топлива, включая корректный расчёт по циклам «до полного»;
- история среднего расхода и стоимости топлива;
- обслуживание по пробегу и/или календарному интервалу;
- журнал ремонтов с неисправностью, выполненными работами, запчастями, стоимостью и пробегом;
- общая история расходов с разделением как минимум на топливо, обслуживание, ремонт и прочие расходы;
- базовая статистика: расход, затраты по периодам, стоимость километра и динамика пробега;
- в перспективе — напоминания о приближающемся обслуживании через общий механизм системных уведомлений;
- собственные schema, migrations, permissions и browser lifecycle с первого этапа;
- возможность полностью отключить или удалить модуль без нарушения работы Core и соседних модулей.

До реализации отдельно определить:

- окончательный состав карточки автомобиля;
- правила расчёта расхода при неполных заправках и пропусках записей;
- единицы измерения и локализацию;
- правила корректировки ошибочно введённого пробега;
- состав статистики и графиков;
- политику хранения фотографий чеков, заказ-нарядов и других вложений;
- нужны ли в первом этапе шины, документы, страховки, сезонные работы и прочие автомобильные сущности.

Импорт телеметрии, OBD-интеграция и автоматическое получение данных от автомобиля не входят в исходный объём. Первая цель — удобная цифровая замена ручному блокноту или таблице.

## Общий импорт справочников из текстовых файлов

Для модулей «Дефекты» и «Наряды и допуски» нужен общий технический механизм загрузки крупных справочников, чтобы сотни значений не приходилось вводить вручную.

Минимальный контракт первого этапа:

- входной файл — обычный текстовый файл UTF-8;
- одно значение на одной строке;
- поддержка окончаний строк Windows `CRLF` и Unix `LF`, а также UTF-8 BOM;
- обрезка пробелов и пропуск пустых строк;
- предварительный просмотр до записи: выбранный справочник, количество строк, новых значений, дубликатов и ошибок;
- явное подтверждение импорта;
- транзакционная запись: частичный импорт при ошибке не допускается;
- повторная загрузка того же файла не создаёт дубликаты;
- нормализация и уникальность определяются отдельно для каждого типа справочника;
- существующие значения не перезаписываются молча;
- журнал результата импорта без сохранения лишней копии исходного файла;
- доступ к импорту ограничен владельцем или явно разрешённой ролью модуля;
- импорт больших списков проверяется отдельным integration-тестом.

Если одинаковый справочник действительно нужен нескольким модулям, он предоставляется отдельной capability с явным владельцем данных. Создавать общую таблицу, которую разные модули меняют напрямую, нельзя.

CSV, Excel, автоматическое распознавание столбцов, слияние конфликтующих справочников и синхронизация с внешними системами относятся к возможному следующему этапу, а не к исходному TXT-import.

## 1.4 — общее воспроизведение медиа

Исторический план включал мультимедиа-плеер. Актуальная модель — общее расширение платформы, которым пользуются Files, Notes, Messenger и будущие модули.

Целевой объём:

- единый viewer/player contract;
- audio/video из разрешённых ресурсов разных модулей;
- встроенный preview без дублирования исходных файлов;
- range requests и streaming больших файлов;
- сохранение позиции воспроизведения там, где это уместно;
- metadata, duration, thumbnails/covers и безопасный media probing;
- playlists/queue как возможность host-модуля;
- интеграция через capability, без прямого чтения чужих таблиц;
- явное декларирование поддерживаемых codec/container capabilities.

Отдельный полноэкранный медиаплеер может появиться позже как оболочка над тем же API.

## 1.5 — CodeExplorer / Workspace IDE

Целевое направление — IDE-подобное рабочее пространство и постепенно «GitHub на минималках» внутри self-hosted Workspace Organizer.

Базовый объём:

- дерево проекта/репозитория;
- несколько открытых файлов;
- подсветка синтаксиса;
- поиск по файлам и содержимому;
- безопасное редактирование текстовых ресурсов;
- diff viewer;
- история файлов;
- клавиатурный сценарий работы редактора;
- ACL рабочего пространства/репозитория;
- явная политика autosave/manual save и восстановление черновиков.

Следующий слой Git:

- обнаружение/создание/import репозиториев;
- status и staged/unstaged changes;
- commits и история;
- branches/tags;
- diff между revisions;
- blame/history navigation;
- облегчённый merge/review workflow;
- локальные репозитории как основной сценарий;
- remote sync как отдельная capability;
- интеграция с Notes/Tasks через публичные contracts.

Произвольный shell, выполнение кода, build/test runner и remote Git credentials не входят автоматически в trusted core и требуют отдельного sandbox/permission/security design.

## 1.6 — Офисный контур: документы, таблицы и презентации

Перспективное направление — встроенный локально разворачиваемый офисный контур с долгосрочной целью функционального паритета с Microsoft Word, Excel и PowerPoint и сопоставимыми конкурентами в обычных и профессиональных сценариях. Цель — не визуально копировать конкретный продукт, а дать внутри Workspace Organizer полноценную работу с офисными файлами без обязательной передачи документов внешнему облачному сервису. Реализация может вводиться поэтапно, но конечная цель не ограничивается «облегчёнными» редакторами.

Это направление не должно строиться как три несвязанных редактора с разными несовместимыми основами. До начала продуктовой разработки необходимо выбрать общий фундамент для модели документов, рендеринга, команд, буфера обмена, отмены/повтора действий, совместной работы, импорта/экспорта и общих графических объектов.

### Целевой пользовательский объём

**Документы:**

- страничный и непрерывный режимы;
- стили абзацев и символов, шрифты, списки, табуляция, интервалы и выравнивание;
- секции, размеры и ориентация страниц, поля, колонтитулы и номера страниц;
- таблицы, изображения, фигуры, ссылки, подписи и обтекание;
- оглавление, сноски, закладки и внутренние ссылки;
- комментарии, рецензирование и история изменений;
- шаблоны и повторно используемые стили;
- поиск/замена и подключаемая проверка орфографии;
- печать и экспорт в PDF;
- совместное редактирование с курсорами/присутствием пользователей и восстановлением после разрыва соединения.

**Таблицы:**

- книги с несколькими листами;
- формулы и функции с совместимой моделью ссылок;
- форматирование чисел и дат, стили ячеек, объединение и границы;
- сортировка, фильтрация, закрепление областей и скрытие строк/столбцов;
- условное форматирование и проверка данных;
- именованные диапазоны и таблицы;
- диаграммы, изображения и графические объекты;
- сводные таблицы как обязательная цель зрелого этапа;
- импорт/экспорт CSV/TSV;
- производительность на больших листах и пересчёт без полной блокировки интерфейса;
- совместное редактирование с корректным разрешением конкурентных изменений.

**Презентации:**

- слайды, темы, шаблоны, образцы и макеты;
- текстовые блоки, изображения, фигуры, таблицы и диаграммы;
- направляющие, привязка, выравнивание, группировка и порядок слоёв;
- заметки докладчика;
- режим показа;
- переходы и базовые анимации после стабилизации основного редактирования;
- экспорт в PDF и совместимый PPTX;
- совместное редактирование и комментарии.

### Продвинутый паритет после базового редактора

После стабильного базового редактирования направление должно последовательно закрывать профессиональные сценарии, а не останавливаться на просмотре и простом форматировании:

- документы: формулы, многоколоночная вёрстка, перекрёстные ссылки, подписи, библиография/цитирование, формы и элементы управления содержимым, слияние данных и расширенное рецензирование;
- таблицы: расширенный набор функций, сводные таблицы и диаграммы, срезы, сценарии анализа, внешние источники данных через безопасные коннекторы, защита диапазонов/листов и сложные диаграммы;
- презентации: полноценные образцы и макеты, расширенные переходы и анимации, аудио/видео, режим докладчика, заметки, шаблоны и брендированные темы;
- общий слой: комментарии, история версий, совместное редактирование, права на документ и его части, доступность, печать, шаблоны, расширения и перенос настроек между устройствами.

Макросы, автоматизация и совместимость с VBA/ActiveX рассматриваются отдельным этапом с собственной моделью разрешений, песочницей и явным предупреждением о риске выполнения кода.

### Форматы и совместимость

Приоритетный контракт обмена:

- OOXML: DOCX, XLSX, PPTX — обязательная проверяемая совместимость;
- ODF: ODT, ODS, ODP — поддержка импорта/экспорта после выбора движка;
- PDF — просмотр и экспорт; полноценное PDF-редактирование не является автоматически частью офисного контура;
- CSV/TSV — для табличного редактора;
- legacy DOC/XLS/PPT — через отдельный контур преобразования, если выбранная база это безопасно поддерживает.

Высокая совместимость проверяется не только тем, что файл «открывается». Нужен набор реальных документов для полного цикла: открыть → изменить → сохранить → повторно открыть в Microsoft Office и LibreOffice и проверить формулы, стили, изображения, диаграммы, размеры страниц/слайдов и отсутствие непреднамеренной потери данных.

### Предлагаемая модульная граница

Офисный контур не переносится в Core. Предпочтительная композиция:

- общий пакет/модуль `office-foundation` — команды, модель общих объектов, буфер обмена, отмена/повтор, базовые средства рендеринга, адаптер совместного редактирования и контракты обмена;
- `office-documents` — текстовый редактор;
- `office-sheets` — табличный редактор и движок формул;
- `office-presentations` — редактор презентаций;
- отдельный модуль-адаптер допустим, если будет выбран внешний локально разворачиваемый офисный сервер вместо встраивания движка.

Каждый редактор должен оставаться отключаемым. Наличие Documents не должно быть обязательным условием работы Sheets или Presentations, кроме явно объявленной зависимости от общего `office-foundation`.

Files остаётся владельцем пользовательского файлового пространства. Офисные редакторы получают файл через публичную capability, не читают таблицы/каталоги Files напрямую и возвращают новую версию через тот же контракт. Совместное редактирование, история версий и временное состояние редактора должны иметь отдельного явного владельца данных.

### Обязательный исследовательский этап до выбора движка

Перед реализацией создать отдельный исследовательский прототип и сравнить как минимум три стратегии:

1. **Интеграция готового локально разворачиваемого офисного сервера** — ONLYOFFICE или Collabora через модуль-адаптер.
2. **Встраиваемый SDK/движок** — в первую очередь проверить реально открытую часть Univer и её лицензионные/функциональные границы.
3. **Собственная композиция** — только если первые два пути не дают нужного контроля: отдельные открытые компоненты для форматированного текста, табличной модели/формул, совместной работы и импорта/экспорта OOXML.

Для каждой стратегии сравнить:

- качество полного цикла DOCX/XLSX/PPTX;
- скорость открытия и редактирования больших файлов;
- мобильную работу;
- совместное редактирование и восстановление после повторного подключения;
- возможность полностью локального развёртывания без обязательного облака поставщика;
- требования к RAM/CPU и отдельным сервисам;
- сценарий развёртывания на Windows/OSPanel и Linux;
- сложность резервного копирования, обновления и отката;
- интеграцию с Workspace RBAC, Files и жизненным циклом модулей;
- лицензионные последствия для исходников, бинарных сборок, SaaS/self-hosted и коммерческого распространения;
- возможность обновлять выбранный внешний проект без постоянного тяжёлого форка.

Результатом исследовательского прототипа должно быть отдельное архитектурное решение с зафиксированной версией исходного проекта, лицензией, прототипом и набором файлов совместимости. До этого не создавать собственный формат документов и не обещать точную внутреннюю реализацию.

### Критерий зрелого результата

Направление считается реализованным только когда пользователь может из Files создать или открыть DOCX/XLSX/PPTX, полноценно отредактировать документ в браузере, безопасно сохранить новую версию, совместно работать согласно ACL и получить файл, который без существенной потери структуры и содержимого повторно открывается в актуальных Microsoft Office и LibreOffice.

## Развитие модульной платформы после 1.0

Платформа развивается в сторону безопасно распространяемых пакетов:

- подписанные module packages и publisher trust metadata;
- проверка integrity до исполнения кода;
- resolver зависимостей и версий;
- module-owned migrations с транзакционным upgrade/rollback;
- install/enable/disable/quarantine/uninstall hooks;
- центральный entitlement service;
- compatibility preflight перед активацией;
- health state каждого модуля;
- curated first-party catalog, затем контролируемая third-party distribution;
- private packages и private catalog для установочно-специфичных модулей;
- общий manifest/dependency resolver для builder и installer/updater.

Загруженный module code не исполняется до проверки подписи, integrity, core compatibility и зависимостей.

## Перспективное направление — системные уведомления и доверенные устройства

Инициатива зафиксирована отдельно в GitHub issue #233. Версия реализации пока не определена; это не релизный блокер и не часть frozen 1.0.2.

Цель — единый системный механизм, через который владелец установки или главный администратор сможет получать значимые события Workspace Organizer без обязательной привязки к электронной почте.

Базовое направление:

- единый сервис системных событий и уведомлений;
- постоянное хранилище уведомлений в БД;
- встроенный центр уведомлений в интерфейсе со счётчиком непрочитанных;
- категории, уровни важности и настройка подписок;
- дедупликация повторяющихся событий;
- первым системным сценарием считать появление доверенно проверенного обновления;
- позднее подключать ошибки обновления и rollback, healthcheck, backup/recovery, события безопасности, состояние realtime-транспорта и события модулей;
- источник события не должен знать конкретный способ доставки.

Возможные способы доставки, решение по которым пока не принято:

- встроенный центр Workspace;
- Browser Push / PWA Push;
- нативное приложение-компаньон для Android/iOS;
- Telegram как необязательная внешняя интеграция;
- подписанный webhook для собственных внешних систем.

- локальный SMS-шлюз через GSM/LTE-модем или отдельное доверенное устройство как необязательный аварийный канал.

### Перспективный SMS-канал через локальный GSM/LTE-шлюз

SMS имеет смысл рассматривать не как часть ядра и не как замену встроенному центру уведомлений, а как дополнительный канал для ограниченного набора критических событий. Его основная ценность — возможность доставить короткое предупреждение владельцу установки без зависимости от электронной почты, PWA, Telegram или внешнего облачного API.

Предпочтительная архитектура:

- `NotificationService` формирует нормализованное событие и очередь доставки, не работая напрямую с модемом;
- отдельный адаптер `sms-gateway` получает только разрешённые для SMS события и передаёт их локальному шлюзу;
- шлюз может работать на Linux, Windows или отдельном доверенном устройстве с GSM/LTE-модемом; для действительно аварийного канала предпочтительно физически отделить его от основного сервера, чтобы отказ питания или ОС Workspace не отключал одновременно и SMS;
- первая реализация — только исходящие уведомления; входящие SMS-команды и USSD не входят в исходный объём и требуют отдельной модели доверия;
- номера получателей задаются явным разрешённым списком и подтверждаются владельцем установки;
- в SMS не передаются пароли, токены, резервные коды, ключи, полные журналы, содержимое пользовательских данных и другие чувствительные сведения; сообщение содержит только безопасное краткое описание, идентификатор события и при необходимости ссылку на Workspace без секретов;
- обязательны дедупликация, ограничение частоты, очередь, повторные попытки с пределом, фиксация статуса доставки и защита от SMS-шторма при повторяющемся дефекте;
- интерфейс между Workspace и внешним шлюзом должен быть аутентифицированным и защищённым; текст сообщения и номер телефона не передаются через незащищённые GET-запросы;
- совместимость конкретного модема, SIM-карты и оператора проверяется отдельным испытанием, поскольку поддержка SMS зависит от оборудования и сети.

Перед реализацией провести отдельный прототип минимум для двух вариантов: поддерживаемый локальный SMS-daemon с очередью и драйверами модема и лёгкий шлюз-компаньон на отдельном устройстве. В качестве актуального открытого референса можно проверить Gammu SMSD или эквивалент: архитектурно он поддерживает очередь исходящих/входящих SMS, SQL/file backend, работу службой и несколько модемов. Конкретную зависимость и версию выбирать только после испытания на целевом оборудовании.

Переданный исторический пример Headwind Personal SMS Server использовать только как подтверждение жизнеспособности схемы «приложение → очередь → GSM-модем → SMS». Его PHP/COM-код, HTTP-интерфейс и бинарные компоненты не должны переноситься в Workspace Organizer: нужен новый изолированный адаптер с современными контрактами безопасности и без зависимости Core от Windows COM/DCOM.

Для нативного приложения пока рассматривается только концепция лёгкого административного компаньона: привязка конкретного устройства одноразовым кодом или QR, просмотр состояния установки и системных уведомлений, без хранения пароля администратора. Технология и состав функций не выбраны. Если направление будет принято, для знакомого .NET-стека отдельно рассмотреть .NET MAUI и .NET for Android.

Отдельно перед реализацией требуется решить, нужен ли специальный статус владельца установки/главного администратора, отличный от обычной роли admin, и какие события разрешено передавать во внешние каналы.

Для уведомления об обновлении доверенная цепочка должна сохраняться: событие создаётся только после проверки manifest, подписи, trusted key и версии. Недоверенный update feed не должен порождать доверенное системное уведомление.

## Возможные направления после запланированных модулей

После Календаря, Дефектов, Нарядов и допусков, общего медиа-слоя, CodeExplorer и офисного контура приоритет определяется реальным использованием. Кандидаты:

- универсальный межмодульный поиск/индекс;
- расширенный общий workspace/team layer;
- automation/workflows между событиями модулей;
- PWA/offline только для сценариев с определённой conflict/recovery semantics;
- публичный API/webhooks поверх тех же contracts, которые используют модули.

Эти пункты не являются обещанием конкретной версии без отдельного согласованного design/contract.

## Архитектурные правила будущих модулей

Новый модуль с первого коммита должен:

- жить под `modules/<id>/`;
- использовать `runtime.mode = isolated`;
- объявлять dependencies/capabilities/storage/schema ownership;
- не добавлять product routes/controllers/services в общий Core;
- не читать и не изменять внутренние данные другого модуля напрямую;
- иметь install/update/disable/recovery tests пропорционально риску;
- корректно отсутствовать из composition без fatal error ядра;
- не расширять trusted core только ради удобства реализации.

Межмодульное расширение не отменяет изоляцию: оно предоставляется через стабильный capability/service contract.

## Когда пункт roadmap считается завершённым

Пункт закрывается только когда согласованы:

- реализация;
- migration/recovery story;
- runtime/integration tests;
- packaging;
- документация;
- критерий приёмки и зафиксированное доказательство.

Наличие только UI, manifest или незавершённой ветки не считается готовой функцией.
