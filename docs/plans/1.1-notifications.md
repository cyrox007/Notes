# 1.1 — Общая система уведомлений

Статус: **обязательная часть 1.1.0**.

Система уведомлений — общий платформенный слой Workspace Organizer. Календарь использует её для напоминаний, но механизм не принадлежит модулю Calendar и должен принимать события от Core и любых модулей через стабильный контракт.

## Цели 1.1.0

В 1.1.0 должны появиться:

- единый `NotificationService` для семантических событий;
- хранение уведомлений и состояния доставки в БД;
- встроенный центр уведомлений в общей оболочке;
- счётчик непрочитанных;
- категории, уровень важности, время события и ссылка на связанный объект;
- отметка «прочитано» / «не прочитано» и массовая отметка;
- настройки подписок пользователя по категориям и каналам;
- дедупликация и идемпотентность;
- надёжная очередь внешней доставки с повторными попытками;
- безопасная обработка пропущенных напоминаний после простоя;
- единый контракт подключаемых каналов доставки.

Источник события не должен знать, каким каналом оно будет доставлено.

## Архитектурный контракт

Базовый поток:

```text
Core / модуль
     |
     v
семантическое событие
     |
     v
NotificationService
     |
     +-- запись уведомления и дедупликация
     +-- встроенный центр уведомлений
     +-- очередь внешней доставки
              |
              +-- E-mail
              +-- Browser / PWA Push
              +-- Telegram
              +-- подписанный Webhook
              +-- локальный SMS-шлюз
```

Примеры событий:

```text
calendar.reminder_due
calendar.event_changed
task.due_soon
update.available
update.installed
update.rollback
system.health_failed
system.storage_low
security.policy_changed
messenger.realtime_degraded
```

Имена событий и полезная нагрузка должны версионироваться. Модуль публикует только данные, необходимые для отображения и маршрутизации уведомления, без передачи секретов и лишнего содержимого объекта.

## Получатели

Система должна поддерживать два класса сценариев:

1. **Пользовательские уведомления** — календарь, задачи и другие события конкретного пользователя.
2. **Системные уведомления** — обновления, восстановление, healthcheck, хранилище, безопасность и эксплуатационные события для уполномоченных администраторов.

В 1.1.0 не требуется вводить отдельную сущность «владелец установки». Получатели системных событий определяются существующей моделью RBAC и явными настройками подписок. Отдельный installation owner можно добавить позднее без изменения контракта событий.

## Встроенный центр уведомлений

Обязательный интерфейс 1.1.0:

- значок уведомлений в общей оболочке;
- число непрочитанных;
- список последних уведомлений с пагинацией;
- время, категория, важность и источник;
- переход к связанному разделу или объекту;
- отметка одного или всех уведомлений прочитанными;
- фильтр по категории и состоянию;
- настройки подписок и каналов;
- понятное состояние ошибки внешней доставки без потери самого уведомления.

Уведомление в Workspace считается основным и не зависит от наличия внешнего канала.

## Каналы доставки

### E-mail

E-mail входит в общий контракт каналов 1.1.0.

Требования:

- SMTP как основной способ отправки;
- адрес, имя отправителя и параметры подключения задаются конфигурацией, а не кодом;
- секреты не попадают в журналы и БД открытым текстом без необходимости;
- HTML-письмо имеет текстовую альтернативу;
- повторная доставка выполняется очередью;
- ошибка почтового канала не удаляет уведомление из Workspace.

Прямой вызов `mail()` с жёстко заданными адресами не является целевым производственным механизмом.

### Browser / PWA Push

Канал проектируется как основной внешний браузерный способ, но встроенный центр уведомлений не зависит от него.

Если Web Push не может быть полностью принят в 1.1.0 без отдельного PWA-контракта, допускается выпустить 1.1.0 с готовым интерфейсом канала и отключённой доставкой, при условии что архитектура и схема БД не потребуют переделки общего сервиса.

### Telegram

Telegram — добровольный подключаемый канал:

- Bot API через HTTPS;
- токен хранится как секрет;
- канал можно полностью отключить;
- в сообщения не включаются чувствительные данные;
- пользователь явно связывает получателя с каналом.

Telegram не является обязательной зависимостью Workspace Organizer.

### Webhook

Webhook — универсальный подключаемый канал для внешних систем.

Обязательны:

- HTTPS;
- подпись запроса;
- ограниченный timeout;
- повторные попытки с backoff;
- защита от SSRF и запрет произвольных внутренних адресов без явной политики;
- минимальная безопасная полезная нагрузка;
- отдельный журнал доставки без секретов.

### Локальный SMS-шлюз

SMS рассматривается как необязательный аварийный канал.

Core не должен напрямую управлять модемом, COM-компонентом или конкретным GSM-драйвером. Поддерживается только отдельный аутентифицированный шлюз с исходящей очередью.

Для первого этапа:

- только исходящие уведомления;
- разрешённый список номеров;
- ограничение частоты;
- повторные попытки;
- короткий безопасный текст без секретов;
- состояние доставки;
- входящие SMS-команды и USSD не поддерживаются.

Старые решения с открытыми HTTP-параметрами, жёстко заданными учётными данными, устаревшими `mysql_*` API или прямым COM-доступом не переносятся в новый код.

## Очередь и доставка

Внешняя доставка должна быть отделена от HTTP-запроса, породившего событие.

Минимальная модель состояния:

```text
pending -> processing -> sent
                    \
                     -> retry -> processing
                     -> failed
```

Для каждой попытки хранятся:

- канал;
- получатель или безопасная ссылка на него;
- число попыток;
- следующее время попытки;
- код результата;
- время успешной доставки.

Повторная обработка одного и того же задания не должна создавать дубликаты.

## Дедупликация

Событие может передать устойчивый ключ идемпотентности, например:

```text
update.available:1.1.0
calendar.reminder:42:2026-10-10T08:00:00Z
system.storage_low:/private:2026-10-01T21
```

Повторное получение того же ключа не создаёт второе уведомление и вторую внешнюю доставку, если политика события явно не допускает повтор.

## Планировщик и shared hosting

1.1.0 не должен требовать постоянно работающего WebSocket или отдельного демона только ради уведомлений.

Обязательный базовый режим:

- обработчик очереди и напоминаний, запускаемый cron/планировщиком;
- безопасный ограниченный проход при обычном HTTP-запросе как резервный catch-up;
- блокировка параллельной обработки;
- bounded batch;
- восстановление после прерывания;
- корректная обработка пропущенных напоминаний после простоя.

На хостингах с доступным долгоживущим worker можно использовать его как ускоритель, но не как единственный способ доставки.

## Календарь

Calendar не отправляет E-mail, Telegram, Push или SMS самостоятельно.

Он публикует события вроде `calendar.reminder_due`, передаёт время, ссылку на событие, получателя и идемпотентный ключ. Выбор каналов и повторная доставка выполняются общим слоем уведомлений.

Для повторяющихся событий ключ должен различать конкретный экземпляр серии.

## Безопасность и приватность

- секреты каналов хранятся через общий механизм секретов и никогда не возвращаются обратно в UI полностью;
- уведомления не содержат приватный текст заметки, сообщения Messenger, содержимое файла или диагностические секреты;
- переход из уведомления повторно проходит обычную авторизацию и ACL;
- внешний канал получает минимальный текст и безопасный идентификатор/ссылку;
- все настройки каналов и критические изменения подписок аудируются;
- webhook, Telegram и SMS можно отключить глобально;
- удаление пользователя прекращает будущую доставку ему без удаления обязательного аудита системных событий.

## Минимальные таблицы

Точные имена утверждаются при реализации, но схема должна разделять:

- событие / уведомление;
- получателя и состояние прочтения;
- подписки;
- конфигурацию каналов без хранения открытых секретов;
- задания доставки;
- историю попыток.

Схема должна поддерживать очистку истории по политике retention без потери обязательного аудита.

## Проверки 1.1.0

До стабильного релиза обязательны:

- создание и чтение встроенного уведомления;
- дедупликация одного события;
- доставка минимум через встроенный канал и E-mail;
- отказ внешнего канала без потери уведомления;
- retry и окончательный `failed`;
- повторный запуск worker без дубликатов;
- напоминание Calendar по одиночному событию и экземпляру повторяющейся серии;
- пропущенное напоминание после простоя;
- запрет доставки отключённому/удалённому получателю;
- RBAC и ACL перехода по ссылке;
- защита секретов в журналах и UI;
- shared-hosting сценарий без постоянного worker;
- нагрузочная проверка очереди и центра уведомлений в рамках контракта 1000 активных пользователей.
