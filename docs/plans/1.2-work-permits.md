# 1.2 — Наряды и допуски

Статус: **обязательный модуль 1.2 в реализации**. Реализованы справочники, шаблоны, черновики, управление бригадой, выдача, первичный и дневные допуски, перерывы, продления, завершение и закрытие, журнал и локальная печатная PDF-копия. Реальная двухсессионная браузерная проверка на HTTP/MySQL пройдена. Местная календарная дата рабочих суток теперь вычисляется по снимку часового пояса организации, сохранённому при выдаче наряда; старые документы используют UTC. До выпуска остаются нормативная сверка PDF, полноценная приёмка на Android/iOS, нагрузочная приёмка. Режим ввода времени объекта реализован: сервер возвращает актуальный пояс черновика и неизменяемый пояс выдачи; формы конвертируют часы объекта в UTC с проверкой весеннего пропуска и выбором осеннего повторного часа.

Модуль автономен и не зависит от «Дефектов» или других прикладных модулей.

## Базовый объём

- карточка наряда/допуска;
- управляемые справочники;
- объект, место работ, структура, исполнитель, персонал, категория и тип документа;
- программа/содержание работ;
- плановые и фактические даты;
- черновик и редактирование;
- журнал с поиском, фильтрами и сортировкой;
- история значимых изменений;
- собственные schema/migrations/permissions/browser lifecycle.

## Целевая модель

Базовые справочники: структура, персонал, объекты.

Принцип интерфейса: **выбрать известное, вписать только изменяемое**.

Система присваивает собственный номер, хранит структурированные данные и формирует итоговый PDF локально.

## Шаблоны

Шаблон — функция первого уровня: выбор → предзаполнение → изменение переменной части → проверка → создание нового документа. Использование шаблона не меняет его без отдельного действия.

## Жизненный цикл

Отдельно хранятся:

- начало подготовки рабочего места;
- допуск бригады;
- фактическое начало работ;
- окончание работ;
- полное закрытие;
- перерывы и их история для многодневных работ.

## Ввод времени объекта

- Все поля жизненного цикла — календарное время организации, а не время устройства пользователя. В интерфейсе показано имя IANA-пояса.
- Для черновика сервер отдаёт текущий пояс организации; при выдаче клиент передаёт использованный пояс, а сервер отвергает устаревшее значение с HTTP 409, не меняя дату незаметно.
- Для выданного документа берётся сохранённый при выдаче снимок пояса, даже если организация уже изменила настройки. Устаревшие выдачи используют UTC.
- Несуществующее весной местное время не принимается. В повторяющийся осенью час обязательно выбирается первый либо второй момент (смещение UTC показывается явно). В базу всегда уходит UTC.
- История рабочих периодов, продлений и закрытия отображается в местном времени документа со смещением UTC; записи в хранилище не переписываются.

## UX

Один последовательный рабочий сценарий без хождения по служебным вкладкам. Поля появляются в порядке фактической работы. Редкие параметры не мешают типовой операции.

Визуальный стиль Workspace Organizer в 1.2 не перерабатывается. Новые экраны продолжают действующую систему интерфейса. Изменения состояния, фильтры, поиск, сохранение черновика и другие действия внутри открытой страницы по возможности выполняются через AJAX с понятным состоянием загрузки и ошибки; переход между полноценными страницами может оставаться обычной навигацией.

## Автономность

Модуль должен работать без внешнего интернета и без других прикладных модулей. PDF формируется локально и не требует Microsoft Office или другого офисного пакета.

## Производительность

До выпуска обязателен сценарий массового утреннего оформления: создание, открытие, поиск, изменение, справочники и генерация документов. Один тяжёлый запрос не должен блокировать остальных пользователей.

Все потенциально большие журналы и справочники используют серверную пагинацию и ограниченные ответы и входят в общую нагрузочную приёмку 1.2 на 1000 одновременно активных пользователей.

## Права, аудит и конкуренция

- права проверяются на сервере;
- значимые переходы жизненного цикла журналируются через общий аудит;
- административные и чувствительные действия проходят общую проверку политики;
- параллельное изменение одной записи не должно молча терять данные;
- повтор изменяющей команды после сетевого сбоя не должен создавать вторую операцию;
- закрытые или зафиксированные состояния изменяются только по явно разрешённому переходу.

## До начала реализации нужно зафиксировать

- точные роли участников;
- итоговый состав полей;
- статусы и переходы;
- правила изменения зафиксированных отметок;
- правила перерывов/возобновления;
- состав официальной PDF-формы;
- границу первого этапа для печати, экспорта, электронной подписи и внешнего обмена.

## Критерий готовности

Администратор может подготовить справочники и шаблоны, пользователь — пройти типовой цикл оформления без лишних служебных экранов, система сохраняет историю переходов и формирует локальный PDF. Модуль устанавливается и обновляется автономно, соблюдает RBAC/политики, корректно переживает повтор запроса и конкурентное изменение, а его массовый рабочий сценарий проходит нагрузочную приёмку 1.2.
