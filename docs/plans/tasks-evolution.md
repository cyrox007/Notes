# Развитие Tasks после 1.1

Актуально: 14 октября 2026.

Этот план развивает существующий модуль `tasks` как лёгкий ежедневник и командный таск-трекер. Цель — повысить фактическое выполнение задач и качество обратной связи, не превращая Workspace Organizer в тяжёлый универсальный комбайн.

## Базовое состояние 1.1

В 1.1 задача остаётся пользовательским объектом с владельцем, названием, описанием, статусом, приоритетом, сроком, подзадачами и напоминаниями. Calendar уже может безопасно связываться с Task через межмодульный контракт, а общая система уведомлений предоставляет единый слой хранения и доставки событий.

Новые возможности должны строиться поверх этих контрактов. `Tasks` не должен напрямую знать про конкретный мессенджер, SMTP, Browser Push или иной канал доставки.

## Принятые продуктовые идеи

Из практического опыта командной работы принимаются следующие направления:

- персональная очередь «Мои задачи» без лишней административной информации;
- быстрые представления «Сегодня» и «Завтра»;
- настраиваемый порядок задач внутри личной и командной очереди;
- исполнители и команды поверх общего платформенного слоя участников;
- ежедневная сводка ближайших задач;
- повторные уведомления при просрочке по настраиваемой политике;
- подтверждение начала работы и завершения задачи как явная обратная связь;
- быстрые действия из уведомления без обязательного перехода через несколько экранов;
- установка веб-интерфейса как приложения после появления общего PWA-контракта;
- API и бот-интеграции как дополнительный способ автоматизации, но не как основной интерфейс создания задач;
- управленческая сводка по зависшим, просроченным и завершённым задачам без превращения Tasks в отдельную BI-систему.

## Что сознательно не копируем

### Постоянная секретная ссылка вместо учётной записи

Длинная персональная ссылка удобна для прототипа, но не должна заменять обычную аутентификацию Workspace Organizer.

Если быстрый доступ понадобится, он реализуется только как отдельный ограниченный механизм:

- подписанный непрозрачный токен;
- ограниченная область действия;
- срок жизни;
- отзыв администратором;
- журнал использования;
- запрет повышения привилегий;
- при необходимости дополнительное подтверждение для чувствительных действий.

### Жёсткая привязка к одному мессенджеру

MAX, Telegram, E-mail, Browser/PWA Push и другие каналы подключаются через общий слой уведомлений. `Tasks` публикует событие и набор разрешённых действий, а канал доставки остаётся сменным адаптером.

### Бот как главный интерфейс

Создание и редактирование сложной задачи через чат на практике быстро становится неудобным. Основным интерфейсом остаётся веб-приложение. Бот позднее может выполнять короткие команды: показать план, отметить выполнение, перенести срок, добавить простую задачу или вернуть ссылку на полноценную форму.

### Нативное приложение раньше времени

Отдельный мобильный клиент не создаётся только ради дублирования веб-интерфейса. Сначала развивается адаптивный интерфейс и PWA. Нативный клиент рассматривается позднее только при доказанной необходимости функций операционной системы, недоступных или ненадёжных в PWA.

## Этапы развития

### 1.2 — личный рабочий день и дисциплина сроков

Минимальное расширение без командной модели:

- «Мои задачи» как основной персональный поток;
- отдельные выборки «Сегодня», «Завтра», «Просрочено»;
- ручной порядок задач внутри дневной очереди;
- события `task.due_soon`, `task.overdue`, `task.completed` через общий сервис уведомлений;
- ежедневная сводка на сегодня и завтра;
- настраиваемая частота повторного напоминания о просрочке;
- явный переход `Запланировано → В работе → Завершена` без полной перезагрузки страницы там, где это безопасно;
- настройки сводки и просрочки на уровне пользователя.

В 1.2 не добавляются команды, внешний API, бот-команды и собственная система каналов доставки.

### 1.3 — команды, исполнители и ответственность

После укрепления платформенных политик:

- общий платформенный объект команды/рабочей группы;
- участники команды и роли без дублирования RBAC;
- назначение задачи одному или нескольким ответственным в рамках разрешённой модели;
- персональная очередь исполнителя и общая очередь команды;
- видимость «поставил / отвечает / наблюдает»;
- подтверждение принятия задачи в работу;
- история переназначений и изменений срока;
- административно задаваемый порядок общих задач;
- ограниченные, отзывные и сроковые ссылки быстрого доступа для специально разрешённых сценариев, если такая потребность подтвердится.

Командный слой должен быть общим для будущих модулей, а не таблицами, принадлежащими только `Tasks`.

### 1.4 — действия прямо из каналов доставки

На базе зрелой системы уведомлений:

- универсальный контракт действий в уведомлении;
- «Взять в работу», «Завершить», «Открыть», «Отложить напоминание»;
- подписанные одноразовые или краткоживущие action-token для внешних каналов;
- защита от повторного применения действия;
- аудит доставки, открытия и выполненного действия без хранения лишнего содержимого сообщения;
- Browser/PWA Push для поддерживаемых окружений;
- подготовка устанавливаемой PWA-оболочки без обещания полного offline-редактирования.

Конкретный мессенджер не становится зависимостью модуля `Tasks`.

### 1.5 — API, автоматизация и бот-интеграции

После появления управляемого контура внешних соединений:

- версионированный API задач с отдельными правами и ограничениями;
- подписанные webhook-события изменения задачи;
- сервисные токены с минимальной областью действия;
- адаптеры ботов для поддерживаемых мессенджеров;
- короткие команды просмотра плана и изменения простых состояний;
- создание простой задачи из внешней системы;
- автоматизация между событиями Calendar, Tasks, Defects и другими модулями без прямого доступа к их таблицам;
- лимиты, идемпотентность и журнал внешних операций.

Бот остаётся вспомогательным клиентом API и не содержит отдельную бизнес-логику Tasks.

### 1.6 — операционная аналитика и интеллектуальные сводки

Без обязательной зависимости от AI:

- сводка просроченных и зависших задач по пользователю/команде;
- фактическое время прохождения основных состояний;
- доля задач, перенесённых по сроку;
- нагрузка по исполнителям без автоматической оценки «эффективности человека»;
- экспорт сводных данных в офисный контур;
- при включённом и разрешённом AI — краткое резюме рабочего дня и рисков только поверх доступных пользователю данных.

Автоматическое назначение задач и оценка сотрудников моделью в обязательный объём не входят.

## Общие требования

Каждый этап обязан сохранять следующие свойства:

- сервер остаётся источником истины;
- действия через AJAX/PWA/бот имеют тот же серверный контракт прав, что и обычный веб-интерфейс;
- внешняя доставка не может потерять встроенное уведомление при сбое канала;
- повтор доставки или повтор нажатия не создаёт дубликат действия;
- пользователь может отключить необязательные сводки и каналы в пределах административной политики;
- сроки рассчитываются с учётом часового пояса пользователя;
- командные выборки имеют серверную пагинацию и пригодны для нагрузочной приёмки 1.2+;
- межмодульные связи выполняются через capability/события, а не чтение чужих таблиц.

## Критерий направления

Tasks должен оставаться быстрее и проще тяжёлых корпоративных систем для повседневной постановки задачи. Новая возможность принимается только тогда, когда она уменьшает число действий пользователя, повышает видимость ответственности или улучшает доставку/обратную связь. Возможности, добавляющие административную сложность без такого эффекта, в модуль не включаются.
