# Развитие Tasks после 1.1

Актуально: 14 октября 2026.

Статус: **обязательная часть единого расширенного цикла 1.2**.

Этот план развивает существующий модуль `tasks` как лёгкий ежедневник и командный таск-трекер. Цель — повысить фактическое выполнение задач и качество обратной связи, не превращая Workspace Organizer в тяжёлый универсальный комбайн.

После решения объединить ранее разнесённые объёмы 1.2 и 1.3 развитие Tasks больше не распределяется искусственно по версиям 1.2–1.6. Основной рабочий, командный, уведомительный, PWA/API и интеграционный объём выполняется внутренними этапами одной линии 1.2.

Общий выпускной план: [1.2-unified-cycle.md](1.2-unified-cycle.md).

## Базовое состояние 1.1

В 1.1 задача остаётся пользовательским объектом с владельцем, названием, описанием, статусом, приоритетом, сроком, подзадачами и напоминаниями. Calendar может безопасно связываться с Task через межмодульный контракт, а общая система уведомлений предоставляет единый слой хранения и доставки событий.

Новые возможности строятся поверх этих контрактов. `Tasks` не знает напрямую про конкретный мессенджер, SMTP, Browser Push или иной канал доставки.

## Принятые продуктовые идеи 1.2

В обязательный объём входят:

- персональная очередь «Мои задачи» без лишней административной информации;
- быстрые представления «Сегодня», «Завтра» и «Просрочено»;
- настраиваемый порядок задач внутри личной и командной очереди;
- исполнители и команды поверх общего платформенного слоя участников;
- постановщик, ответственный и наблюдатель;
- ежедневная сводка ближайших задач;
- повторные уведомления при просрочке по настраиваемой политике;
- подтверждение начала работы и завершения задачи как явная обратная связь;
- быстрые действия из уведомления без обязательного перехода через несколько экранов;
- устанавливаемая PWA-оболочка и Browser/PWA Push;
- версионированный API Tasks;
- бот- и мессенджер-адаптеры как дополнительный интерфейс, но не как отдельная бизнес-логика;
- управленческая сводка по зависшим, просроченным и завершённым задачам без превращения Tasks в отдельную BI-систему;
- защита от конкурентной перезаписи, повторных команд и устаревших быстрых действий.

## Принципы интерфейса

В 1.2 новый визуальный стиль не создаётся. Текущий стиль Workspace Organizer сохраняется.

Для повседневной работы приоритет имеет мобильная рабочая очередь, а не сложная доска управления.

- первый экран отвечает на вопрос «что мне нужно сделать сейчас»;
- задача читается как компактная карточка: название, срок, состояние и ответственный без перегрузки метаданными;
- завершение и принятие в работу доступны в одно действие;
- личные задачи и командное управление разделяются, чтобы обычный исполнитель не видел административную сложность;
- создание новой задачи остаётся заметным и коротким действием;
- изменение статуса, сортировка, перенос срока, быстрые фильтры и аналогичные действия внутри уже открытой страницы по возможности выполняются через AJAX без полной перезагрузки;
- каждое асинхронное действие имеет понятное состояние выполнения и ошибки;
- переход между полноценными страницами может оставаться обычной навигацией;
- канбан, диаграммы и расширенные панели являются дополнительными представлениями при подтверждённой потребности, а не главным экраном Tasks.

AJAX, PWA, API и внешние действия используют один и тот же серверный контракт прав и бизнес-правил.

## Команды и ответственность

В 1.2 появляется общий платформенный объект команды/рабочей группы.

Требования:

- участники команды и роли без дублирования RBAC;
- назначение задачи одному или нескольким ответственным в пределах разрешённой модели;
- видимость ролей «поставил / отвечает / наблюдает»;
- персональная очередь исполнителя;
- общая очередь команды;
- подтверждение принятия задачи в работу;
- история переназначений;
- история изменения срока;
- административно задаваемый порядок общих задач;
- командные выборки с серверной пагинацией и ограниченными ответами.

Командный слой должен быть общим для будущих модулей, а не набором таблиц, принадлежащих только `Tasks`.

## Личный рабочий день

Обязательные рабочие представления:

- «Мои задачи»;
- «Сегодня»;
- «Завтра»;
- «Просрочено»;
- ручной порядок задач внутри дневной очереди;
- быстрый переход `Запланировано → В работе → Завершена`;
- настройки сводки и просрочки на уровне пользователя;
- учёт часового пояса пользователя.

## Защита от потери изменений

У изменяемой задачи вводится серверная версия состояния.

Клиент отправляет ожидаемую версию задачи вместе с командой изменения. Сервер атомарно выполняет изменение только при совпадении версии. Если задача уже изменилась другим пользователем, вкладкой, PWA или внешним клиентом, сервер возвращает конфликт и актуальное состояние вместо молчаливой перезаписи.

Такой конфликт не повторяется автоматически.

Этот контракт применяется к:

- редактированию задачи;
- смене статуса;
- переносу срока;
- переназначению;
- быстрым действиям из уведомлений;
- API-командам;
- действиям бот-адаптера.

## Идемпотентные команды

Изменяющая операция получает устойчивый идентификатор команды (`command_id` или эквивалент).

Повтор одного и того же запроса после потери ответа не должен:

- создать вторую задачу;
- повторно изменить срок;
- повторно применить завершение;
- дважды выполнить действие из уведомления;
- создать два внешних события для одной логической операции.

Повтор допускается для временной ошибки сети, 429 и безопасных 5xx-сценариев. Ошибка валидации и конфликт версии автоматически не повторяются.

## Ежедневные сводки

Сводка включает как минимум:

- просроченные задачи;
- задачи на сегодня;
- задачи на завтра;
- ближайшую важную задачу;
- короткие разрешённые действия.

Сводка является живым представлением, а не бесконечной последовательностью новых сообщений.

Для пары пользователь/день/канал хранится логический экземпляр сводки. Система рассчитывает отпечаток содержимого:

- если состояние не изменилось — повторная отправка не выполняется;
- если канал умеет редактировать ранее доставленное сообщение — оно обновляется;
- если канал не умеет редактирование — адаптер применяет свою безопасную политику замены/новой доставки;
- сбой внешнего канала не удаляет встроенное уведомление Workspace.

## Повторные напоминания о просрочке

Пользовательская или административная политика определяет допустимую частоту повторов.

Повтор не должен создавать лавину одинаковых событий. Дедупликация, планировщик и очередь обязаны корректно переживать:

- повтор cron;
- запуск нескольких workers;
- перезапуск сервера;
- недоступность внешнего канала;
- смену суток;
- изменение часового пояса.

## Быстрые действия из уведомлений

Универсальный контракт допускает действия:

- «Взять в работу»;
- «Завершить»;
- «Открыть»;
- «Отложить»/перенести срок или напоминание;
- другие короткие действия только при наличии явного серверного контракта.

Для внешних каналов применяются ограниченные и краткоживущие action-token либо эквивалентный подписанный механизм.

Быстрое действие содержит защиту от повторного и устаревшего применения:

- идентификатор команды;
- ожидаемую версию задачи;
- ограниченный срок действия;
- проверку прав на сервере;
- аудит результата.

Устаревшая кнопка не может молча изменить уже обновлённую задачу.

## NotificationService

Поток остаётся общеплатформенным:

```text
Tasks
  ↓
семантическое событие
  ↓
NotificationService
  ↓
встроенный центр / Push / E-mail / MAX / Telegram / Webhook / другой адаптер
```

Конкретный мессенджер не является зависимостью `Tasks`.

Для интерактивных сценариев 1.2 общий сервис поддерживает:

- надёжную очередь внешней доставки;
- повторные попытки с пределом;
- отдельное ошибочное состояние для диагностики;
- дедупликацию;
- схлопывание заменяемых событий;
- обновляемые сводки;
- безопасные действия;
- аудит доставки и результата действия без хранения лишнего содержимого.

## PWA

В 1.2 подготавливается устанавливаемая PWA-оболочка:

- адаптивный рабочий интерфейс;
- быстрый запуск основных сценариев Tasks;
- Browser/PWA Push;
- безопасный переход из уведомления в нужную задачу;
- действия через те же серверные команды, что и обычный веб-интерфейс.

Полное двустороннее offline-редактирование всех задач не обещается до определения общей модели конфликтов, локальной очереди команд и восстановления.

Отдельный нативный клиент не создаётся только ради дублирования PWA.

## API и бот-интеграции

В 1.2 появляется версионированный API Tasks.

Обязательный контракт:

- отдельные права и области действия;
- сервисные токены с минимальными полномочиями;
- серверная проверка ACL/RBAC/политики;
- непрозрачная курсорная пагинация;
- версионирование сущностей;
- идемпотентность изменяющих команд;
- лимиты и защита от перегрузки;
- журнал внешних операций;
- подписанные webhook-события при необходимости;
- отсутствие прямого доступа к внутренним таблицам.

MAX, Telegram и другие поддерживаемые интеграции реализуются как адаптеры/клиенты этого контракта. Бот может показать план, выполнить короткое действие, создать простую задачу или вернуть ссылку на полноценную форму, но не содержит отдельную копию бизнес-логики Tasks.

## Быстрый доступ

Постоянная секретная ссылка не заменяет штатную аутентификацию.

Если сценарии быстрого доступа нужны для конкретного действия, используется только ограниченный механизм:

- подписанный непрозрачный токен;
- минимальная область действия;
- срок жизни;
- отзыв;
- журнал использования;
- запрет повышения привилегий;
- дополнительное подтверждение для чувствительной операции при необходимости.

## Операционная сводка

В 1.2 допускается базовая управленческая сводка без отдельной BI-системы:

- просроченные задачи;
- зависшие задачи;
- завершённые за период;
- изменение сроков;
- состояние очереди команды.

Автоматическая оценка «эффективности человека» и автоматическое назначение задач моделью не входят в обязательный объём.

Интеллектуальные AI-резюме остаются отдельным будущим направлением и не являются зависимостью Tasks 1.2.

## Общие требования

Tasks 1.2 обязан сохранять следующие свойства:

- сервер остаётся источником истины;
- AJAX/PWA/API/бот используют один серверный контракт прав;
- внешняя доставка не может потерять встроенное уведомление;
- повтор доставки или повтор нажатия не создаёт второе действие;
- пользователь может отключить необязательные сводки и каналы в пределах административной политики;
- сроки рассчитываются с учётом часового пояса пользователя;
- потенциально большие выборки используют серверную пагинацию;
- межмодульные связи выполняются через capability/события, а не чтение чужих таблиц;
- новый код не связывает `Tasks` с конкретным внешним провайдером;
- интерфейс сохраняет текущий стиль системы.

## Обязательные race/failure проверки

До выпуска 1.2 проверяются минимум:

- два пользователя редактируют одну задачу;
- две вкладки меняют одну задачу;
- повтор команды после потери ответа;
- двойное нажатие действия;
- повтор webhook;
- устаревшая кнопка из старого уведомления;
- падение worker после внешней доставки;
- недоступность внешнего канала;
- повторное построение одной сводки;
- смена суток/часового пояса;
- параллельный cron/worker;
- восстановление очереди после рестарта.

## Внутренние этапы 1.2

1. версия сущности, идемпотентные команды и общие события;
2. «Мои задачи», сегодня/завтра/просрочено и AJAX-действия;
3. команды, участники и ответственность;
4. сводки и повторные уведомления;
5. быстрые действия и NotificationService;
6. PWA/Push;
7. API и внешние адаптеры;
8. операционная сводка, нагрузка, race/failure и browser-приёмка.

Это этапы одной ветки/дорожной карты 1.2, а не причины переносить утверждённый объём в отдельные 1.3–1.6.

## Критерий направления

Tasks должен оставаться быстрее и проще тяжёлых корпоративных систем для повседневной постановки задачи. Новая возможность принимается тогда, когда она уменьшает число действий пользователя, повышает видимость ответственности или улучшает доставку/обратную связь. Возможности, добавляющие административную сложность без такого эффекта, в модуль не включаются.
