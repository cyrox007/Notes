# Messenger E2EE — фундамент 1.2

Актуально: 16 октября 2026.

Статус: **обязательный архитектурный фундамент цикла 1.2**.

## Цель

В 1.2 необходимо заложить возможность настоящего сквозного шифрования Messenger, при котором сервер Workspace Organizer не обладает ключами содержимого и не может расшифровать текст сообщений или защищённые вложения.

Текущее серверное шифрование Messenger через XChaCha20-Poly1305 сохраняется как совместимый режим хранения, но не считается E2EE: серверный `MSG_SECRET_KEY` позволяет приложению расшифровывать содержимое.

E2EE проектируется как отдельный версионированный протокол поверх существующего транспорта Messenger. WebSocket и Long Poll отвечают только за доставку и не получают права расшифровывать пользовательское содержимое.

## Границы обязательного объёма 1.2

В 1.2 должны быть определены и реализованы базовые контракты:

- криптографическая идентичность устройства;
- отдельная пара ключей для каждого доверенного устройства пользователя;
- безопасная регистрация нового устройства;
- отзыв потерянного или скомпрометированного устройства;
- безопасное установление ключа личного диалога без передачи серверу ключа содержимого;
- ротация ключевого материала;
- защита истории при изменении состава устройств;
- версионированный формат E2EE-сообщения;
- защита от повторной доставки, перестановки и подмены шифротекста;
- сквозное шифрование вложений на клиенте до загрузки на сервер;
- безопасная передача ключа вложения только участникам диалога;
- совместимость с личными и групповыми диалогами;
- явная модель смены состава группового чата и ротации группового ключевого состояния;
- безопасная работа нескольких устройств одного пользователя;
- отображение состояния защищённого диалога и состава доверенных устройств;
- миграционный режим рядом с существующим серверным шифрованием;
- тесты потери, отзыва, повторной регистрации и рассинхронизации устройств.

## Криптографический принцип

Собственный неподтверждённый криптографический протокол не разрабатывается.

Перед реализацией проводится отдельный технический выбор проверенной схемы класса Signal Protocol / Double Ratchet либо другого зрелого протокола с сопоставимыми свойствами. Выбор должен быть документирован отдельным решением с анализом библиотек, лицензий, поддержки браузера/PWA и серверной части.

Минимальные требуемые свойства:

- аутентифицированное шифрование;
- уникальные ключи/состояния диалога, а не один общий мастер-ключ сервера;
- прямая секретность для уже отправленных сообщений;
- восстановление защищённости будущих сообщений после обновления ключевого состояния;
- защита от подмены сообщения;
- безопасная ротация при изменении доверенных устройств;
- криптографическая случайность из системного CSPRNG;
- версионирование протокола без скрытой смены формата.

## Модель устройств

E2EE привязывается не только к аккаунту, но и к конкретным доверенным устройствам.

Для каждого устройства нужны как минимум:

- устойчивый `device_id`, не являющийся скрытым аппаратным отпечатком;
- публичный ключ идентичности;
- служебные публичные ключи, необходимые выбранному протоколу;
- дата регистрации;
- дата последней успешной проверки;
- состояние `active/revoked` или эквивалент;
- информация, достаточная пользователю для распознавания собственного устройства;
- аудит регистрации и отзыва без записи приватного ключа.

Приватные E2EE-ключи не передаются серверу в открытом виде и не сохраняются в серверной конфигурации.

Основа доверенных устройств из общего контура безопасности 1.2 должна быть совместима с этой моделью, но доверенный сеанс приложения и криптографическое E2EE-устройство не должны молча считаться одним и тем же объектом.

## Личные диалоги

Для личного диалога сервер хранит и пересылает только публичные материалы установки сеанса, служебные идентификаторы и шифротекст.

Сервер не должен получать:

- приватный ключ устройства;
- открытый ключ содержимого диалога в форме, достаточной для расшифровки;
- открытый текст сообщения;
- незашифрованный ключ вложения.

Смена/отзыв устройства требует обновления ключевого состояния диалога. Устаревшее или отозванное устройство не должно автоматически получать новые сообщения.

## Групповые диалоги

Групповое E2EE не строится на одном вечном симметричном ключе группы.

Должны быть формально определены:

- добавление участника;
- удаление участника;
- добавление нового устройства существующего участника;
- отзыв устройства;
- ротация ключевого состояния после изменения состава;
- поведение старой истории;
- права администратора группы без возможности серверного чтения содержимого.

Изменение состава группы создаёт новое криптографическое состояние для будущих сообщений.

## Вложения

Текущий Messenger хранит вложения в приватном серверном хранилище. Для E2EE этого недостаточно.

В E2EE-диалоге файл должен:

1. получить случайный ключ содержимого на клиенте;
2. быть зашифрован до отправки на сервер;
3. загружаться как непрозрачный шифротекст;
4. иметь контроль целостности;
5. передавать ключ содержимого участникам только внутри защищённого протокола диалога;
6. расшифровываться только на устройстве получателя.

Сервер может знать технические метаданные, необходимые для хранения и доставки, но не должен получать открытое содержимое файла.

Отдельно требуется решение по сокрытию имени файла, типа и размера: какие метаданные обязательны транспорту, а какие должны быть перенесены внутрь зашифрованного конверта.

## Поиск, превью и Push

Настоящее E2EE запрещает текущую серверную схему поиска, при которой сервер расшифровывает сообщения и ищет по открытому тексту.

Для E2EE-диалогов:

- полнотекстовый поиск выполняется на клиенте по локально доступной расшифрованной истории либо по отдельному безопасному индексу после отдельного проектного решения;
- серверный поиск по открытому тексту отключён;
- превью содержимого не формируется сервером из расшифрованного текста;
- Push по умолчанию не содержит открытый текст сообщения;
- PWA/нативный клиент после получения сигнала Push самостоятельно получает шифротекст и расшифровывает его локально, если платформа позволяет сделать это безопасно;
- журналы и диагностика не должны содержать открытый текст E2EE-сообщений.

## Резервные копии и восстановление

E2EE не должно превращаться в скрытую серверную возможность восстановления ключей.

Нужно выбрать явную пользовательскую модель:

- безопасный перенос с уже доверенного устройства;
- зашифрованная резервная копия ключевого материала, защищённая секретом, которого сервер не знает;
- либо сознательная невозможность восстановить старую E2EE-историю без существующего доверенного устройства/резервной копии.

Конкретная схема восстановления утверждается до включения E2EE по умолчанию.

Администратор не получает «аварийный мастер-ключ» чтения пользовательской переписки. Если организационному развёртыванию требуется режим с серверным доступом или архивированием, это должен быть отдельный явно обозначенный режим, а не скрытое ослабление E2EE.

## Совместимость и миграция

Переход выполняется без удаления существующей истории.

На первом этапе Messenger поддерживает минимум два явно различимых режима:

- `server_encrypted` — существующее серверное шифрование хранения;
- `e2ee` — содержимое доступно только конечным устройствам.

Режим задаётся на уровне диалога/криптографической эпохи и не определяется догадкой по содержимому поля.

Для старой переписки необходимо отдельно определить:

- остаётся ли она в серверно-зашифрованном режиме;
- допускается ли пользовательская миграция истории в E2EE;
- как маркируется граница перехода;
- что происходит при участнике без E2EE-совместимого устройства.

Нельзя молча показывать серверно-зашифрованный диалог как «сквозно защищённый».

## Метаданные и аудит

E2EE защищает содержимое, но не устраняет все метаданные.

Серверу могут оставаться известны участники диалога, время доставки, технический размер конверта, идентификаторы сообщений и устройств и другие данные, необходимые маршрутизации.

Документация и интерфейс должны честно различать:

- содержимое, недоступное серверу;
- транспортные метаданные;
- административные события;
- события безопасности устройств.

Аудит E2EE хранит только метаданные безопасности: регистрацию/отзыв устройства, смену криптографической эпохи, ошибки проверки подписи, конфликт ключей и аналогичные события. Текст сообщения, ключи и расшифрованные вложения в аудит не попадают.

## Связь с API, PWA и будущими приложениями

E2EE должно жить над единым клиентским протоколом и не зависеть от конкретного интерфейса.

Web/PWA, будущий Android/iOS-клиент и другие разрешённые клиенты используют один формат криптографических конвертов и одну серверную модель устройств.

API Messenger не получает endpoint «расшифровать сообщение на сервере» для E2EE-диалогов.

PWA 1.2 должна проектироваться так, чтобы ключевой материал можно было хранить с использованием доступных защищённых возможностей браузера, не помещая приватные ключи в обычные серверные session/cookie/localStorage без отдельной модели защиты.

## Приёмочные проверки

До заявления поддержки E2EE обязательны проверки:

- сервер с полным доступом к БД не может расшифровать E2EE-сообщение;
- сервер с доступом к файловому хранилищу не может прочитать E2EE-вложение;
- компрометация `MSG_SECRET_KEY` не раскрывает E2EE-содержимое;
- два устройства одного пользователя получают только предназначенные им зашифрованные состояния;
- отозванное устройство не получает новые сообщения;
- добавление/удаление участника группы меняет криптографическое состояние будущих сообщений;
- повтор старого шифротекста не создаёт новое корректное сообщение;
- повреждение шифротекста определяется до показа пользователю;
- смена транспорта WebSocket ↔ Long Poll не меняет криптографическую модель;
- Push не раскрывает открытый текст серверной стороне;
- диагностические журналы не содержат содержимое сообщений и ключи;
- потеря одного устройства не приводит к раскрытию ключей другим пользователям;
- выбранный сценарий восстановления проверен отдельно.

## Что считается результатом 1.2

Минимальный обязательный результат цикла 1.2:

1. утверждённый и документированный криптографический протокол;
2. серверная модель устройств и публичного ключевого материала;
3. версионированный формат E2EE-конверта;
4. рабочий E2EE-путь как минимум для личных диалогов;
5. клиентское шифрование вложений;
6. отзыв устройства и ротация ключевого состояния;
7. совместимый переход рядом с текущим `server_encrypted` режимом;
8. отсутствие серверной расшифровки в E2EE-пути;
9. обязательные security/failure-тесты;
10. подготовленный контракт для групп, PWA и будущих мобильных клиентов.

Полное включение E2EE по умолчанию для всех существующих диалогов допускается только после выполнения этих условий и отдельной проверки миграции старой истории.
