# Files 1.2 — файловые пространства и гибкие права доступа

Статус: **обязательная часть единого цикла 1.2**.

Цель — развить текущий персональный файловый менеджер в единое файловое пространство Workspace Organizer. Пользователь сохраняет собственное приватное хранилище, одновременно появляется общее организационное хранилище с управляемыми правами. Архитектура сразу должна допускать командные, проектные и модульные пространства без второй переделки схемы доступа.

## Состояние работ в линии 1.2 (18 октября 2026)

Реализованы основа общего пространства, наследуемый ACL, загрузка и скачивание, операции
над собственными и чужими объектами, корзина и восстановление. В текущем этапе
добавлены файловые группы, их состав, административная панель управления правами,
диагностика эффективных разрешений и настройка срока хранения в корзине.

Срок удержания настраивается в администрации (по умолчанию 30 дней).
Реализована **операторская команда окончательной очистки** с предварительным
просмотром, карантином, журналом и восстановлением после аварии. Без явного
`--apply` данные не удаляются. Автоматическое расписание **не включено** —
это отдельное эксплуатационное решение после проверки резервных копий.

Группы файлового доступа не заменяют роли системной платформы.
Выполнена постраничная загрузка общих каталогов: выдача ограничена 40 доступными
объектами, закрытые папки не включаются в результаты, продолжение использует
курсор с проверкой версии родительского каталога. Загрузка до конца большого
каталога возможна без снятия ACL и без раскрытия общих счётчиков объектов.

Остаются задачами до полной готовности Files 1.2: нагрузочная приёмка,
дополнительные групповые сценарии и удобство массового администрирования прав.

### Очистка корзины оператором

Перед началом проверьте резервную копию базы данных и приватного хранилища.

```bash
php bin/migrate.php --status
php bin/files-purge.php --limit=5
php bin/files-purge.php --limit=5 --apply
```

Последняя команда **безвозвратно удаляет** корневые объекты корзины, у которых
истёк срок хранения, включая файлы и вложенные папки. Один корневой объект
ограничен 500 узлами; слишком большие деревья не удаляются частично и требуют
отдельной обработки. Ключи физического хранения проходят проверку, а действие
сначала помещает данные в карантин. Если транзакция БД не подтвердилась,
следующий запуск возвращает файлы из незавершённого карантина. Если подтвердилась,
повторный запуск завершает удаление временных физических копий.

Очистка действует только на пространство `global`, не касается `user_files`.
Программа возвращает ненулевой код при ошибке и не скрывает нарушения
целостности. Учитывайте, что восстановление из корзины после успешной очистки
невозможно — потребуется резервная копия.

## Базовая модель

Вводится объект файлового пространства `FileSpace`.

Поддерживаемые типы на уровне модели:

- `personal` — персональное пространство пользователя;
- `global` — общее пространство организации;
- `team` — пространство рабочей группы;
- `project` — проектное пространство;
- `module` — пространство прикладного модуля.

В пользовательский интерфейс первой реализации 1.2 обязательно выводятся как минимум:

- «Мои файлы»;
- «Общие файлы».

Типы `team`, `project` и `module` могут подключаться по мере появления соответствующих сценариев, но не должны требовать новой несовместимой модели хранения или прав.

## Владение объектами

Персональное пространство принадлежит пользователю.

Файлы и папки глобального пространства принадлежат самому `FileSpace`, а не учётной записи автора. Для каждого объекта сохраняется `created_by`, но удаление или блокировка автора не должна лишать организацию доступа к документу.

Минимальный контракт объекта:

- `space_id`;
- `parent_id`;
- `created_by`;
- `created_at`;
- `updated_by`;
- `updated_at`;
- версия состояния для защиты от конкурентной перезаписи;
- состояние удаления/архива;
- собственная политика доступа либо признак наследования.

Физическое расположение файла не является источником прав доступа. Решение принимается только серверной политикой по идентификаторам пространства и объекта.

## Права

Права разделяются по операциям, а не сводятся к одному `read/write`.

Минимальный набор:

- видеть пространство или папку;
- получать список содержимого;
- открывать и скачивать файл;
- загружать новый файл;
- создавать папку;
- переименовывать;
- перемещать;
- заменять содержимое файла;
- изменять собственные объекты;
- изменять чужие объекты;
- удалять собственные объекты;
- удалять чужие объекты;
- создавать внутреннюю или публичную ссылку, если политика это разрешает;
- просматривать историю;
- восстанавливать удалённое;
- управлять политикой доступа объекта.

Отдельные права на свои и чужие объекты обязательны. Например, обычной роли можно разрешить создавать и редактировать собственные файлы, но запретить изменение и удаление чужих.

## Субъекты политики

Правило может назначаться:

- всем авторизованным пользователям;
- конкретной роли;
- рабочей группе/команде;
- конкретному пользователю;
- владельцу/автору объекта как специальному условию;
- администратору или иной управляемой административной роли.

Files не создаёт вторую независимую систему RBAC. Субъекты связываются с общими ролями, группами и политиками платформы 1.2.

## Наследование

По умолчанию дочерняя папка наследует политику ближайшего родителя.

Администратор или субъект с правом управления политикой может:

- оставить наследование;
- отключить наследование для конкретной папки;
- задать собственные правила;
- позже вернуть наследование.

Интерфейс обязан явно показывать источник эффективного права: собственное правило либо родительскую папку, от которой оно унаследовано.

Не допускается ситуация, когда администратор не может объяснить, почему пользователь получил или не получил доступ.

## Разрешение конфликтов правил

До реализации фиксируется единая детерминированная модель приоритета.

Обязательные свойства:

- явный запрет не должен случайно отменяться более широким разрешением;
- более конкретное правило пользователя/объекта имеет предсказуемый приоритет над общим правилом роли или пространства;
- сервер возвращает итоговое решение и при необходимости диагностический источник политики без раскрытия лишней информации обычному пользователю;
- отсутствие права просмотра означает, что объект не появляется в дереве, поиске и счётчиках пользователя.

Точная таблица приоритетов должна быть закреплена контрактным тестом до реализации UI управления ACL.

## Глобальное пространство

Глобальный `FileSpace` создаётся платформой и управляется администраторами.

Администратор может настроить, например:

- всем только чтение;
- выбранным ролям создание файлов;
- выбранным ролям создание папок;
- изменение только собственных объектов;
- изменение собственных и чужих объектов;
- полный запрет записи для всех;
- отдельные исключения для конкретных пользователей или групп.

Глобальное пространство не означает публичность всех его папок. Внутри него допускаются полностью закрытые разделы, которые не видны пользователям без соответствующего права.

## Частные папки и локальные политики

Любая папка пространства может иметь собственную политику.

Пример:

```text
Общие файлы
├── Инструкции          читать: все; изменять: администраторы
├── Общие материалы     читать: все; свои изменять: да; чужие: нет
└── Бухгалтерия         видеть/читать/изменять: только группа бухгалтерии
```

Подпапка может ужесточать или расширять доступ только в пределах разрешённой платформенной политики и административных полномочий.

## Удаление и восстановление

Для общих пространств обычное удаление не должно немедленно уничтожать файл физически.

Базовый путь:

`active → deleted/archived → retention → physical purge`.

Окончательное удаление выполняется только субъектом с отдельным правом и с аудитом. Срок хранения может задаваться политикой пространства.

## Аудит

Для общих пространств обязательно журналируются как минимум:

- создание файла или папки;
- замена содержимого;
- переименование;
- перемещение;
- удаление;
- восстановление;
- изменение ACL/наследования;
- создание и отзыв ссылки;
- скачивание, если это включено политикой аудита.

Аудит хранит идентификаторы и необходимые метаданные операции, но не копирует содержимое файлов.

## Конкурентные изменения и идемпотентность

Files использует общие контракты 1.2:

- версия изменяемой сущности;
- ожидаемая версия в изменяющей команде;
- явный конфликт при устаревшем состоянии;
- `command_id` или эквивалент для защиты от повторного создания/перемещения/удаления;
- отсутствие скрытого автоматического повтора конфликтов версии.

Особенно это обязательно для ACL, перемещения, переименования и удаления.

## Поиск, пагинация и производительность

Поиск и список содержимого работают только в пределах доступных пользователю пространств и папок.

Обязательны:

- серверная пагинация больших каталогов;
- индексы по `space_id`, `parent_id`, имени, состоянию и полям политики;
- отсутствие N+1 при вычислении видимости каталога;
- пакетное вычисление эффективных прав;
- отсутствие обхода всего дерева на каждый запрос;
- включение Filespaces в нагрузочную приёмку 1000 пользователей.

## AJAX и интерфейс

Визуальный стиль системы не меняется.

Внутри открытого файлового менеджера без полной перезагрузки выполняются там, где это безопасно:

- создание папки;
- загрузка;
- переименование;
- перемещение;
- удаление/восстановление;
- переключение представления;
- изменение ACL;
- фильтрация и сортировка.

Каждая операция имеет состояние выполнения, успешный результат и понятную ошибку. При ошибке интерфейс сверяется с серверным состоянием.

## Безопасность

Все права проверяются на сервере независимо от состояния UI.

Запрещено:

- доверять `space_id`, `owner_id` или ACL из клиента без проверки;
- выдавать физический путь private storage;
- позволять прямой доступ к файлу по предсказуемому URL;
- считать скрытие кнопки достаточной проверкой права;
- переносить объект между пространствами без отдельной проверки прав источника и назначения.

## Миграция текущего Files

Существующее персональное хранилище должно быть перенесено без потери UID, вложений, квот и прав владельцев.

Предпочтительная стратегия:

1. создать персональный `FileSpace` для каждого существующего пользователя;
2. связать текущие файлы и папки с соответствующим `space_id` без физического перемещения данных, если это возможно;
3. сохранить существующие квоты и ссылки;
4. создать глобальный `FileSpace` отдельно;
5. только после подтверждения миграции включить новый UI выбора пространств.

Миграция обязана иметь preflight, повторный безопасный запуск и recovery/rollback в рамках updater-контракта 1.2.

## Критерий готовности Files 1.2

Функция считается готовой, когда одновременно:

- персональные файлы существующих пользователей доступны без потери данных;
- глобальное пространство работает;
- администратор может полностью запретить либо разрешить операции по ролям, группам и пользователям;
- права на свои и чужие объекты разделены;
- ACL наследуются и могут локально переопределяться;
- закрытая папка не раскрывается через дерево, поиск, API или прямой запрос;
- ACL и файловые операции защищены версиями и идемпотентностью;
- удаление общих файлов восстанавливаемо до физической очистки;
- значимые операции попадают в общий аудит;
- браузерные и интеграционные тесты покрывают положительные и отрицательные сценарии;
- нагрузочная приёмка подтверждает работу больших каталогов и вычисления прав.
