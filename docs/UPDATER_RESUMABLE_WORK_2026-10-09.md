# Сохраняемые шаги обновления: состояние реализации

Изменения предназначены для проверки в черновике PR. Полная готовность браузерного обновления и выпуска не подтверждена.

## Реализовано

- Контрольная точка записывается во временный приватный файл, синхронизируется и публикуется переименованием. При чтении проверяются идентичность операции и хеш состояния.
- Распаковка продолжает работу с сохранённого файла. Незавершённый текущий файл создаётся заново; кандидат публикуется только после проверки полного дерева.
- Переключение кода использует неизменяемый план и курсор. Обрыв между заменой файла и записью курсора допускает только точное состояние после запланированной операции.
- План сохраняется после завершения HTTP-шагов переключения: обрыв перед записью состояния `code_switched` допускает повторное подтверждение.
- Откат кода повторяет только отличающиеся файлы, сохраняя пользовательские данные и права файлов.
- Восстановление БД сохраняет список удаляемых объектов и положение в SQL. Для INSERT данные и курсор фиксируются одной транзакцией InnoDB. DDL допускает повтор до начала данных объекта. Служебная таблица удаляется перед итоговой проверкой.
- Штатная пауза не вызывает откат и не отзывает токен продолжения.
- До первого HTTP-шага публикуется отдельный capability-защищённый PHP-вход. Он проверяет SHA-256 внешнего runtime и подключает только его классы; index.php, Router и live-классы не нужны. Браузер получает same-origin URL с учётом BASE_PATH. Каталог `update-continuations` исключён из backup, apply и rollback.
- Состав внешнего runtime замыкается по локальным require-зависимостям; отдельно включён публичный реестр доверенных ключей. После проверенной резервной точки runtime привязывается к журналу; обрыв до этой привязки исправляется следующим шагом candidate.
- Копирование кода резервной точки возобновляется по уже проверенным файлам. Неполный файл переписывается; manifest публикуется атомарно после fsync. Обрыв после записи готового backup manifest и до rename каталога допускает повторную проверку и публикацию той же точки.

## Проверено локально

PHP 8.3.6; восстановление БД — MariaDB. Пройдены проверки пофайлового отката, прав файлов, применения и отката, внешнего исполнительного окружения, браузерного режима без CLI, раннего восстановления, независимости отката от кандидата, перехода с 1.0.14, потокового разбора дампа и резервной точки транзакции.

Проверка БД принудительно завершает каждый вызов после одной операции; новые объекты исполнителя продолжают восстановление. Проверены количество строк, Unicode, BLOB, TEXT, JSON и триггер. Проверка переключения удаляет сохранённый курсор после замены файла и подтверждает безопасное продолжение и повтор завершённого переключения. Это моделирование разрыва контрольной точки; оно не заменяет испытания с принудительным завершением PHP-процесса на каждой границе.

Паузы внутри применения и отката включаются командой только при выполнении из внешнего окружения. Новый HTTP-вход запускает именно это окружение; старый maintenance-мост остаётся для совместимости. Пошаговая распаковка безопасна, поскольку ещё не изменяет рабочие файлы.

Дополнительно проверены PHP 8.1.9 (Windows/OSPanel) и PHP 8.3.6 (WSL): настоящий HTTP-вход при недоступных live index.php и core, запрещённых процессных функциях и лимите 32 МБ; неверный токен, чужой Origin, отзыв токена и повреждение runtime. JavaScript проверяет переключение на внешний same-origin endpoint и отклоняет чужой origin. На MariaDB 10.8 проверено пофайловое резервирование с паузой после каждого файла, повтор неполной копии и обрыв перед публикацией готовой точки. На MariaDB 10.11 проверен настоящий SIGKILL посреди пошагового SQL-восстановления с новыми соединениями между шагами: без дублей, с Unicode, JSON, BLOB и рабочим триггером. Эти сценарии добавлены в CI; это ещё не сквозной тест exact 1.0.14 через новый HTTP-вход.

## Обязательно до слияния и выпуска

1. Сквозная проверка нового браузерного входа через все фазы применения/отката, включая потерю клиента и истечение capability lease при частично заменённом live-tree. Терминальный HTTP-тест подтверждает независимость загрузки, но не весь переход и автоматический ранний recovery при недоступном live-коде.
2. Сохраняемое создание согласованного снимка БД. Копирование кода уже возобновляется; дамп БД всё ещё создаётся одной транзакцией и при смерти PHP начинается заново. Между HTTP-запросами нельзя удерживать исходную транзакцию БД; необходим отдельно проверенный протокол согласованности.
3. Подписанный браузерный переход с точной версии 1.0.14. Имеющийся bootstrap предназначен для CLI.
4. Ограничение времени внутри обработки одного большого файла и SQL-запроса. Бюджет сейчас проверяется после долговечного завершения операции; полное хеширование, проверка дампа, миграции и отдельные операции могут превышать лимит запроса.
5. Расширенные испытания с реальным завершением процесса на остальных границах, MySQL, ограничениями памяти и времени, отключёнными процессными функциями и приёмка на целевом хостинге.

До завершения этих пунктов черновик не следует выпускать как полностью отказоустойчивый браузерный обновлятор. Пользователь подтвердил: тестовый хостинг находится у приятеля, доступа к нему у пользователя нет. Приёмка на нём остаётся внешним неподтверждённым этапом.
