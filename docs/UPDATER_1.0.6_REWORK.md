# Workspace Organizer 1.0.6 — переработка системы обновлений

Актуально: 26 сентября 2026.

## Причина переработки

Реальная приёмка перехода 1.0.4 → 1.0.5 на Windows / OSPanel 5.2.2 выявила дефекты, которые автоматические Linux/Windows-контракты не поймали:

- старый updater credential может остаться локально валидным по формату, но быть отозван сервером; клиент не выполняет автоматический повторный bootstrap по действующей лицензии;
- destructive apply/recovery запускается из live-каталога `bin`, а затем rollback пытается переименовать тот же каталог; на Windows это приводит к отказу `Cannot quarantine failed release entry during rollback: bin`;
- rollback-dump сериализует строковые значения как `X'HEX'`; для MySQL JSON это значение имеет binary charset и восстановление падает с `Cannot create a JSON value from a string with CHARACTER SET 'binary'`;
- maintenance остаётся активным после ошибки recovery и требует ручного CLI-вмешательства;
- фактический `PRIVATE_STORAGE_PATH` и устаревшие параметры окружения недостаточно прозрачно отражаются в Admin.

1.0.6 не выпускается, пока эти сценарии не проходят на реальной Windows / OSPanel установке без ручного редактирования файлов и без CLI-восстановления.

## Что показал разбор зрелых CMS

### WordPress

Полезные для нас принципы:

- отдельная блокировка обновления;
- распаковка во временное место до изменения live-файлов;
- проверка контрольных сумм;
- обновляющий код новой версии подготавливается до основного переключения;
- файлы копируются/заменяются поэлементно, а не переименовывается целиком исполняемое дерево;
- maintenance используется только на ограниченной части операции;
- rollback не должен зависеть от кода, который одновременно заменяется.

### Joomla

Полезные принципы:

- отдельный ранний путь обновления/извлечения до обычной загрузки приложения;
- отдельные update packages и контрольные суммы;
- обновление выполняется специализированным updater-контуром, а не обычным web-runtime;
- важные update-entrypoints должны оставаться совместимыми с исходной установленной версией.

### 1C-Битрикс

По официальной документации и доступным публичным исходникам старых версий полезны:

- система обновлений имеет собственный жизненный цикл и умеет обновлять сам updater;
- загрузка идёт во временные каталоги;
- обновления устанавливаются пошагово;
- ведётся журнал установки и ошибок;
- лицензия и право на обновления отделены от локального файлового механизма.

Код сторонних CMS не копируется. Используются только архитектурные выводы.

## Граница совместимости линии 1.0.6

1.0.6 считается новой опорной точкой системы обновлений. Обязательная совместимость updater с 1.0.5 и более ранними багованными реализациями не входит в критерии выпуска 1.0.6.

Автоматические и ручные проверки обновления строятся от актуальной архитектуры 1.0.6:

- CI поднимает тестовую установку 1.0.6 из текущего дерева;
- подписанные тестовые пакеты имитируют следующий релиз 1.0.7;
- проверяются успешное обновление 1.0.6 → 1.0.7, откат при ошибке миграции, откат при ошибке post-healthcheck и boot recovery;
- реальная Windows / OSPanel приёмка также начинается с чистой 1.0.6 и проверяет обновление на следующий тестовый релиз;
- теги 1.0.4/1.0.5 не используются как обязательные источники для updater CI.

Старый код совместимости может сохраняться там, где он не усложняет и не ослабляет новую архитектуру, но его работоспособность не является release-blocker для 1.0.6.

## Целевая архитектура Notes 1.0.6

### 1. Внешний updater runtime

Destructive apply и recovery никогда не исполняются из дерева приложения.

Перед crossing destructive boundary текущая версия:

1. создаёт каталог `PRIVATE_STORAGE_PATH/updates/runtime/<version-code>/`;
2. копирует туда минимальный доверенный updater runtime;
3. повторно проверяет его SHA-256 по release manifest;
4. запускает отдельный PHP-процесс только из внешнего runtime;
5. live-tree после этого считается данными для замены, а не местом исполнения updater.

Ни `bin`, ни `core`, ни другие заменяемые каталоги не должны быть заняты исполняющим updater-процессом.

### 2. Пофайловое переключение вместо переименования верхних каталогов

Отказаться от обязательного `rename()` целых `bin`, `core`, `modules` и других top-level директорий.

Для каждого release-owned файла заранее строится план:

- новый файл;
- изменённый файл;
- удаляемый файл;
- сохраняемый mutable-файл.

Перед заменой старый файл копируется в проверенный rollback snapshot. Затем новый файл атомарно записывается через временный файл в том же каталоге и `rename(temp, target)`.

Для удаления файл сначала должен существовать в rollback snapshot.

Каталоги создаются отдельно; удаление пустых каталогов выполняется после успешной замены файлов.

### 3. Credential self-healing

При `401` от update API:

1. локальный credential признаётся устаревшим;
2. текущий файл credential атомарно переносится в диагностический quarantine;
3. по уже действующей подписанной лицензии выполняется новый `license-bootstrap`;
4. новый credential сохраняется во внешнем private storage;
5. исходный запрос повторяется ровно один раз.

При `403` автоматическая ротация не выполняется. Пользователь получает конкретную причину: revoked, expired, updates_until или другое серверное ограничение.

### 4. Автоматическое private storage

Пользователь не должен редактировать `.env` для обычного сценария обновления.

Единый `PrivateStorageResolver` должен:

- сначала использовать уже валидный настроенный внешний путь;
- распознавать исторический автоматически созданный sibling-каталог установки;
- при отсутствии пути безопасно создать детерминированный внешний sibling-каталог;
- проверить, что он находится вне web-root/live-tree и доступен для записи;
- возвращать один и тот же путь installer/updater/credentials/state/backups;
- показывать фактический путь в Admin в диагностическом режиме без раскрытия секретов.

### 5. Надёжный backup/restore базы

Формат rollback backup становится типо-зависимым:

- числа сохраняются как числа;
- NULL — как NULL;
- бинарные BLOB/BINARY — как hex literal;
- текстовые типы — как UTF-8 текстовое значение;
- JSON — как валидный UTF-8 JSON, без binary coercion;
- структура таблиц, триггеры и row counts по-прежнему проверяются.

1.0.6 обязана уметь восстановить legacy rollback-dump 1.0.5/старше, где текст и JSON записаны как `X'HEX'`: для JSON выполняется явное `CONVERT(... USING utf8mb4)`.

Сам backup после фиксации SHA не переписывается.

### 6. Recovery без участия пользователя

Первый HTTP-запрос после оборванного обновления:

- читает внешний maintenance marker;
- запускает recovery через внешний runtime;
- не загружает обычное приложение до завершения recovery;
- после `committed` или `rollback_verified` снимает maintenance;
- при невосстановимой ошибке показывает идентификатор транзакции и понятную диагностическую причину.

Обычный пользователь не должен запускать CLI.

### 7. База данных и миграции

До destructive boundary:

- полный preflight;
- проверенный rollback backup;
- проверенный candidate;
- достаточно свободного места;
- корректный PHP/MySQL;
- отсутствие активной другой транзакции.

После переключения файлов:

- миграции;
- exact-version check;
- healthcheck;
- только после этого commit.

При ошибке после destructive boundary выполняется автоматический rollback кода и БД.

## Этапы реализации

### Этап A — зафиксировать воспроизводимые регрессии

- [x] тест устаревшего credential: 401 → новый bootstrap → повтор feed;
- [x] тест Windows file-lock: updater runtime физически вне live-tree;
- [x] тест MySQL JSON/BLOB rollback;
- [x] тест recovery после падения процесса между file-copy и migration;
- [x] тест recovery после failed healthcheck;
- [ ] Windows / OSPanel 5.2.2: реальная проверка 1.0.6 → тестовый 1.0.7.

Автоматические контракты покрывают внешний runtime вне live-tree, типо-зависимый rollback БД, аварийный обрыв после переключения файлов и отдельный сбой post-update healthcheck. Последний ручной пункт этапа A — реальная Windows / OSPanel приёмка новой цепочки 1.0.6 → тестовый 1.0.7.

### Этап B — private storage и credential

- [x] единый resolver private storage;
- [x] автоматическое переиспользование legacy sibling path;
- [x] self-healing credential;
- [x] точные серверные ошибки вместо общего 401/403 текста.

HTTP 401 остаётся сигналом для однократного автоматического refresh credential. Для HTTP 403 сервер возвращает только разрешённый код причины без текста внутренних исключений, а клиент различает отзыв лицензии, истечение updates_until, ограничение версии и ошибку проверки лицензии.

### Этап C — внешний runtime

- [x] минимальный внешний updater runtime;
- [x] проверка состава и SHA;
- [x] запуск destructive apply/recovery только из внешнего runtime;
- [x] отсутствие runtime-зависимости от заменяемого `bin/core/modules`.

Этап C закрыт: runtime готовится во внешнем private storage, повторно проверяется по manifest/SHA-256, destructive apply и boot recovery запускаются через внешний entrypoint, а live-tree после пересечения destructive boundary используется только как изменяемые данные.

### Этап D — пофайловый apply/rollback

- [x] immutable file plan;
- [x] backup только release-owned файлов плюс DB;
- [x] atomic same-directory file replacement;
- [x] корректная обработка новых/удалённых файлов;
- [x] Windows locks не требуют переименования каталогов.

Этап D реализован пофайлово: apply фиксирует хэши исходного live-tree, candidate и детерминированного списка операций, повторно сверяет их до первой записи, удаляет obsolete-файлы от самых глубоких путей и заменяет новые/изменённые файлы через временный файл в том же каталоге. Rollback независимо восстанавливает точный release-owned набор из проверенного backup. Переименование live-каталогов верхнего уровня больше не используется ни для apply, ни для rollback.

### Этап E — backup/restore БД

- [x] type-aware SQL dump;
- [x] JSON/BLOB/TEXT round-trip;
- [x] compatibility restore старого mysql-sql-v1;
- [ ] MySQL 8 и поддерживаемая MariaDB в тестах.

MySQL 8.4 уже входит в обязательный backup gate. Для MariaDB 10.11 добавлен отдельный обязательный job с тем же новым и legacy rollback-контрактом; пункт считается окончательно закрытым после его зелёного прогона в CI.

### Этап F — recovery и UX

- [x] автоматический boot recovery;
- [x] понятный прогресс в Admin;
- [x] пользователь не видит credential/path/transaction в обычном happy path;
- [x] maintenance не может остаться навечно без диагностического статуса;
- [x] CLI остаётся только аварийным операторским способом.

При запуске установки Admin показывает последовательность фактических этапов updater и блокирует повторную отправку формы; фиктивные проценты и небезопасный публичный status-endpoint не используются. При неуспешном boot recovery ранний HTTP-барьер остаётся fail-closed, но возвращает безопасный диагностический код и ID транзакции в HTML/JSON. В успешном сценарии служебный ID транзакции пользователю не показывается.

## Защита CI от очереди устаревших PR-запусков

Для PR-проверок добавлен служебный workflow `.github/workflows/pr-ci-stale-run-cleanup.yml`. При новом коммите в PR он на отдельном Windows-runner отменяет только запуски этого же PR со статусом `queued` или `in_progress`, если они относятся к предыдущему SHA. Проверки текущего SHA, другие PR, `master`, `1.0`, push/tag/release-запуски не затрагиваются.

Очистка использует штатный `GITHUB_TOKEN` с правом `actions: write`, не добавляет внешних runtime-зависимостей и нужна только для CI. Это предотвращает накопление полного набора проверок после серии коротких коммитов и не меняет релизные критерии updater.

## Критерии готовности 1.0.6

1. Чистая установка работает без ручной настройки private storage.
2. Установка с историческим private storage автоматически его переиспользует.
3. Устаревший updater credential чинится автоматически по действующей лицензии.
4. Обновление 1.0.6 → следующий подписанный релиз одной кнопкой проходит на Windows / OSPanel 5.2.2.
5. Обновление 1.0.6 → тестовый 1.0.7 одной кнопкой проходит в Linux CI.
6. Никакой destructive updater-процесс не исполняется из live-tree.
7. JSON/BLOB/TEXT rollback проходит с точным сравнением данных.
8. Ошибка миграции автоматически возвращает код и БД.
9. Ошибка healthcheck автоматически возвращает код и БД.
10. Принудительное завершение PHP-процесса восстанавливается следующим HTTP-запросом.
11. После любой успешной операции maintenance снят.
12. Пользователю не нужны PowerShell/SSH/ручной ZIP/.env/SQL/transaction ID.
13. Все новые тесты входят в обязательный release gate.
14. До публикации stable 1.0.6 фиксируется реальная OSPanel-приёмка новой архитектуры на цепочке 1.0.6 → тестовый 1.0.7.
