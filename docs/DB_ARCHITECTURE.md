# Архитектура базы данных

## Источник истины

Каноническая схема новой установки **не строится replay всех исторических миграций**.

`Core\DatabaseOwnership` собирает fresh-схему из:

- core-owned schema;
- schema, объявленных установленными модулями в `module.json`.

`install.php` применяет именно этот набор.

## Существующие установки

`database/migrations/` содержит compatibility-upgrade скрипты для установок, созданных предыдущими версиями.

`bin/migrate.php`:

- применяет только ещё не применённые upgrade-скрипты;
- хранит filename и SHA-256 в `schema_migrations`;
- не позволяет молча изменить уже применённую миграцию;
- поддерживает `--status` и `--dry-run`.

История строк `schema_migrations` не является частью runtime-контракта приложения.

## Правило изменения схемы

Для новой функции:

1. сначала изменяется каноническая схема владельца данных;
2. если уже опубликованной установке нужен `ALTER`/backfill/reconciliation, добавляется новый compatibility-upgrade;
3. ранее применённый SQL не переписывается;
4. fresh install и upgrade должны приводить к одному фактическому контракту данных.

## Владение данными

Core владеет только платформенными таблицами: identity, access control, audit, settings, module lifecycle и другими общими контрактами.

Прикладной модуль владеет собственными таблицами и объявляет их в manifest. Другой модуль не должен напрямую читать или изменять их как интеграционный API.

## Доступ модулей к БД через ядро (1.2)

Модуль отвечает за бизнес-правила и собственную схему, но не за создание
соединения, диагностику SQL и реализацию общих механизмов транзакций.

- Для обычных выборок и моделей применяется `Core\ORM` либо методы
  `Core\DatabaseManager::fetchOne`, `fetchAll`, `fetchValue`.
- Параметризованные изменения проходят через `DatabaseManager::execute`.
- Для повторно используемых выражений, потокового чтения, пакетной записи
  и блокировок `FOR UPDATE` применяется `DatabaseManager::prepare`.
  Выражение отслеживается ядром; оно использует текущее соединение и не
  завершает транзакцию самостоятельно.
- Транзакции запускает `beginTransaction`, завершает `endTransaction`.
  Нельзя переоткрывать соединение во время одной изменяющей команды.
- После вставки идентификатор читается через `DatabaseManager::lastInsertId`,
  а не через выдачу низкоуровневого соединения.
- HTTP-контроллеры передают сервисам `DatabaseManager::getInstance()`,
  а не `getPdo()`. Предметные SQL-запросы остаются в модулях, но
  выполняются через библиотеку ядра; добавление третьей ORM не допускается.

Режим `DatabaseManager::forConnection(PDO)` используется в изолированных
тестах и переходных контрактах, где уже создано соединение с собственной
схемой и префиксом. Он **не** подменяет глобальную базу проекта, **не**
создаёт новое соединение и не переподключает его после ошибки. Совместимые
конструкторы существующих сервисов временно принимают PDO для старых тестов,
сразу преобразуя его в менеджер ядра; в рабочем коде передаётся менеджер.

После перехода FileSpace-сервисов и Tasks также устранены известные прямые
обращения `getPdo` из Calendar, Messenger и Admin. Регрессионный
[контракт границы БД](../tests/integration/module_database_boundary_12.php)
проверяет PHP-файлы всех модулей; исходный перечень разрешённых
исключений хранится в
[базе исключений](../tests/integration/module_database_legacy_12.json).
Добавление обхода ядра требует явного архитектурного изменения.

Не все формы сырого SQL запрещены: выражение может быть сложным и
принадлежать бизнес-логике модуля. **Запрещён обход инфраструктуры
ядра при его выполнении**. Специализированные возможности сначала
добавляются в библиотеку ядра, затем используются модулями.

## Границы данных модулей и интерфейсы возможностей

Правила `MODULE_PLATFORM.md` и `MODULE_DEVELOPMENT.md` действуют
независимо от способа выполнения SQL. Даже корректный вызов
`DatabaseManager::fetchOne` нарушает архитектуру, если читает
внутреннюю таблицу соседнего модуля.

В 1.2 Admin обращается к объектам соседних модулей через:
- `AccountDeactivationGuard` для проверки владения общими группами Messenger
  и досками Tasks;
- `AccountAvatarCleanup` для очистки аватара средствами Profile;
- `ProfileCustomFields` для чтения и изменения полей, которыми владеет Profile.

Интерфейсы определяются ядром, а реализации остаются в модулях. Нельзя
подключать их реализацию из другого модуля напрямую. Когда необходимые
возможности Messenger или Tasks отсутствуют, опасная операция деактивации
либо постановки аккаунта на удаление отклоняется: отсутствие модуля
не подтверждает отсутствие принадлежащих ему данных. Пользовательский
интерфейс должен объяснять, какой модуль требуется активировать.

[Проверка владения таблицами](../tests/integration/module_schema_ownership_contract_12.php)
сверяет SQL-литералы со списками владельцев в `module.json`, проверяет
прямые файловые зависимости и выполняется в проверках модульной платформы.
Она не анализирует произвольный динамически собранный SQL, поэтому результат
«0 найденных нарушений» не является исчерпывающим аудитом всего кода.
Проверки контрактов, выключенных модулей и ручное ревью остаются обязательными.

### Фоновая проверка владельцев при обезличивании (1.2)

`RetentionService` не обращается к таблицам других модулей при проверке
возможности обезличить аккаунт. `Core\BackgroundAccountRetention` получает
из `ModuleRegistry::discover()` проверенные manifest всех присутствующих
пакетов, **включая disabled, unlicensed и несовместимые с runtime**.
Пользовательский `runtime.php`, маршруты и интерфейсы модулей не запускаются.

Каждый модуль объявляет в `module.json` фоновые обязательства:
- `"background": {"account_purge_guard": "none"}` — владелец подтверждает,
  что у него нет объектов, препятствующих обезличиванию;
- `"background": {"account_purge_guard": "background/account-purge.php"}`
  — ядро загружает **только** проверку, которая реализует
  `Core\BackgroundAccountRetentionGuard` и использует
  `Core\DatabaseManager`.

Для Messenger и Tasks SQL остался внутри модульных сервисов владения,
используемых как активными возможностями, так и фоновыми проверками.
При ошибке SQL, отсутствующем поставщике, повреждённом manifest,
потерянной схеме или ранее зарегистрированном, но отсутствующем на диске
модуле операция закрывается отказом.

Проверка владения повторяется под блокировкой строки пользователя до
очистки личного аватара и изменения регистрационных данных. Удаление
учётной записи происходит только после снятия всех ограничений.

Новый контракт касается именно **обезличивания аккаунтов**.
Общая очистка устаревших данных по модулям в `RetentionService` — отдельная
историческая область; она не объявляется автоматически приведённой
к полной модульной изоляции.


## Отключение модуля

`disabled` и `unlicensed` не означают удаление таблиц. Данные сохраняются для повторного включения и recovery.

Физическое удаление данных — отдельный явный lifecycle-шаг пакета и не должно происходить как побочный эффект выключения.

## Проверки

Релизные проверки должны подтверждать:

- fresh install на пустой БД;
- upgrade с поддерживаемой предыдущей версии;
- идемпотентность повторного запуска;
- checksum-защиту миграций;
- rollback/recovery updater;
- одинаковый конечный schema contract.

Историческое обоснование решения 0.12 сохранено в [DB_ARCHITECTURE_AUDIT_0.12.md](DB_ARCHITECTURE_AUDIT_0.12.md).
