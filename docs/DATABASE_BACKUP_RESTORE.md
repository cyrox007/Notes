# Резервная копия и восстановление базы данных

## Что произошло в 1.0.14

В таблице `notes` использовались три descending-индекса MySQL 8:

- `idx_user_notes (..., created_note DESC)`;
- `idx_updated_notes (..., updated_note DESC)`;
- `idx_notes_profile_public (..., updated_note DESC)`.

Некоторые старые версии phpMyAdmin при экспорте такой структуры формируют повреждённый SQL и теряют имя последней колонки:

```sql
ADD KEY `idx_user_notes` (`user_id`, `is_deleted`, DESC)
ADD KEY `idx_updated_notes` (`user_id`, DESC)
ADD KEY `idx_notes_profile_public` (`user_id`, `is_profile_public`, `is_deleted`, DESC)
```

При импорте MySQL воспринимает `DESC` как имя столбца и останавливается с ошибкой `#1072 Key column 'DESC' doesn't exist in table`.

Это повреждение SQL-экспорта, а не потеря пользовательских строк в самом дампе.

## Исправление в 1.0.15

Начиная с 1.0.15 эти три индекса пересоздаются как обычные B-tree без явного `DESC`.

Для запросов Notes это не меняет результат: MySQL/InnoDB может читать B-tree в обратном порядке для сортировки по убыванию. Зато структура корректно экспортируется старыми phpMyAdmin.

Миграция 1.0.14 → 1.0.15 выполняет замену индексов автоматически. Свежая установка 1.0.15 сразу создаёт совместимую схему.

## Как восстановить уже созданный повреждённый дамп 1.0.14

Исходный SQL-файл не нужно выбрасывать и не нужно переустанавливать Workspace.

В 1.0.15 есть безопасный исправляющий инструмент:

```bash
php bin/repair_phpmyadmin_dump.php --input=backup.sql --output=backup-fixed.sql
```

Инструмент:

- никогда не перезаписывает исходный файл;
- исправляет только три известные повреждённые определения индексов Notes;
- не меняет `INSERT` и пользовательские данные;
- создаёт отдельный `backup-fixed.sql`.

После этого импортируйте `backup-fixed.sql` обычным способом.

Если PHP CLI недоступен, те же три определения можно исправить вручную:

```sql
ADD KEY `idx_user_notes` (`user_id`, `is_deleted`, `created_note`)
ADD KEY `idx_updated_notes` (`user_id`, `updated_note`)
ADD KEY `idx_notes_profile_public` (`user_id`, `is_profile_public`, `is_deleted`, `updated_note`)
```

После успешного импорта выполните штатный healthcheck Workspace и убедитесь, что схема БД готова.

## Практика резервного копирования

Перед удалением или заменой данных сохраняйте исходный SQL-файл отдельно и не редактируйте его на месте. Для восстановления используйте копию дампа.

Rollback-резервная копия, которую updater создаёт во время обновления, предназначена для автоматического восстановления транзакции обновления. Она не заменяет отдельный пользовательский backup перед ручными операциями с БД.
