# Устойчивость обновлятора: проверенное состояние на 4 октября 2026

## Исходное состояние

Работа ведётся в `fix/updater-resilience-20261004`, от кандидата
`fix/1.0.15-post-release-regressions` (`c52aaea8386520f7910fd152bef0272d41b22f30`).
Опубликованная 1.0.14 и её артефакты не изменяются.

Проверены доступная история обсуждений, предыдущий аудит от 4 октября,
исходники, локальные и удалённые ветки, открытые запросы на слияние и журнал
неуспешного сквозного перехода. Полнота выгрузки всех чатов не подтверждена.

Основная ветка: `fa5a32c43a06320b8e0906ee387d1b21bf2a0549`. Открыты #337
(кандидат 1.0.15), #336 и #333 (фиксация публикации 1.0.14), #334 (план
уведомлений 1.1). Ветка `dev` в полученных удалённых ссылках отсутствует.

Старая проверка GitHub `37150871592`, задание `111284326362`, показывала
`code_switched → migration_failed → rollback_verified` без первичного исключения.
Повтор с сервисным журналом (`37213301806`, задание `111468648704`) установил
причину: SQL #1 в `20261002_user_lifecycle.sql`, SQLSTATE `42000`, MySQL `1044`.
Миграция создаёт процедуру, а доступные права хостинга не включают CREATE ROUTINE.

Неопубликованная миграция 1.0.15 переписана на SET / PREPARE / EXECUTE /
DEALLOCATE. Все проверки совместимости выполнены перед первым ALTER;
несовместимая схема останавливает выполнение. Опубликованные старые SQL-файлы
не изменены. Сам факт успешного отката не считается успешным обновлением.

## Внесённые изменения

- Восстановление БД разбирает дамп потоком, без загрузки всей базы и массива SQL
  в память. Сохранены SHA-256, размер, переносимость триггеров и совместимость
  старого формата JSON.
- Формат дампа проверяется при подтверждении резервной точки, до изменения
  рабочего кода, и повторно перед удалением таблиц. Пустой, оборванный дамп,
  неверный UTF-8 и незавершённый разделитель отвергаются заранее.
- Одно SQL-выражение ограничено 8 МиБ. Это предел выражения, а не базы.
  Исправленный исполнитель отклоняет более крупное выражение при подготовке
  резервной точки. Проверка формата не является проверкой всей семантики SQL
  сервером БД. Первая подготовка на исходной опубликованной 1.0.14 ещё
  выполняется её старым кодом; эта новая проверка не появляется там заранее.
- Ошибки миграции в браузерном и консольном исполнителях содержат имя файла,
  номер выражения, SQLSTATE, код MySQL и SHA-256 SQL. Данные INSERT и текст
  внешней ошибки с потенциальными пользовательскими значениями не включаются
  в новое сообщение. Сервисное событие применения содержит исходную и целевую
  версии.
- Доставка фиксирует начало и исход попытки до появления транзакции. Этапы:
  предварительная проверка, список релизов, описание релиза, загрузка и проверка
  подписи, загрузка и проверка пакета, подготовка пакета. Сохраняются ID,
  безопасное имя сервера, HTTP-код, длительность и тип ошибки. URL-параметры,
  заголовки и текст внешней ошибки не сохраняются. Недоступность сервисного
  журнала не скрывает первичный отказ; при ненастроенном хранилище запись
  попытки не гарантируется.
- Браузер прекращает повторы при `retryable=false`, включая HTTP 403 от WAF.
  Для временных ошибок сохраняются восемь повторов; ожидание HTTP ограничено
  90 секундами. Потеря ответа на начало операции не вызывает автоматический
  повтор запуска. Серверные блокировки и журнал остаются источником истины.
- Подготовленный удалённый пакет сохраняется в привязке формы и используется
  при установке с повторной штатной проверкой подписи и хэша.
- Уведомление показывает код диагностики отката. Сквозной тест больше не
  утверждает, что commit состоялся, когда целевая версия не подтверждена.

## Выполненные проверки

Локально использован PHP 8.3.6. Прошли:

- потоковый разбор дампа около 137 МБ при `memory_limit=32M`, включая триггер;
- отказ для оборванного SQL, неверного UTF-8, пустого дампа, слишком большого
  выражения и незавершённого переключения разделителя;
- поведение браузера при постоянных HTTP 400/403/409/422/500,
  HTML-странице WAF, временном HTTP 409/503 и разрыве сети;
- сохранение раннего отказа HTTP 403 с общим ID и без тестового секрета;
- подписанная удалённая доставка, независимый внешний исполнитель,
  работа без запуска процессов, раннее восстановление до резервной точки,
  готовность конфигурации, инварианты восстановления и контракты интерфейса;
- синтаксис изменённых PHP/JS и проверка пробелов в изменениях.

Полный локальный прогон БД не состоялся: сервер MariaDB подготовлен,
но среда запрещает соединение с ним. Этот результат не является проверкой
реального восстановления MySQL. PHP 8.1 и MySQL целевого хостинга локально
не проверены.

## Проверки GitHub

Для этой ветки запущены профильные проверки:

1. Точный переход опубликованной 1.0.14 → кандидата 1.0.15: отдельно без
   журнала миграций и с журналом. Права исключают CREATE VIEW / SHOW VIEW;
   процессы и `opcache_reset` запрещены; PHP ограничен 256 МБ / 80 секундами.
   При отказе выводится сервисный журнал с первичной причиной.
2. Существующая матрица резервного копирования и восстановления MySQL/MariaDB.
   Добавлен сценарий: корректный хэш оборванного дампа не разрешает удалить
   рабочие таблицы.
3. Проверки памяти, HTTP-повторов, ранней диагностики и независимого
   восстановления на PHP 8.1. На MySQL с ограниченными правами отдельно
   проверены отсутствующие, частично добавленные и полностью добавленные
   поля жизненного цикла, повторное выполнение и несовместимый тип поля.
4. Три аварийных браузерных сценария exact v1.0.14 → 1.0.15: отказ SQL после
   создания таблицы и строки, закрытие клиента после переключения кода и
   после миграций. Проверяются исходная версия, `rollback_verified`, отсутствие
   maintenance, возврат схемы и контрольных данных.
5. Настоящий SIGKILL отдельного PHP посреди SQL-восстановления: именованная
   блокировка останавливает поток после первой восстановленной строки;
   после принудительной смерти новый процесс повторяет откат из того же
   проверенного дампа. Проверяются JSON, BLOB, отсутствие дублей аудита,
   удаление таблицы неудачной миграции и работоспособность триггера.
   Запуск процессов требуется только этому испытанию; рабочий web-updater
   проверен отдельно с запрещёнными функциями запуска.

## Что ещё блокирует готовность

1. Разбить длинные операции копирования, распаковки, переключения и
   восстановления файлов на сохраняемые ограниченные шаги. Текущая смена
   HTTP-фаз сама по себе не ограничивает время всех внутренних операций.
2. Определить подтверждённый предел времени согласованного резервирования и
   восстановления БД. Потоковый SQL устраняет рост памяти с размером дампа,
   но не ограничивает полное время отката и тяжёлого ALTER TABLE.
3. Подтвердить проверку объектов, прав и ресурсов до опасной границы,
   долговечное отображение исхода после перезагрузки и путь установки
   исправленного исполнителя на уже опубликованную 1.0.14.
4. Выполнить аварийные сценарии на копии того же хостинга: обрыв запроса,
   закрытие вкладки, смерть PHP, два администратора, недостаток места,
   OPcache и WAF. Отдельно проверить реальный подписанный HTTPS-канал.

Доказан успешный переход на малой контрольной установке с ограничениями
хостинга, восстановление после отказа/закрытия клиента и повтор нового
SQL-восстановителя после SIGKILL. Это не доказывает время отката базы
произвольного размера, работу WAF реального сервера или завершение тяжёлого
ALTER TABLE в пределах 80 секунд.
Стабильный релиз и рабочая установка не обновлялись.
