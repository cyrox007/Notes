## Назначение релиза

`1.0.14` — исправляющий и визуально финализирующий выпуск линии 1.0 после первого эксплуатационного обновления опубликованной установки 1.0.12.

Во время попытки перехода `1.0.12 → 1.0.13` транзакционный updater безопасно вернул предыдущую рабочую версию, но после rollback установка временно оставалась на ранней странице восстановления с сообщением, что обновление или recovery ещё выполняется. Одновременно аудит реального shared-hosting пути выявил отсутствие явной инвалидации OPcache при пофайловом переключении кода.

Пользовательские данные при наблюдавшемся сбое не были потеряны: rollback вернул рабочую 1.0.12. Разбор эксплуатационного архива показал первичную причину: установка 1.0.12 не имела журнала `schema_migrations`, поэтому updater ошибочно считал 26 уже вошедших в эту версию миграций неприменёнными. На ограниченном хостинге повторный запуск старой миграции упал на запрете MySQL `ALTER ROUTINE`.

1.0.14 инициализирует журнал миграций из подтверждённого baseline опубликованной исходной версии. Старые миграции 1.0.12/1.0.13 не переписываются и не запускаются повторно только ради создания журнала.

## Исправление восстановления

Web-updater использует короткоживущий continuation lease длительностью 180 секунд, чтобы обычный запрос не перехватил живую транзакцию между последовательными HTTP-шагами.

До 1.0.14 lease проверялся раньше итогового состояния журнала. Поэтому даже если журнал уже содержал `rollback_verified` или `committed`, ранний recovery мог ждать окончания lease и показывать защитную HTTP 503-страницу.

В 1.0.14:

- журнал транзакции проверяется до решения о том, что web-операция ещё выполняется;
- `rollback_verified` и `committed` считаются доказанными terminal-state и завершаются немедленно;
- если реальный шаг ещё держит coordinator-lock, recovery по-прежнему не вмешивается в него;
- после успешного автоматического recovery continuation-token удаляется;
- незавершённые нетерминальные транзакции по-прежнему защищаются активным lease.

Таким образом, активный браузерный lease не может удерживать установку в maintenance после уже подтверждённого rollback.

## Брендовый интерфейс

1.0.14 закрепляет новый визуальный язык Workspace Organizer по утверждённым светлому и тёмному бренд-референсам.

В релиз входят:

- фирменный векторный знак и логотип Workspace Organizer вместо старого текстового `Notes / N`;
- единая палитра светлой и тёмной темы с глубоким синим контуром, голубым/синим градиентом и фиолетовым акцентом;
- тёмный фирменный sidebar и полупрозрачная верхняя панель;
- обновлённая главная страница и экран входа;
- единые радиусы, тени, карточки и состояния наведения;
- постоянные цветовые роли модулей: Notes — синий, Tasks — зелёный, Files — оранжевый, Messenger — фиолетовый, Profile — голубой, Admin — бирюзовый;
- нижняя информационная строка при коротком содержимом прижимается к нижнему краю окна без перекрытия страницы;
- аватар публичного профиля использует ту же рамку и внешний контур, что и основной профиль.

Редизайн не меняет маршруты, RBAC, состав модулей или формат пользовательских данных.

## OPcache на PHP-FPM

Пофайловая замена кода ранее атомарно меняла файлы на диске, но не инвалидировала OPcache.

На средах без OPcache это незаметно. На PHP-FPM/shared hosting следующий HTTP-шаг мог попасть в worker с закэшированным байткодом предыдущей версии, хотя файлы на диске уже относились к новой версии.

Начиная с 1.0.14:

- после замены release-owned файла очищается stat-cache;
- при доступном `opcache_invalidate()` путь инвалидируется принудительно;
- перед удалением release-owned файла его старый байткод также инвалидируется;
- тот же механизм используется при rollback, потому что восстановление выполняется через общий `UpdateFileMutator`.

OPcache не отключается глобально и не является обязательной PHP-возможностью; исправление работает условно только когда функция доступна.

## Диагностика автоматического отката

До 1.0.14 интерфейс показывал только общий итог «предыдущая рабочая версия автоматически восстановлена», не сохраняя оператору безопасную первичную причину.

Теперь rollback фиксирует нормализованный код причины, например категорию ошибки миграции или postcheck. После успешного восстановления web-updater возвращает поле:

```text
diagnostic_code
```

Admin показывает этот код рядом с сообщением об откате. Полные пути, секреты, токены и необработанный внутренний stack trace в пользовательский интерфейс не передаются.

## Сервисная диагностика

В состав 1.0.14 входит отдельный сервисный JSONL-журнал updater/recovery/runtime во внешнем приватном хранилище. Суперадминистратор может создать в Admin **одноразовый диагностический ZIP** и передать доступ поддержке.

ZIP фиксируется в момент создания, действует 15 минут, гасится после первого скачивания и не даёт постоянного удалённого доступа. Он содержит `manifest.json`, `hosting-profile.json`, health/maintenance, последние сервисные события, updater-журналы и security-сводку.

`hosting-profile.json` сохраняет только разрешённые параметры окружения: PHP/SAPI, лимиты, `disable_functions`, OPcache, файловые возможности и карту объявленных MySQL-привилегий, включая `CREATE ROUTINE`/`ALTER ROUTINE`. Полный `phpinfo()`, физические пути и DB identity не выгружаются.

Пакет не содержит `.env`, дамп БД, пользовательский контент, пароли, лицензионные токены и ключи. Секретные поля очищаются до записи.

Endpoint выдачи расположен до проверки схемы БД и общего maintenance-barrier, поэтому заранее созданный пакет можно получить даже после перехода приложения в 503/recovery. Одноразовый HTTPS GET с `Authorization: Bearer <одноразовый-токен>` остаётся резервным способом передачи пакета.

Начиная с 1.0.14 суперадминистратор также может нажать **«Отправить диагностику разработчику»**. Notes отправляет тот же обезличенный ZIP только в уже активированный control plane по `<UPDATE_BASE_URL>/diagnostics`, используя существующие Installation ID и updater credential. Произвольный адрес назначения не принимается. После успешного приёма сервер возвращает `diagnostic_id`, а отчёт появляется во входящих JSInteractive с привязкой к установке, лицензии, клиенту и версии Notes.

## Проверяемый путь обновления

Опубликованные 1.0.12 и 1.0.13 имеют ранний web-only updater, который после переключения файлов продолжает первый post-switch шаг старым внутрипроцессным runtime. Этот runtime ещё не умеет инициализировать `schema_migrations` из baseline и не инвалидирует заменённые PHP-файлы в OPcache. Исправить уже выпущенные байты этих версий только содержимым 1.0.14 невозможно: целевой runtime начинает надёжно действовать слишком поздно.

Поэтому поддерживаемый переход к 1.0.14 состоит из двух частей:

`1.0.12/1.0.13 → одноразовый совместимый updater-handoff → штатный подписанный web-updater → 1.0.14`.

Одноразовый handoff выполняется из доверенного exact-пакета 1.0.14 командой:

```bash
php tools/release/bootstrap-1.0.12-updater.php --yes --root=/path/to/workspace
```

Мост меняет только updater-контур. Он не меняет `core/Version.php`, версию приложения и БД; после его успешного завершения установка 1.0.14 выполняется обычной кнопкой **Admin → Updates**. Промежуточная установка 1.0.13 и ручной запуск SQL не требуются.

Сквозная релизная матрица обязана отдельно проверять exact 1.0.12 и exact 1.0.13: после handoff основное обновление выполняется в web-only режиме PHP 8.1 с отключёнными process API и ограниченными правами MySQL.

При регистрации 1.0.14 во внешнем реестре обновлений:

```text
min_source_version_code = 10012
```

Это позволяет опубликованной 1.0.12 получить исправляющий выпуск напрямую.

Последняя опубликованная stable `1.0.13` также обязана проходить тот же web-only upgrade-path до 1.0.14 на PHP 8.1.

## Регрессионные проверки

Добавлены отдельные контракты:

- `rollback_verified` при ещё активном web-lease должен немедленно запускать terminal recovery;
- maintenance после terminal recovery должен быть снят;
- устаревший continuation-token должен быть удалён;
- второй живой updater с занятым coordinator-lock по-прежнему нельзя перехватывать;
- пофайловый mutator обязан содержать явную инвалидацию OPcache;
- Admin обязан показывать безопасный `diagnostic_code` после автоматического rollback.

Полный exact-head CI выполняется до снятия draft с PR релиза.

## Совместимость

Требования не меняются:

- PHP 8.1+;
- MySQL 8.0+ или MariaDB 10.5+;
- Windows / OSPanel и Linux/shared hosting остаются поддерживаемыми сценариями согласно действующей матрице;
- одноразовый переход с опубликованных 1.0.12/1.0.13 требует PHP CLI только для совместимого updater-handoff; само подписанное обновление после handoff остаётся web-only и не требует process API;
- Long Poll остаётся полноценным транспортом Messenger без отдельного WebSocket-процесса.

## Что не меняется

1.0.14 не добавляет новый прикладной модуль и не меняет формат пользовательских данных. Пользовательский интерфейс и бренд обновлены, но маршруты, права доступа, лицензионные и модульные ограничения 1.0.13 не ослабляются.

Опубликованный тег `v1.0.13` и его артефакты остаются неизменяемыми; 1.0.13 снята с публичной ленты обновлений, но путь 1.0.13 → 1.0.14 остаётся поддерживаемым.
