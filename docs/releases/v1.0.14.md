# Workspace Organizer 1.0.14

Дата кандидата: 30 сентября 2026  
Статус: исправляющий релиз-кандидат  
Код версии: `10014`

## Назначение релиза

`1.0.14` — исправляющий выпуск линии 1.0 после первого эксплуатационного обновления опубликованной установки 1.0.12.

Во время попытки перехода `1.0.12 → 1.0.13` транзакционный updater безопасно вернул предыдущую рабочую версию, но после rollback установка временно оставалась на ранней странице восстановления с сообщением, что обновление или recovery ещё выполняется. Одновременно аудит реального shared-hosting пути выявил отсутствие явной инвалидации OPcache при пофайловом переключении кода.

Пользовательские данные при наблюдавшемся сбое не были потеряны: rollback вернул рабочую 1.0.12. Исправление направлено на завершение служебного состояния updater и устойчивость PHP-FPM/shared hosting.

## Исправление восстановления

Web-updater использует короткоживущий continuation lease длительностью 180 секунд, чтобы обычный запрос не перехватил живую транзакцию между последовательными HTTP-шагами.

До 1.0.14 lease проверялся раньше итогового состояния журнала. Поэтому даже если журнал уже содержал `rollback_verified` или `committed`, ранний recovery мог ждать окончания lease и показывать защитную HTTP 503-страницу.

В 1.0.14:

- журнал транзакции проверяется до решения о том, что web-операция ещё выполняется;
- `rollback_verified` и `committed` считаются доказанными terminal-state и завершаются немедленно;
- если реальный шаг ещё держит coordinator-lock, recovery по-прежнему не вмешивается в него;
- после успешного автоматического recovery continuation-token удаляется;
- незавершённые нетерминальные транзакции по-прежнему защищаются активным lease.

Таким образом, активный браузерный lease не может удерживать установку в maintenance после уже подтверждённого rollback.

## OPcache на PHP-FPM

Пофайловая замена кода ранее атомарно меняла файлы на диске, но не инвалидировала OPcache.

На средах без OPcache это незаметно. На PHP-FPM/shared hosting следующий HTTP-шаг мог попасть в worker с закэшированным байткодом предыдущей версии, хотя файлы на диске уже относились к новой версии.

Начиная с 1.0.14:

- после замены release-owned файла очищается stat-cache;
- при доступном `opcache_invalidate()` путь инвалидируется принудительно;
- перед удалением release-owned файла его старый байткод также инвалидируется;
- тот же механизм используется при rollback, потому что восстановление выполняется через общий `UpdateFileMutator`.

OPcache не отключается глобально и не является обязательной PHP-возможностью; исправление работает условно только когда функция доступна.

## Диагностика автоматического отката

До 1.0.14 интерфейс показывал только общий итог «предыдущая рабочая версия автоматически восстановлена», не сохраняя оператору безопасную первичную причину.

Теперь rollback фиксирует нормализованный код причины, например категорию ошибки миграции или postcheck. После успешного восстановления web-updater возвращает поле:

```text
diagnostic_code
```

Admin показывает этот код рядом с сообщением об откате. Полные пути, секреты, токены и необработанный внутренний stack trace в пользовательский интерфейс не передаются.

## Проверяемый путь обновления

Для установок, оставшихся на 1.0.12 после автоматического rollback, основной путь:

`1.0.12 → встроенный подписанный updater → 1.0.14`.

Промежуточная установка 1.0.13 не требуется.

При регистрации 1.0.14 во внешнем реестре обновлений:

```text
min_source_version_code = 10012
```

Это позволяет опубликованной 1.0.12 получить исправляющий выпуск напрямую.

Установки 1.0.13 также могут штатно обновляться до 1.0.14.

## Регрессионные проверки

Добавлены отдельные контракты:

- `rollback_verified` при ещё активном web-lease должен немедленно запускать terminal recovery;
- maintenance после terminal recovery должен быть снят;
- устаревший continuation-token должен быть удалён;
- второй живой updater с занятым coordinator-lock по-прежнему нельзя перехватывать;
- пофайловый mutator обязан содержать явную инвалидацию OPcache;
- Admin обязан показывать безопасный `diagnostic_code` после автоматического rollback.

Полный exact-head CI выполняется до снятия draft с PR релиза.

## Совместимость

Требования не меняются:

- PHP 8.1+;
- MySQL 8.0+ или MariaDB 10.5+;
- Windows / OSPanel и Linux/shared hosting остаются поддерживаемыми сценариями согласно действующей матрице;
- PHP CLI и дочерние процессы не требуются для совместимого web-режима updater;
- Long Poll остаётся полноценным транспортом Messenger без отдельного WebSocket-процесса.

## Что не меняется

1.0.14 не добавляет новый пользовательский функционал, не меняет формат пользовательских данных и не ослабляет лицензионные или модульные ограничения 1.0.13.

Опубликованный тег `v1.0.13` и его артефакты остаются неизменяемыми.
