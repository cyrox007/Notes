# Workspace Organizer 1.0.0

Дата релиза: 16 сентября 2026

`1.0.0` — первый stable-релиз Workspace Organizer. Он фиксирует runtime, licensing и update/recovery contracts, которые в beta-линии оставались незавершёнными platform blockers.

## Stable runtime

- PHP runtime больше не зависит от Composer `vendor/`: `.env` загружается внутренним `Core\Environment`, UI рендерится native PHP renderer, WebSocket runtime реализован внутри проекта поверх `stream_socket_server()` / `stream_select()` и RFC6455.
- Hosting bundle запускается без `vendor/` и не содержит vendor signing tools или private signing material.
- HTTP Router/Request boundary усилен bounded strict JSON parsing, fail-closed malformed requests, duplicate-route validation, typed params и корректным `405 Allow`.

## Installation-bound licensing

- Каждая установка имеет стабильный `installation_id`.
- Лицензия — offline Ed25519 token, привязанный к установке.
- Admin activation и recovery-safe read-only enforcement входят в runtime contract.
- License signing private key никогда не должен находиться в репозитории, CI, customer bundle или на customer installation.

## Signed updater and recovery

Полный update pipeline 1.0:

`signed feed -> Ed25519 manifest verification -> SHA-256/package compatibility checks -> ZIP audit -> external immutable staging -> maintenance -> durable transaction journal -> verified code+MySQL rollback backup -> verified external release candidate -> data-only migration preflight -> live mutation boundary -> controlled code switch -> migrations -> post-update health/version/schema verification -> commit -> maintenance off`

Ключевые гарантии:

- package не распаковывается поверх live tree;
- candidate и rollback backup повторно проверяются перед destructive boundary;
- pre-live migration validation читает только canonical JSON manifest + SQL + current DB ledger и не исполняет PHP из candidate;
- после `live_mutation_started` любая ошибка ведёт в automatic rollback code + MySQL;
- rollback считается успешным только после проверки восстановленной версии, migration status и healthcheck;
- если rollback не удалось подтвердить, installation остаётся в maintenance и journal фиксирует `rollback_failed`;
- durable journal позволяет продолжить recovery после process crash между фазами.

## Remote delivery and Admin UI

- Updater умеет получать signed manifest/package через hardened public HTTPS transport с SSRF/address policy и pinned resolved IP.
- Admin UI позволяет явно проверить signed feed и подготовить verified immutable stage.
- Browser UI намеренно не превращён в one-click destructive apply: live mutation/recovery остаётся отдельным transaction boundary.

## Upgrade from 0.14.0-beta.4

Опубликованный `v0.14.0-beta.4` появился до signed updater runtime, поэтому первый переход Beta4 → 1.0 нельзя запускать как self-update из самой Beta4.

Для него используется trusted external runner `bin/update_bootstrap.php` из доверенного 1.0 release bundle. Он:

1. проверяет точную source-version Beta4 до maintenance;
2. использует только public update trust registry;
3. выполняет signed verify/stage, external backups и release candidate;
4. запускает тот же transactional live apply, что и последующие self-updates;
5. поддерживает crash recovery через тот же durable journal.

CI release drill устанавливает две точные копии опубликованной Beta4 через реальный HTTP installer. Первая обновляется до signed 1.0 target; во второй после code switch намеренно вызывается post-update failure и проверяется automatic code + database rollback обратно до здоровой Beta4.

Подробный runbook: `docs/UPDATER_BETA4_BOOTSTRAP.md`.

## Release verification

Перед stable cut подтверждены:

- vendor-free PHP runtime;
- fresh installer и canonical 32-table schema;
- browser HTTPS/WSS smoke с native WebSocket runtime;
- licensing contracts на PHP 8.1/8.3;
- signed updater staging, backup, release-candidate, live-apply и rollback contracts;
- exact Beta4 → 1.0 upgrade/rollback drill;
- остаточный branch audit; полезные security/updater изменения из старых веток перенесены отдельными PR, устаревшие ветки не мержились целиком.

## Production signing keys

До публикации production release должны быть проведены **две независимые offline key ceremonies**:

- license signing key;
- update signing key.

В Git/release bundle добавляются только соответствующие 32-byte Ed25519 **public** keys и immutable key IDs. Private keys остаются только в контролируемом vendor/offline storage.
