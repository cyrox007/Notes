# Релизная приёмка Windows / OSPanel для 1.0.14

Этот чек-лист дополняет автоматический CI на `windows-latest` и предназначен для финальной ручной проверки updater `1.0.14` на **OSPanel 5.2.2**. Успешный GitHub-hosted Windows подтверждает базовую совместимость PHP, путей и файловых операций, но не заменяет проверку реального web-only контура на ограниченном виртуальном хостинге.

Проверка релизной сборки выполняется на контролируемых установках 1.0.12 и предыдущей опубликованной stable 1.0.13. Выпуск 1.0.13 снят с публичного канала обновлений, но остаётся обязательной исходной точкой успешного upgrade-сценария. Намеренно неисправные пакеты для rollback/recovery проверяются только на одноразовых копиях установки и базы данных и никогда не подаются рабочим пользователям.

## Что считается успехом

Оператор должен подтвердить один полный цикл:

1. чистая установка релизной сборки 1.0.14 запускается без ручной настройки private storage и не наследует recovery предыдущей установки;
2. действующая лицензия автоматически получает или обновляет credential доступа к обновлениям;
3. неисправный подписанный 1.0.14 с ошибкой миграции автоматически возвращает код и БД к 1.0.12;
4. неисправный подписанный 1.0.14 с ошибкой post-health автоматически возвращает код и БД к 1.0.12;
5. после имитации оборванного обновления первый следующий HTTP-запрос автоматически завершает recovery;
6. после одноразового совместимого updater-handoff исправный подписанный релиз 1.0.14 обнаруживается обычным интерфейсом и устанавливается штатным web-updater;
7. после всех сценариев maintenance снят, пользовательские данные сохранены, приложение и Messenger продолжают работать.
8. при `WS_ENABLED=0` Messenger сохраняет полный пользовательский набор функций через Long Poll: сообщения, файлы/медиа, редактирование и удаление, реакции, статусы, activity и непрочитанные;
9. настройка TOTP показывает локальный QR-код и запасной Base32-секрет без обращений к внешним QR API;
10. совместимый режим запускается при отключённых process API, а отсутствие WebSocket-сервера не блокирует установку и базовую работу.

Для перехода с exact `1.0.12` и `1.0.13` требуется одноразовый совместимый updater-handoff из доверенного exact-пакета 1.0.14: `php tools/release/bootstrap-1.0.12-updater.php --yes --root=<live-каталог>`. Handoff меняет только updater-контур и не меняет версию приложения или БД. После него обновление до 1.0.14 выполняется штатным подписанным web-updater; ручной SQL, правка `.env` и ручные миграции не требуются.

## Автоматический Windows gate

Workflow `.github/workflows/windows-hosting-compat.yml` выполняется на Windows и проверяет:

- Windows-пути, включая drive-letter, slash/backslash, UNC и регистр;
- staging и проверку подписанных manifest/package;
- внешний updater runtime вне рабочего дерева приложения;
- пофайловую замену без переименования верхних каталогов;
- remote delivery и проверку кандидата;
- retention recovery-артефактов;
- operator CLI как аварийный путь, а не как обязательную часть пользовательского обновления;
- совместимость основных runtime-контрактов приложения.

Отдельные Linux CI-проверки дополнительно подтверждают MySQL 8.4 и MariaDB 10.11 backup/restore, автоматический rollback и ранний boot recovery.

## Подготовка OSPanel

Используйте отдельный домен и отдельную тестовую БД, например:

```text
C:\OSPanel\domains\notes-1014-acceptance.local
C:\OSPanel\private\notes-1014-acceptance
```

Private storage должен находиться вне публичного рабочего дерева приложения. Если путь не задан вручную, приложение должно безопасно выбрать или создать внешний sibling-каталог автоматически.

Перед началом зафиксируйте:

```powershell
php -r "require 'core/Version.php'; echo Core\Version::VERSION, PHP_EOL;"
php -r "require 'core/Version.php'; echo Core\Version::VERSION_CODE, PHP_EOL;"
php bin/healthcheck.php --json
```

Ожидаемая исходная идентичность финального кандидата после релизного version bump:

```text
1.0.14
10014
```

Проверка выполняется на точном зафиксированном SHA релизной сборки `1.0.14`; последующее изменение исходников аннулирует доказательство затронутых сценариев.

## Контроль исходных данных

Создайте в тестовой установке данные, которые легко проверить после каждого сценария:

- одну заметку с уникальным текстом;
- одну задачу;
- один файл в File Manager;
- одно сообщение Messenger между двумя тестовыми пользователями;
- одну настройку профиля.

Создайте проверенный backup тестовой БД и внешнего private storage. Восстановление backup должно быть проверено до destructive-сценариев.

## Сценарий A — чистая 1.0.14 и автоматический private storage

1. Разверните точный зафиксированный пакет 1.0.14 в отдельный домен OSPanel.
2. Не создавайте вручную updater credential и не указывайте `UPDATE_CREDENTIALS_FILE`.
3. Выполните обычную установку через браузер.
4. Войдите администратором и откройте **Админ → Обновления**.
5. Убедитесь, что интерфейс показывает фактически используемый внешний private storage без раскрытия секретов.
6. Выполните проверку обновлений.
7. Подтвердите, что действующая лицензия автоматически создала credential во внешнем private storage.
8. Повторная проверка обновлений должна переиспользовать credential без кода активации и без ручной настройки пути.

Содержимое credential-файла нельзя выводить в терминал, CI, отчёт или чат.

## Сценарий A2 — private storage предыдущей установки

На одноразовой копии воспроизведите сценарий, найденный на OSPanel 5.2.2:

1. используйте тот же физический путь приложения, для которого внешний private storage уже существует;
2. оставьте валидный `workspace-maintenance.json` и journal старой updater-транзакции, чей `started_at` предшествует `INSTALL_DATE` новой установки;
3. выполните чистую установку exact 1.0.14;
4. откройте приложение обычным HTTP-запросом.

Ожидается:

- старый maintenance marker распознаётся как состояние предыдущей установки;
- автоматический rollback старой транзакции не запускается;
- валидный старый maintenance снимается через штатное владение marker;
- journal и диагностические данные не удаляются;
- приложение продолжает обычную загрузку;
- состояние `rollback_failed` не появляется.

Повреждённый marker, транзакция текущей установки или неоднозначное состояние должны по-прежнему обрабатываться fail-closed и не очищаться автоматически.

## Сценарий B — устаревший credential

На одноразовой копии поместите ранее валидный, но отозванный тестовый credential во внешний private storage.

При следующей проверке обновлений ожидается:

1. сервер отвечает `401`;
2. старый credential переносится в диагностический quarantine;
3. по действующей лицензии выполняется новый bootstrap;
4. новый credential сохраняется атомарно;
5. исходный запрос повторяется ровно один раз;
6. пользователь получает нормальный результат проверки обновлений без ручного вмешательства.

Ответ `403` не должен запускать бесконечную ротацию credential: интерфейс показывает безопасную конкретную причину ограничения.

## Сценарий C — автоматический rollback при ошибке миграции

На отдельной установке exact опубликованной 1.0.12 сначала примените одноразовый `bootstrap-1.0.12-updater.php`, убедитесь, что версия приложения и БД не изменились, затем переключите тестовый signed feed на пакет 1.0.14, у которого миграция намеренно завершается ошибкой.

Через обычный интерфейс нажмите установку обновления.

Ожидается:

- destructive apply исполняется из внешнего updater runtime, а не из рабочего `bin/core/modules`;
- файлы переключаются пофайлово;
- ошибка миграции фиксируется в журнале;
- код и БД автоматически возвращаются к exact 1.0.12;
- состояние транзакции становится `rollback_verified`;
- maintenance снимается;
- интерфейс снова доступен без CLI-восстановления.

После rollback повторно проверьте контрольные пользовательские данные.

## Сценарий D — автоматический rollback при ошибке post-health

На восстановленной exact 1.0.12 с уже применённым совместимым updater-handoff переключите signed feed на пакет 1.0.14, в котором миграции проходят, но post-update healthcheck намеренно завершается ошибкой.

Ожидается тот же итог:

- автоматический rollback к exact 1.0.12;
- восстановление БД;
- `rollback_verified`;
- отсутствие активного maintenance;
- сохранность контрольных данных;
- обычный web-runtime снова работает без действий оператора.

## Сценарий E — boot recovery после аварийного обрыва

На одноразовой копии воспроизведите контролируемый обрыв после начала destructive boundary так, как предусмотрено тестовым acceptance-сценарием.

После обрыва не запускайте ручной recovery CLI. Откройте приложение обычным HTTP-запросом.

Ожидается:

1. ранний recovery gate обнаруживает внешний maintenance marker;
2. обычные БД и модули ещё не загружаются;
3. recovery запускается через внешний updater runtime;
4. установка возвращается в согласованное состояние;
5. maintenance снимается после `committed` или `rollback_verified`;
6. при невосстановимой ошибке показывается безопасный диагностический код и идентификатор транзакции, но не секреты.

## Сценарий F — успешное обновление 1.0.12/1.0.13 → 1.0.14

Сначала на exact опубликованной 1.0.12, затем на отдельной exact опубликованной 1.0.13 примените одноразовый `bootstrap-1.0.12-updater.php`, проверьте неизменность версии приложения и БД, и только после этого переключите signed feed на исправный релизный пакет 1.0.14.

Обычный пользовательский путь:

1. приложение само обнаруживает доступное обновление;
2. уведомление ведёт в штатный интерфейс обновления;
3. одно нажатие запускает установку;
4. пользователь видит реальные этапы операции без фиктивного процента;
5. после завершения приложение сообщает новую версию;
6. maintenance отсутствует.

После обновления выполните только проверочные команды:

```powershell
php -r "require 'core/Version.php'; echo Core\Version::VERSION, PHP_EOL;"
php -r "require 'core/Version.php'; echo Core\Version::VERSION_CODE, PHP_EOL;"
php bin/healthcheck.php --json
php bin/migrate.php --status
php bin/update_doctor.php --json
```

Для принятого release-candidate ожидается:

```text
1.0.14
10014
```

## Сценарий G — совместимый updater без proc_open

На отдельной копии установки включите для **web-PHP** профиль, в котором `proc_open` находится в `disable_functions`. Доступность PHP CLI для этого сценария значения не имеет: отсутствие `proc_open` уже должно принудительно выбрать совместимый web-режим.

После перезапуска web-PHP:

1. откройте Admin → Updates;
2. убедитесь, что режим установки показан как «Совместимый с хостингом»;
3. для exact `1.0.12` сначала примените одноразовый `bootstrap-1.0.12-updater.php`, затем подайте исправный подписанный `1.0.14`;
4. нажмите установку один раз;
5. не запускайте PowerShell, CLI updater или ручные миграции.

Ожидается:

- проверка обновления не сообщает, что `proc_open` или PHP CLI обязательны;
- браузер сам выполняет последовательные шаги updater;
- maintenance пропускает только защищённое продолжение текущей updater-транзакции;
- после завершения установлена `1.0.14 (10014)`;
- при намеренной ошибке выполняется автоматический rollback без ручных команд;
- после успешного commit maintenance отсутствует;
- обычные функции приложения и Long Poll продолжают работать.

После сценария верните исходную конфигурацию web-PHP и перезапустите профиль OSPanel.

## Проверка браузера и realtime после обновления

После успешного сценария:

- вход и выход из аккаунта работают;
- Notes, Tasks, Files, Profile и Admin открываются без HTTP/PHP ошибок;
- контрольные данные сохранились;
- light, dark и system темы отображаются корректно;
- интерфейс остаётся пригодным на компактной ширине ноутбука;
- Messenger между двумя пользователями работает через WebSocket;
- при остановке WebSocket клиенты автоматически переходят на Long Poll без перезагрузки;
- сообщения продолжают доставляться;
- после восстановления WebSocket клиенты автоматически возвращаются на него без перезагрузки.

## Что записать в доказательство приёмки

Зафиксируйте без секретов:

- дату проверки;
- OSPanel 5.2.2 или OSPanel 6+; точную версию среды зафиксируйте в отчёте;
- выбранную версию PHP;
- точный SHA зафиксированной сборки 1.0.14;
- SHA-256 пакета 1.0.14;
- точный SHA и пакет исходной опубликованной 1.0.12 для upgrade/rollback-сценариев;
- публичный идентификатор update signing key;
- результат clean-install healthcheck;
- результат проверки stale maintenance/private storage предыдущей установки;
- результат автоматического credential bootstrap/refresh;
- результат rollback при ошибке миграции;
- результат rollback при ошибке post-health;
- результат boot recovery;
- результаты успешных 1.0.12 → 1.0.14 и 1.0.13 → 1.0.14;
- результат установки в совместимом режиме с отключённым `proc_open`;
- проверку сохранности контрольных данных;
- проверку WebSocket → Long Poll → WebSocket;
- проверку Long Poll-only Messenger;
- проверку локального QR при настройке 2FA;
- проверку установки без обязательных process API и WebSocket-сервера;
- визуальную проверку тем и компактной ширины.

Приватные ключи, license token, updater credential и содержимое private storage в доказательство не включаются.

## Критерий закрытия

Windows / OSPanel gate для `1.0.14` закрывается только после успешного выполнения этого чек-листа на точном зафиксированной сборке 1.0.14. Любое последующее изменение updater, private storage, Messenger transport или install/recovery-кода требует повторить затронутые сценарии на новом SHA.
