# Notes 1.2 — диагностика готовности SMTP на установленной системе

## Назначение

В административном разделе «Каналы уведомлений» теперь показываются **отдельно** препятствия и предупреждения для SMTP. Ту же проверку можно выполнить на сервере без отправки письма:

```bash
php bin/notifications_diagnose.php --json
```

В отчёте нужно смотреть блок `smtp_readiness`. Он не содержит пароля, ссылки на секрет, адреса отправителя или получателя, имя SMTP-сервера либо пользовательский текст.

Диагностика проверяет:

- наличие и включение общей конфигурации;
- допустимые параметры сервера, порта, отправителя и защищённого соединения;
- наличие секрета для соединения с авторизацией **в окружении того процесса PHP, который делает проверку**; без авторизации секрет не обязателен;
- наличие активных подписок на внешнюю почту;
- наличие свежего успешного прохода *отдельного* обработчика очереди.

Предупреждение об отдельном обработчике не означает, что резервная доставка HTTP или составной цикл Tasks не работает. Отсутствие подписок не запрещает пробную отправку, у которой собственная диагностическая категория.

Статус `needs_delivery_proof` **не означает успешную доставку**. До реального получения на контролируемом ящике статус `delivery_verified` всегда `false`.

## Проверка на установленном сервере

1. В разделе «Каналы уведомлений» проверьте найденные препятствия. Включите канал и укажите рабочий адрес отправителя, режим TLS и необходимый секрет через `env:ИМЯ_ПЕРЕМЕННОЙ`.
2. Выполните чтение диагностики **и в окружении веб-сервера, и для пользователя планировщика**. Переменная в веб-сервере может отсутствовать при запуске по cron/Windows Task Scheduler и наоборот. Не публикуйте файлы окружения.
3. Убедитесь, что пользователь, которому нужно отправлять уведомления, имеет активную почтовую подписку на нужную категорию. Пробный тест не является проверкой пользовательских категорий.
4. Убедитесь, что настроен регулярный запуск `php bin/notifications_worker.php --json` или другой документированный механизм очереди. Отметка «здоров» лишь подтверждает успешный проход, а не получение письма.
5. Через административную кнопку пробной отправки запустите **одно** письмо, найдите номер задания в истории и проверьте состояние и безопасный код ошибки. Результат `sent` означает принятие почтовым сервером.
6. Проверьте получение в контролируемом ящике, включая спам, и зафиксируйте ручное свидетельство получения или отсутствия. Это отдельный этап приёмки.

Если интерфейс недоступен, можно явно проверить конфигурацию по существующей команде:

```bash
php bin/notifications_smtp_probe.php --config-id=N --user-id=N --json
php bin/notifications_smtp_probe.php --config-id=N --user-id=N --send --json
```

Вторая команда делает настоящую отправку; применять только с согласованным контролируемым получателем. Значения `N` — числовые идентификаторы, их надо получить из собственной БД, а не придумывать.

### Сквозная проверка через реальную очередь

Для установленного сайта есть отдельный сценарий, который проверяет именно проблемную цепочку от публикации события до итогового состояния задания:

```bash
php bin/notifications_smtp_roundtrip.php --help
php bin/notifications_smtp_roundtrip.php --user-id=N --category=КАТЕГОРИЯ --confirm=SEND_ONE_LIVE_EMAIL --json
```

Он требует точную существующую категорию **включённой** пользовательской почтовой подписки и действующего пользователя с E-mail. Команда создаёт **одно** встроенное уведомление, находит связанное задание `email`, захватывает только его, выполняет попытку SMTP и читает итоговое состояние. Другие отложенные уведомления не обрабатываются. Результат `email_job_not_created` доказывает проблему на этапе подписки/настройки/постановки в очередь, а не сетевой сбой. `delivery_not_confirmed` указывает на необходимость смотреть безопасный `result_code` и очередь попыток.

Ключ подтверждения обязателен, потому что команда действительно отправляет письмо. JSON не содержит адреса получателя, SMTP-сервер, секрет и тело сообщения. Состояние `accepted_by_smtp` означает **только приём письма сервером**, фактическое получение адресатом фиксируется отдельно.

Эта команда не исправляет настройки, планировщик или сеть и не заменяет подтверждение на настоящем почтовом ящике.

### Проверки разработчика

```bash
php -l app/services/notifications/SmtpOperationalReadiness.php
php tests/integration/notification_smtp_readiness_12.php
php tests/integration/notification_smtp_guidance_12.php
```

CI проверяет только логику и отсутствие утечек. Он не имеет доступа к пользовательскому SMTP, серверу Notes, реальному почтовому ящику и системному расписанию. Поэтому задача #429 остаётся открытой до подтверждённой доставки на установленной системе.
