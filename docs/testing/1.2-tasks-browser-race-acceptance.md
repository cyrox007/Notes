# Браузерная приёмка конкурентных изменений Tasks 1.2

## Что изменилось

Для каждой карточки личной или командной задачи теперь допускается не более одной изменяющей команды в полёте. Если человек быстро дважды нажмёт «Сохранить» или переключит статус параллельно с редактированием, клиент не отправит второе изменение поверх первого. Пока сервер отвечает, карточка имеет атрибут `aria-busy=true`. После успеха или сбоя ограничение снимается.

Серверные гарантии остаются обязательными: `expected_version` предотвращает незаметную перезапись данных другой вкладки, а `command_id` обеспечивает повторобезопасность после потери сетевого ответа. Браузерное ограничение **не заменяет** атомарные транзакции и проверки доступа на сервере.

## Проверяемые случаи

Автоматизированные испытания запускают настоящий Chromium с производственными JavaScript-файлами и разметкой личной задачи, сформированной текущим PHP-шаблоном.

1. Быстрое двойное сохранение личной задачи вызывает ровно один запрос.
2. Версионный конфликт HTTP 409 показывает фактические данные и новую версию, не перезагружая страницу.
3. Временная ошибка HTTP 503 сохраняет идентификатор изменяющей команды для безопасного повтора, разблокирует форму и не меняет версию.
4. При сохранении статуса второе редактирование той же карточки не отправляется.
5. Ошибка сохранения статуса возвращает визуальное состояние к последней подтверждённой версии.
6. В командной доске две разные формы одной карточки не отправляются одновременно; успешно изменённая карточка перемещается между колонками.
7. Конфликт общей задачи обновляет версию и состояние из ответа сервера без слепой перезаписи.
8. На отдельных базах MySQL 8.4 и MariaDB 11.4 проверяются защита от повторного выполнения команды, конфликт версии и запрет изменения чужой задачи.

Тестовые HTTP-ответы браузерной части имитируются управляемым транспортом: можно задержать ответ и действительно послать несколько действий из Chromium. Транзакционная часть проверяется отдельно на настоящей БД. **Это ещё не полный внешний браузерный цикл установленного сервера:** для финальной приёмки нужны тесты на развёрнутом приложении с двумя авторизованными вкладками, настоящими POST-запросами и устройствами пользователя.

## Запуск

```sh
node tests/e2e/tasks-versioned-browser-race-12.mjs
php tests/integration/tasks_api_write_mysql_12.php
```

Для браузерного теста требуются Node.js и Playwright с установленным Chromium. Для теста БД обязательна отдельная база с `test` в имени; параметры подключения задаются `TEST_DB_*`. Ни один из этих сценариев нельзя запускать на рабочей базе данных.

## Ограничения и дальнейшая приёмка

Сетевой сбой, во время которого сервер успел применить изменение, безопасно обрабатывается сохранённым `command_id`; после конфликта формируется новая команда. Ни одно локальное состояние «успешно» не считается доказательством того, что сервер принял изменение до получения соответствующего ответа.

Перед релизом 1.2 дополнительно требуются подтверждённые пользовательские сценарии на мобильном экране, две реальные сессии с общей доской, изменение прав во время открытой страницы, полная проверка установки/обновления и нагрузочная приёмка.
