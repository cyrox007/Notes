# Notes 1.2 — полный переход миграций с префиксом таблиц

## Цель

Проверить, что мигратор 1.2 действительно выполняет **все** новые миграции над схемой из опубликованного тега `v1.1.0` при `DBPREFIX=''` и `DBPREFIX=nt12_`. Существующая предварительная проверка настраивала лишь журнал и не заменяла полноценный переход.

## Испытательный стенд

Процесс `.github/workflows/upgrade-11000-full-migrations.yml` использует матрицу из двух СУБД — MySQL 8.4 и MariaDB 11.4 — двух режимов префикса и двух состояний исторического журнала, всего восемь независимых заданий. Для каждого задания:

1. Получает исходное дерево опубликованного тега `v1.1.0` отдельно от проверяемого SHA ветки `1.2`.
2. Берёт набор схем **опубликованной** версии, преобразует только SQL-идентификаторы через `Core\DatabasePrefix` из кандидата, создаёт таблицы в отдельной временной базе.
3. При непустом префиксе предварительно создаёт чужую таблицу `users` с контрольным значением. Для режима «с журналом» в таблицу `schema_migrations` записываются 36 исторических миграций 1.1.0 с контрольными суммами. Для режима «без журнала» соответствующую исходную базовую запись формирует штатный мигратор.
4. Добавляет контрольного пользователя в логическую таблицу `users`, запускает `UpdateDatabaseMigrator` сначала на просмотр, затем на полное применение.
5. Проверяет количество новых миграций, целевой контракт таблиц, сохранность пользователя и журнала.
6. Повторяет выполнение, убеждается, что миграции не запускаются вторично.
7. При непустом префиксе сверяет чужую таблицу и отсутствие непрефиксированного журнала `schema_migrations`.

Испытание не меняет реальные данные и использует только базу с `test` в названии.

Эта матрица доказывает корректность *SQL-этапа*, но не заменяет подписанный пакет, полный Admin → Updates, прерывания транзакции, сравнение файлового хранилища, реальную Windows/OSPanel, восстановление и проверку результата на окончательном SHA 1.2.0. Состояние задачи #425 остаётся открытым.
