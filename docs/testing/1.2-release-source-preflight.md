# Notes 1.2 — предварительная проверка исходников релиз-кандидата

## Назначение

Это самостоятельная проверка ветки 1.2, **не замена** исторической приёмки выпуска 1.0.16 и не подтверждение готовности выпуска 1.2.0. Она не меняет текущую версию приложения и не публикует релиз.

Проверяются: точное совпадение 40-символьного SHA, версия 1.2.0 и код 12000 со статусом stable, указанная дата релиза, идентичность README и CHANGELOG, отдельное описание `docs/releases/v1.2.0.md`, требование PHP не ниже 8.3, реестр миграций и наличие каждого перечисленного SQL-файла.

Текущая ветка `1.2` пока объявляет версию `1.1.0`, а описание выпуска 1.2 отсутствует. Поэтому **строгая проверка реального кандидата сейчас обязана отказывать**. Объявлять успех только по зелёному тесту контракта нельзя: тест проверяет, что инструмент умеет безопасно отклонять неподготовленное состояние.

## Использование

В GitHub Actions выбирают процесс «1.2 — контракт и предварительная проверка релиз-кандидата» и выполняют ручной запуск на выбранном коммите, передав его точный SHA в `expected_sha`. При расхождении коммита, версии и документации команда завершится с ошибкой.

Сама команда в GitHub Actions:

```bash
php bin/release_12_source_preflight.php --expected-sha=ПОЛНЫЙ_SHA --json
```

Вне GitHub Actions переменная `GITHUB_SHA` отсутствует, и проверка не должна молча принимать неизвестный коммит.

Для разработки:

```bash
php -l core/Release12SourcePreflight.php
php -l bin/release_12_source_preflight.php
php tests/integration/release_12_source_preflight_contract.php
```

## Что не подтверждено

Даже статус `source_eligible` устанавливает `release_ready=false`. Отдельно требуются защита веток и независимое одобрение, подписи и проверка доверенных ключей, полный переход с 1.1 и восстановление, DBPREFIX, настоящая почтовая доставка, приёмка нарядов, Android/iOS/Windows, межбраузерные испытания и нагрузка 1000 пользователей. Эти доказательства должны относиться к **тому же окончательному SHA**. Задачи #425, #426, #429, #421 и #274 не закрываются этим этапом.

После завершения всех внешних проверок должен быть создан самостоятельный строгий релизный барьер, подтверждающий доказательства, а не только исходники.
