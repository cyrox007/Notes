# Статус релизной линии Workspace Organizer 1.0.x

> **Обновлено 28 сентября 2026.** Текущий релиз-кандидат — `1.0.7 (10007)`. Тег `v1.0.7` и GitHub Release до финального решения владельца не создаются.

## Текущее состояние 1.0.7

- версия релиз-кандидата: `1.0.7`;
- код версии: `10007`;
- статус приложения: `stable`;
- исходная опубликованная версия для обновления: `v1.0.6`;
- релизная ветка: `release/1.0.7-rc`;
- релизный PR: `release/1.0.7-rc → master`;
- публикация `v1.0.7`: **ещё не выполнена**;
- merge релизного PR в `master` разрешён только после ручной приёмки и отдельной команды владельца релиза.

## Что завершено

### Код и автоматические проверки

- исправлена обработка stale maintenance/recovery от предыдущей установки;
- Long Poll стал полноценным резервным realtime-транспортом без обязательного WebSocket;
- переход `1.0.6 → 1.0.7` проверяется сквозным браузерным сценарием;
- автоматический rollback проверяется отдельно при ошибке миграции и при ошибке post-health;
- ранний boot recovery выполняется до обычного bootstrap приложения;
- обновление из Admin больше не требует `proc_open` и отдельного PHP CLI;
- при ограничениях shared hosting автоматически используется пошаговый web-режим без shell/process API;
- `proc_open`/PHP CLI остаются только необязательным ускоренным режимом;
- capability-продолжение web-updater хранит на диске только SHA-256 токена;
- recovery выполняется из отдельного проверенного runtime вне live-tree;
- минимальная поддерживаемая версия PHP остаётся 8.1, совместимость проверяется также на новых версиях;
- полный набор автоматических workflow должен быть зелёным на **точном финальном HEAD**, а результаты предыдущего SHA после любого изменения не переносятся автоматически.

До финальной подготовки документации и hosting-package предыдущий runtime-кандидат прошёл полный прогон **67/67**. После любого финального prep-изменения требуется новый exact-head прогон.

## Что осталось до публикации v1.0.7

### 1. Финальная Windows / OSPanel-приёмка

Выполнить `docs/WINDOWS_OSPANEL_ACCEPTANCE.md` на точном финальном SHA:

- чистая установка 1.0.7;
- сохранность данных и лицензии;
- stale maintenance/private storage;
- реальный `1.0.6 → 1.0.7` одной кнопкой;
- rollback при ошибке миграции;
- rollback при ошибке post-health;
- boot recovery после контролируемого обрыва;
- WebSocket → Long Poll → WebSocket;
- совместимый updater с отключённым `proc_open`, без обязательного PHP CLI;
- визуальная проверка основных модулей и компактной ширины.

CI не заменяет эту операторскую проверку.

### 2. Проверить production trust roots

До публикации:

- license и update используют разные пары Ed25519;
- в репозитории и release bundle находятся только публичные trust roots;
- приватные ключи не попадают на сервер приложения, в GitHub, CI, логи, артефакты или чат;
- license canary и update-manifest canary проходят на exact release-candidate.

Процедура описана в `docs/PRODUCTION_TRUST_CEREMONY.md`.

### 3. Зафиксировать финальный hosting package

Tag-driven `Build hosting package` должен:

1. собирать `workspace-organizer-v1.0.7.zip` из exact tagged SHA;
2. проверять обязательные runtime-файлы, включая web-updater/recovery;
3. исключать `.env`, tests, internal tools, vendor и приватный signing material;
4. создавать SHA-256 и source-SHA sidecar;
5. не перепаковывать уже опубликованный immutable release.

### 4. Опубликовать релиз

После закрытия ручной приёмки:

1. слить exact accepted `release/1.0.7-rc` в `master`;
2. дождаться зелёного `Stable release gate` на push в `master`;
3. workflow публикации создаст неизменяемый аннотированный тег `v1.0.7`;
4. tag-driven `Build hosting package` соберёт ZIP и GitHub Release;
5. через control plane опубликовать подписанный stable feed для `1.0.7`;
6. на обычной лицензированной установке проверить feed → manifest → signature → package;
7. сверить checksum уже опубликованного ZIP.

## Ветки

- `master` — опубликованная основная линия; до решения о релизе 1.0.7 не изменяется релизным PR;
- `release/1.0.7-rc` — единственный источник текущего 1.0.7 release-candidate;
- временные fix/refactor ветки после merge не являются источником релиза.

Старую ветку нельзя вливать только ради очистки списка: сначала проверяется, содержит ли она уникальное изменение, отсутствующее в RC.
