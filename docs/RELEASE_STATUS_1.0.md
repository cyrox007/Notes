# Статус релизной линии Workspace Organizer 1.0.x

> **Обновлено 26 сентября 2026.** Последний опубликованный GitHub Release — `v1.0.4`. Код `1.0.5 (10005)` уже находится в `master`, но тег `v1.0.5` и неизменяемый публичный релиз ещё не созданы.

## Текущее состояние 1.0.5

- версия в `master`: `1.0.5`;
- код версии: `10005`;
- статус приложения: `stable`;
- последний опубликованный тег: `v1.0.4`;
- `v1.0.5`: **ещё не опубликован**;
- переход `1.0.4 → 1.0.5` проверяется как последний переходный путь через Admin → Updates;
- постоянный контракт `автоматическое уведомление → одна кнопка → подписанная транзакционная установка` начинается с `1.0.5 → 1.0.6`;
- автоматический откат проверяет как отказ миграции после начала изменения рабочих файлов, так и отказ post-update healthcheck;
- раннее восстановление после аварийного завершения выполняется до запуска БД и прикладных модулей.

## Что уже завершено

### Исходники и автоматические проверки

- фундамент одношагового обновления 1.0.5 слит в `master`;
- устранены прямые зависимости updater, обнаруженные сквозным rollback-тестом;
- exact `v1.0.4 → 1.0.5` входит в актуальный browser E2E;
- два намеренно неисправных подписанных 1.0.6 проверяют автоматический возврат на 1.0.5 после ошибки миграции и после ошибки post-health;
- исправный тестовый 1.0.6 проверяет последующее успешное одношаговое обновление;
- maintenance/recovery проверяется отдельным сценарием первого следующего HTTP-запроса;
- README, CHANGELOG, `docs/releases/v1.0.5.md` и финальный release acceptance уже используют идентичность 1.0.5.

### Продуктовая дорожная карта

- «Дефекты» и «Наряды и допуски» зафиксированы как независимые автономные модули;
- у «Дефектов» собственный цикл «регистрация → контроль → закрытие → отчётность» без обязательных перекрёстных связей;
- SMS-шлюз остаётся перспективным необязательным аварийным каналом системных уведомлений и не входит в Core или релизный объём 1.0.5.

## Что осталось до публикации v1.0.5

### Синхронизация стабилизационной ветки — завершена

Защищённая ветка `1.0` синхронизирована с составом 1.0.5 через pull request. Точный HEAD стабилизационной ветки повторно проходит полный релизный набор; любое последующее изменение требует нового exact-head прогона.

### 1. Завершить операторскую приёмку

На Windows/OSPanel 5.2.2 и репрезентативном окружении необходимо подтвердить пункты `docs/RELEASE_ACCEPTANCE.md`:

- backup + restore drill;
- `php bin/healthcheck.php --json`;
- HTTPS/WSS и автоматический Long Poll fallback с возвратом на WebSocket;
- automatic update credential по действующей лицензии;
- реальный переход exact `1.0.4 → 1.0.5`;
- два автоматических rollback-сценария тестового 1.0.6;
- успешное одношаговое обновление на исправный тестовый 1.0.6;
- визуальную приёмку light/dark/system и компактной ширины;
- 2FA/TOTP;
- отсутствие открытых P0/P1 и release-blocking регрессий.

CI не заменяет эти операторские проверки.

### 2. Проверить production trust roots

До публикации:

- license и update используют разные пары Ed25519;
- в репозитории и артефакте присутствуют только публичные trust roots;
- приватные ключи не попадают на сервер приложения, в GitHub, CI, логи, артефакты или чат;
- license canary и update-manifest canary проходят на точном принятом релиз-кандидате.

### 3. Зафиксировать неизменяемый артефакт

После завершения приёмки:

1. собрать `workspace-organizer-v1.0.5.zip` из точного принятого SHA;
2. проверить ZIP, SHA-256 и source-SHA;
3. сформировать update manifest с точными version/version-code/source commit;
4. подписать точные bytes manifest offline-приватным update key;
5. проверить подпись публичным trust registry;
6. после принятия SHA-256 не перепаковывать ZIP.

### 4. Опубликовать релиз

Только после предыдущих пунктов:

1. создать аннотированный тег `v1.0.5` на точном принятом SHA;
2. опубликовать GitHub Release с уже принятым ZIP и sidecar-файлами;
3. через control plane `jsint-site` опубликовать подписанный stable feed;
4. на обычной лицензированной установке проверить загрузку feed, manifest, signature и package;
5. проверить checksum уже опубликованного файла.

## Ветки

- `master` — текущий код 1.0.5 и дальнейшая основная линия;
- `1.0` — защищённая стабилизационная ветка, синхронизированная с принятым составом 1.0.5;
- старые `fix/1.0.3-*`, `release/publish-1.0.3`, `release/publish-1.0.4` и тестовые ветки не являются источником новых изменений без отдельной проверки.

Устаревшую ветку нельзя вливать только ради очистки списка: сначала проверяется, есть ли в ней уникальное изменение, отсутствующее в актуальном коде.

## Правило остановки

До появления тега `v1.0.5` версия 1.0.5 считается релиз-кандидатом, даже если `core/Version.php` уже содержит статус `stable`.

Любое изменение исходников после заморозки accepted SHA аннулирует exact-head доказательства для затронутых gates. Релиз нельзя объявлять опубликованным только по факту зелёного CI или наличия версии 1.0.5 в `master`.
