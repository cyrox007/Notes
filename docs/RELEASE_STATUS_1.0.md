## Оставшийся операторский gate: stable update feed

Публикация GitHub Release не равна публикации доверенного update feed.

Следующий обязательный шаг выполняется через control plane `jsint-site`:

1. открыть Admin → Releases → «Выпустить»;
2. control plane должен взять последний официальный GitHub Release `v1.0.4`;
3. сервер проверяет Git tag, source SHA, GitHub digest, SHA-256 sidecar и версию внутри ZIP;
4. exact manifest подписывается приватным update key только на компьютере оператора или сохранённым в браузере неэкспортируемым ключом;
5. на сервер передаются только manifest, detached signature и ссылка на уже проверенный package;
6. после публикации stable feed проверить доступ к `feed.json`, manifest, signature и package через обычный лицензированный клиент.

Приватный `.update-secret` не должен попадать на сервер, в GitHub, CI, логи или чат.

## Финальная эксплуатационная проверка 1.0.3 → 1.0.4

После появления 1.0.4 в подписанном stable feed на реальной Windows/OSPanel 5.2.2 установке:

1. исходная установка должна быть exact `1.0.3 (10003)` и активирована;
2. Admin → Updates получает подписанный stable feed;
3. PHP CLI обнаруживается автоматически без ручного `UPDATE_PHP_BINARY`, если `php.exe` находится рядом с web-PHP или доступен через абсолютный каталог `PATH`;
4. установка проходит staging, backup, release candidate, live apply и post-update healthcheck;
5. после обновления приложение сообщает `1.0.4 (10004)`;
6. журнал транзакции имеет состояние `committed`;
7. maintenance marker снят;
8. основные пользовательские данные и вход остаются рабочими.

Если этот реальный сценарий обнаружит дефект, он открывается как новый воспроизводимый дефект 1.0.4. Старые закрытые пункты аудитов автоматически не переоткрываются.
