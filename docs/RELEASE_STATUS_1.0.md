## Что вошло в 1.0.13

### Лицензионный состав модулей

Каждый встроенный прикладной модуль имеет собственное `license.feature`:

- `workspace.admin`;
- `workspace.notes`;
- `workspace.tasks`;
- `workspace.files`;
- `workspace.messenger`;
- `workspace.profile`.

Модуль запускается только если действующая подписанная лицензия явно содержит его feature. Пустой или отсутствующий список `features` не даёт неявного полного доступа.

Если разрешения нет:

- операторский `configured_state` сохраняется;
- фактическое состояние становится `unlicensed`;
- provider, capability и маршруты не загружаются;
- соседние модули не получают точки интеграции;
- данные модуля не удаляются.

### Управление модулями

Суперадминистратор управляет разрешёнными лицензией модулями через **Admin → Модули**.

- отключение модуля не удаляет данные;
- разрешения ролей и ролевые политики сохраняются;
- нелицензированные модули не показываются в панели управления;
- Admin является обязательным системным модулем и не может быть отключён операторским переключателем;
- при отсутствии `workspace.admin` остаётся независимая core-страница восстановления лицензии.

### Межмодульная изоляция

Отключённый или нелицензированный модуль:

- не входит в `enabledComposition()`;
- не отображается в общей навигации и на главной;
- не оставляет пользовательские действия в Messenger и Profile;
- не регистрирует свои HTTP-маршруты и runtime-provider;
- не оставляет фоновой WebSocket-службы Messenger после отзыва соответствующего разрешения.

### Обновление

Проверяемый переход релизной матрицы:

`1.0.12 → встроенный подписанный updater → 1.0.13`.

Миграция `20260930_module_entitlements.sql` добавляет состояние `unlicensed`. Обновлятор учитывает короткое окно до применения миграции, сохраняет возможность rollback и корректно останавливает WebSocket, если Messenger после обновления больше недоступен.

## Публикация и эксплуатационный ввод

GitHub Release и релизный ZIP уже опубликованы.

Следующий операторский шаг выполняется **после публикации GitHub Release** и не является основанием задерживать сам выпуск:

1. занести `v1.0.13` и её артефакты в реестр релизов на внешнем сайте;
2. опубликовать/обновить stable-feed так, чтобы обычная установка увидела 1.0.13;
3. выполнить контрольное обновление лицензированной установки `1.0.12 → 1.0.13` через опубликованный канал;
4. если эксплуатационная проверка выявит дефект, выпустить следующий patch-релиз линии 1.0.x, не изменяя опубликованный тег 1.0.13.

До появления записи в реестре отсутствие 1.0.13 в пользовательском update-feed является ожидаемым состоянием, а не дефектом релиза.
