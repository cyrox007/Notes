# Релизная приёмка Windows / OSPanel для 1.0.15

Этот чек-лист дополняет автоматический CI и проверяет главное пользовательское требование 1.0.15: **существующая установка 1.0.14 должна обновляться до 1.0.15 без переустановки с нуля**.

Целевая среда ручной проверки — OSPanel 5.2.2 на Windows.

## Исходная точка

Используется exact опубликованный `v1.0.14` с существующими пользовательскими данными.

До обновления необходимо зафиксировать:

- версию `1.0.14 (10014)`;
- Installation ID и состояние лицензии;
- одного обычного пользователя и суперадминистратора;
- одну заметку;
- одну задачу;
- один файл с известным SHA-256;
- один диалог Messenger и одно сообщение;
- путь и размер private storage.

Для перехода 1.0.14 → 1.0.15 повторный `bootstrap-1.0.12-updater.php` запрещён как ненужный: исправленный updater уже входит в 1.0.14.

## Сценарий A — штатное обновление

1. Откройте **Admin → Updates** на exact 1.0.14.
2. Убедитесь, что предлагается именно 1.0.15.
3. Запустите обновление обычной кнопкой интерфейса.
4. Не копируйте файлы вручную, не запускайте SQL и не переустанавливайте приложение.
5. Дождитесь успешного commit и обычного выхода из maintenance.
6. Выполните новый HTTP-запрос и убедитесь, что интерфейс показывает `1.0.15 (10015)`.

После обновления должны сохраниться Installation ID, лицензия, пользователи, роли, заметка, задача, файл, private storage, диалог и сообщение Messenger.

## Сценарий B — пользовательские регрессии 1.0.14

На обновлённой установке проверить:

- переключение между вкладками браузера не оставляет Messenger в бесконечном восстановлении;
- загрузка файла сразу показывает его без F5;
- созданная папка сразу появляется без F5;
- переименование и удаление синхронизируются без полной перезагрузки;
- регистрация показывает фирменный знак и `+7`;
- код приглашения копируется отдельной кнопкой;
- на узком экране действия Messenger раскрываются под сообщением и не уменьшают ширину текста.

## Сценарий C — восстановление

На одноразовой копии установки проверить отказ после destructive-фазы и штатный rollback.

После `rollback_verified`:

- приложение возвращается к исходной версии;
- maintenance снимается;
- пользовательские данные и private storage сохраняются;
- следующий обычный HTTP-запрос открывает приложение без ручной очистки state-файлов.

Состояние `rollback_failed` является блокирующим дефектом релиза.

## Приёмка

Windows / OSPanel gate для 1.0.15 закрывается только после проверки exact release candidate. Изменение updater, File Manager, Messenger transport или install/recovery-кода после проверки требует повторить затронутые сценарии.
