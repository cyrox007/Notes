# Производительность Workspace Organizer: 1000 одновременных пользователей

Актуально: 26 сентября 2026.

## Цель

Workspace Organizer должен комфортно обслуживать **не менее 1000 одновременно активных авторизованных пользователей** на документированной эталонной конфигурации.

Цель относится ко всей системе, а не к одному модулю. Новый модуль не считается готовым к производственной линии, если его типичный сценарий разрушает общий бюджет производительности.

Версия 1.0.5 остаётся замороженным релиз-кандидатом и не обязана доказывать этот новый масштаб задним числом. Контракт становится обязательной инженерной границей для дальнейшего развития 1.1+.

## Что именно считается 1000 одновременных пользователей

Нагрузочный профиль должен создавать 1000 независимых авторизованных сессий и поддерживать их одновременно в течение всего устойчивого этапа теста.

Сессии должны выполнять реалистичную смесь действий, а не один искусственный GET-запрос:

- открытие главной страницы и навигация между модулями;
- списки Notes, Tasks, Files и Messenger;
- поиск и фильтрация;
- чтение карточек;
- создание и изменение небольших записей;
- фоновые проверки уведомлений;
- Messenger realtime;
- ограниченная доля загрузок и скачиваний файлов;
- административные операции в небольшой доле нагрузки;
- для будущих модулей — типичные реестры, фильтры и отчётные выборки.

Между действиями используется реалистичное пользовательское ожидание. Тест не должен моделировать ситуацию, когда каждый из 1000 пользователей непрерывно посылает запросы без пауз, если такой режим не соответствует реальной эксплуатации.

## Эталонная конфигурация

Результат «1000 пользователей поддерживается» действителен только вместе с опубликованным профилем инфраструктуры:

- количество HTTP-узлов;
- количество WebSocket-узлов;
- CPU и RAM каждого узла;
- версия PHP и модель запуска PHP;
- число PHP-работников и их ограничения;
- версия и конфигурация MySQL;
- максимальное число соединений БД;
- наличие и назначение Redis либо другого общего быстрого хранилища;
- тип private storage;
- пропускная способность сети;
- версия приложения и точный commit;
- размер тестовой БД и объём файлов.

Нельзя заявлять ёмкость 1000 пользователей без этой информации.

## Пользовательские критерии

На устойчивом этапе при 1000 параллельных сессиях:

- не должно быть массовых HTTP 5xx, необработанных исключений и зависаний;
- доля ошибок рабочих запросов должна оставаться ниже 0,5%;
- p95 обычных операций чтения должен укладываться в 700 мс на серверной стороне;
- p95 обычных операций изменения данных должен укладываться в 1200 мс;
- p99 обычных операций не должен превышать 2500 мс, кроме явно тяжёлых фоновых операций;
- интерфейс не должен превращать массовую работу в последовательную очередь из-за глобальной блокировки сессии;
- Messenger не должен терять устойчивые сообщения при переключении WebSocket ↔ Long Poll;
- после завершения пикового этапа система должна возвращаться к нормальной задержке без ручного перезапуска.

Если отдельная операция по природе тяжёлая — большой импорт, экспорт, отчёт или массовая обработка — она переводится в фоновую задачу с видимым состоянием, а не увеличивает допустимую задержку обычного запроса.

## Профиль испытаний

Минимальная приёмка состоит из трёх этапов.

### Разогрев

- 5–10 минут;
- постепенный рост от малой нагрузки до 1000 активных сессий;
- проверка отсутствия лавины соединений, компиляции, кэшей и блокировок при старте.

### Устойчивая нагрузка

- не менее 30 минут;
- 1000 активных сессий;
- реалистичная смесь чтения/записи/realtime;
- сбор p50/p95/p99, ошибок, RPS, SQL и системных метрик.

### Длительная проверка

- не менее 2 часов;
- не менее 1000 подключённых сессий с реалистичной активностью;
- контроль утечек памяти, накопления очередей, роста числа соединений, незавершённых транзакций и деградации задержек.

Дополнительно выполняется краткий пиковый этап выше штатной нагрузки, чтобы проверить управляемую деградацию и восстановление после пика.

## База данных

До достижения целевой ёмкости обязательны:

- инвентаризация самых частых и самых медленных SQL-запросов;
- `EXPLAIN ANALYZE` для критических выборок на объёмах, близких к производственным;
- индексы под реальные фильтры, сортировки и связи;
- запрет N+1 в списках;
- пагинация всех потенциально больших реестров;
- отсутствие неограниченных `SELECT *` для пользовательских списков;
- короткие транзакции без сетевых и файловых операций внутри;
- контроль lock wait/deadlock и понятный повтор безопасных транзакций;
- ограничение числа соединений со стороны приложения;
- отдельный бюджет для фоновых работников и realtime-процессов.

Новый модуль обязан поставлять индексы и нагрузочные данные вместе со своей схемой.

## HTTP и PHP

Основной HTTP-контур должен быть пригоден к горизонтальному масштабированию:

- обработчик запроса не хранит незаменимое состояние только в памяти одного процесса;
- блокировка PHP-сессии снимается до ожидания внешних событий и длительных операций;
- число PHP-работников ограничено и соотнесено с БД, а не увеличивается бесконтрольно;
- тяжёлые действия имеют ограничения времени, размера и количества элементов;
- большие списки получают серверную пагинацию;
- повторяющиеся системные настройки, роли и безопасные справочники кэшируются с явной инвалидизацией;
- входящие запросы имеют backpressure/rate-limit там, где перегрузка опаснее контролируемого отказа.

## Realtime и Messenger

Для 1000 пользователей realtime не должен отбирать все HTTP-ресурсы:

- WebSocket остаётся основным быстрым каналом;
- Long Poll остаётся резервом и не удерживает PHP-сессионную блокировку;
- соединения, очереди отправки и буферы имеют верхние пределы;
- медленный клиент не может неограниченно накапливать данные в памяти сервера;
- измеряются число активных соединений, скорость reconnect и очередь исходящих событий;
- если одного WS-узла недостаточно, вводится межузловой pub/sub/fan-out и общий механизм маршрутизации событий;
- несколько WS-узлов не должны дублировать или терять устойчивые сообщения.

До реализации межузлового fan-out текущая single-node граница должна быть явно обозначена в документации и не выдаваться за горизонтально масштабируемую архитектуру.

## Фоновые задачи

В отдельный фон должны уходить операции, которые не нужны для формирования текущего HTTP-ответа:

- большие отчёты;
- импорт/экспорт;
- пакетная обработка файлов;
- массовые уведомления;
- обслуживание индексов;
- длительные операции будущих модулей.

Очередь должна иметь:

- ограничение размера;
- приоритеты;
- повтор с пределом;
- идемпотентность там, где возможен повтор;
- dead-letter/ошибочное состояние;
- метрики длины очереди и времени ожидания.

## Файлы и хранилище

- загрузки и скачивания не должны полностью буферизоваться в памяти PHP;
- большие файлы передаются потоково;
- метаданные файлов и содержимое разделяются;
- операции листинга всегда ограничены и пагинированы;
- антивирусная/медиа-обработка при появлении должна выполняться асинхронно;
- при нескольких HTTP-узлах private storage должен иметь согласованную модель общего доступа либо чёткую маршрутизацию к владельцу данных.

## Наблюдаемость

Для нагрузочного прогона собираются как минимум:

- p50/p95/p99 задержек;
- RPS;
- доля 4xx/5xx по маршрутам;
- CPU, RAM и swap;
- число PHP-работников: активные/ожидающие;
- число соединений MySQL;
- количество и p95 времени SQL-запросов;
- slow queries;
- deadlock/lock wait;
- длина фоновых очередей;
- активные WebSocket-соединения;
- reconnect rate;
- использование файлового хранилища и I/O;
- ошибки приложения и события безопасности.

Результат теста сохраняется как артефакт с точным commit и конфигурацией окружения.

## Этапы оптимизации

### Этап 1 — измерение базового состояния

- создать репрезентативный набор данных;
- расширить генератор нагрузки до независимых пользователей;
- снять профиль CPU, RAM, SQL и маршрутов;
- зафиксировать исходные p95/p99 и максимальную устойчивую ёмкость.

### Этап 2 — БД и списки

- устранить N+1;
- добавить/исправить индексы;
- перевести большие списки на серверную пагинацию;
- сократить повторные запросы системных настроек и прав;
- убрать полные сканирования из горячих пользовательских путей.

### Этап 3 — HTTP и фоновые операции

- настроить модель PHP-работников под реальный профиль;
- вынести тяжёлые синхронные операции в очередь;
- добавить ограничение параллельности и backpressure;
- устранить ненужные глобальные блокировки.

### Этап 4 — realtime

- доказать устойчивость одного WS-узла на целевой нагрузке;
- при недостаточном запасе добавить несколько узлов и общий pub/sub/fan-out;
- проверить массовый reconnect и переключение на Long Poll без шторма запросов.

### Этап 5 — эталонная приёмка 1000 пользователей

- выполнить полный профиль разогрев → 30 минут устойчивой нагрузки → 2 часа длительной проверки;
- подтвердить пользовательские критерии;
- сохранить отчёт и конфигурацию;
- только после этого обозначать 1000 одновременных пользователей как подтверждённую ёмкость.

## Автоматические проверки

Текущая `.github/workflows/release-evidence.yml` использует малую параллельность и остаётся быстрым регрессионным тестом. Его нельзя просто заменить на 1000 параллельных запросов на общем GitHub runner: такой результат будет измерять лимиты случайной CI-машины, а не производственную ёмкость Workspace Organizer.

Нужны два уровня:

1. быстрый обязательный CI smoke, который ловит крупные регрессии;
2. отдельный воспроизводимый performance-runner/эталонное окружение, где выполняется полная нагрузка 1000 пользователей и сохраняется отчёт.

Перед стабильным минорным релизом полный нагрузочный отчёт на точном релизном SHA должен быть актуальным.

## Правило для будущих модулей

Любой новый модуль до слияния обязан ответить на четыре вопроса:

1. Какие запросы и операции становятся горячими при 1000 пользователях?
2. Какие индексы, лимиты и пагинация это обеспечивают?
3. Какие действия должны выполняться в фоне?
4. Как модуль проверяется под нагрузкой и какой бюджет ресурсов добавляет?

Функция, которая работает только на малой тестовой БД и не имеет ограничений объёма, не считается завершённой.
